# Shared custom runtime and orchestration

## 1. Status and scope

**Status: ACCEPTED architecture decision.** MyStacks uses a common Mastra-based custom runtime and curated tools, with direct normal-chat execution, queued background work, and durable user-scoped state outside worker processes. A [Cloud Run API service and separate worker pool](0017-cloud-run-worker-pool.md) host those entrypoints; BullMQ queue state uses [dedicated managed Valkey storage](0020-managed-valkey-queue-storage.md). This records the design, not an implemented service; the overall architecture remains tentative.

The [requirements](../requirements.md) own product behavior, and the [architecture](../architecture.md) owns responsibilities and flows. This decision preserves Phase 1 informational work, read-only financial access, and the exclusion of specific investment recommendations.

## 2. Decision

The **orchestration layer** binds incoming work to an authenticated user, routes that work, and delivers progress and results. The **custom runtime** uses Mastra's regular `Agent` and core facilities to execute the agent loop, load context, apply skills, and select and compose tools. These logical responsibilities use the same backend codebase with distinct API/chat and worker entrypoints and deployments. The API service uses Cloud Run instance-based billing so CPU remains available after HTTP acknowledgement. This independent project owns its deployments, PostgreSQL, Valkey, identities, secrets, configuration, pipeline, and resources; sibling projects supply reference conventions only. The [framework decision](0005-mastra-runtime-framework.md) owns the selection rationale and adoption scope, and the [hosting decision](0017-cloud-run-worker-pool.md) owns deployment choices and the unresolved coordinator handoff.

Shared workers run MyStacks application code and can serve different users across separate runs. The pool may span multiple hosts. A run does not require a permanent machine for its user or a new infrastructure job for every task. **Pooled multi-tenancy** describes this shared runtime: common infrastructure serves many accounts, while trusted application authorization isolates each account. [AWS pooled isolation](https://docs.aws.amazon.com/whitepapers/latest/saas-tenant-isolation-strategies/pool-isolation.html)

Normal chat initially runs directly in the backend after inbound verification, storage, and transport acknowledgement. Each linked channel has one logical ordered event stream and one foreground main-agent turn at a time. A turn can contain several model/tool rounds. Substantial work uses explicitly delegated background subagents so the foreground can finish and handle new questions.

The [Apple messaging decision](0021-apple-messages-with-bird.md) selects **Bird as the MSP for MyStacks' Apple Messages for Business account**, with iMessage as the product shorthand. Bird carries messages; MyStacks retains runtime, memory, and scheduling ownership. iMessage is the priority channel for chat, one-off analysis/background work, user-created schedules, and proactive reports. WhatsApp supports user-initiated chat and one-off requested analysis/background work; WhatsApp schedules, proactive reports, and template messaging are deferred. A WhatsApp scheduling request is explained and directed to linked iMessage without creating, controlling, or retargeting iMessage work. Photon is a backup integration plan, without automatic failover or assumed same-number/thread migration. Native Bird API/webhook product/version/configuration, Apple account approval/experience review, and permitted financial notification scope remain validation items.

The [conversation ownership decision](0022-human-support-conversation-ownership.md) selects Bird Conversations as the Apple staff UI. The backend enforces native conversation ownership: human takeover pauses automated replies and reports until explicit staff handback, and a new inbound message does not resume AI. Requested analyses and user-created schedules continue and save results. Proactive starts are skipped while automated delivery is unavailable; an already-running finding waits for handback and is considered only if still useful and eligible. The main agent handles pending results with correct timestamps, current evidence, and delivery checks. Exact native ownership integration and WhatsApp transport/staff integration remain open.

Workers save background results in PostgreSQL before completing their BullMQ jobs. Native BullMQ `QueueEvents` normally notifies the coordinator. Saved completions retain pending/handled state; startup and periodic checks recover pending work through the same ordered channel handler with current authorization, cancellation, and delivery checks. Empty checks make no model calls, and recovery reuses saved research. A completion becomes a **new main-agent turn** when its channel is available. The main agent can retrieve details, investigate further, combine results, or delegate more top-level work and owns every agent-authored user reply. Requested work returns to its originating channel; proactive work reuses one investigation for eligible linked iMessage while the account's proactive insights setting is enabled, by default subject to applicable channel permissions. WhatsApp linking does not enable proactive work. Actual background jobs have durable status and result records; the main agent judges the overall answer from channel context and those records. The [channel-turn decision](0009-channel-turns-and-background-subagents.md) owns these boundaries, open completion-handling mechanics, and the five-outstanding delegation limit. Scheduler-started runs are outside that quota; the [scheduling decision](0004-durable-scheduling-and-queued-execution.md) owns saved-schedule limits, independent occurrences, and retry policy.

The backend promptly acknowledges recorded cancellation requests, stops waiting work, and requests running workers to stop through native SDK controls where available. It suppresses unsent results, including late completions, and confirms execution stopped only when known. In-flight provider requests may finish and incur cost, and submitted messages may not be recallable. Delivery uses provider-supported idempotency, deduplication, or status checks where available; an unresolved timeout is recorded as uncertain without blind automatic resend. Occasional missing automatic reports are accepted, while saved results remain available on request. Delivery failure never reruns completed analysis. The [scheduling decision](0004-durable-scheduling-and-queued-execution.md) owns these lifecycle and delivery trade-offs, and the [task design](../design/tasks.md) owns their flows.

Conversation history, context, memory, task definitions, progress, and useful analysis data must remain user-scoped in durable storage outside worker processes. Workers bind Mastra resource and thread identifiers from trusted backend context, load authorized state, and save required outcomes. Account-shared personal memory uses native Mastra structured working memory under the [shared-memory decision](0008-channel-scoped-work-and-shared-memory.md); native [Observational Memory compacts each channel's context](0010-native-channel-context-compaction.md). Main-agent turns control profile writes, including [profile-only forgetting](0011-profile-only-forgetting.md), under the accepted [last-successful-save rule](0012-last-save-wins-profile-updates.md). One [PostgreSQL database on a dedicated TimescaleDB-enabled Tiger Cloud service](0013-shared-postgresql-storage.md) holds separate ordinary application-owned and Mastra-owned tables, including small structured results and file metadata/references. The [analysis retention decision](0023-analysis-data-retention-and-object-storage.md) selects private Google Cloud Storage for retained datasets and workspace files. Retain useful provider inputs actually used, reusable intermediate calculations, final results, and supporting evidence conservatively, subject to provider data rights; automatic pruning is deferred. Storage follows purpose rather than mandatory size thresholds. MyStacks owns exact schemas, authorized transfers, task persistence, and recovery behavior.

The initial runtime and deployed capabilities are common across users; preferences and remembered context can vary by user. A **skill** supplies instructions, while a **tool** supplies executable capability. Relevant capabilities should compose through the common loop without a separate hard-coded intent for every workflow.

Trusted, predefined operations and web research tools may execute in the shared backend. Model-directed shell commands, file operations, and Python/JavaScript execute in E2B under the [sandbox boundary](0003-sandboxed-code-execution.md). Each foreground invocation or background job attempt lazily creates one sandbox if needed and reuses it across successive calls; the shared Mastra process retains the agent loop. Durable records and saved outputs provide continuity beyond that workspace. A retry starts fresh, and a main-agent continuation reads saved child results in its own run.

Before destroying E2B, save useful retained files with account/channel/run ownership, type, saved/retrieval/source-as-of times, provider/connection, size, and storage reference metadata; unknown source time remains explicit. A later authorized run may restore chosen files into a fresh sandbox. Backend-controlled native SDK access and run-scoped transfers must not grant agents or sandboxes broad cloud credentials or unrestricted bucket access. Retention supports follow-ups without promising exact process replay, reasoning checkpoints, persistence of every scratch file, or fresh evidence for current claims. It does not create a Phase 1 indexer or continuous portfolio-history archive.

The [credential boundary](0002-backend-owned-financial-credentials.md) keeps raw provider secrets outside sandbox environments, files, and prompts. **Credential brokering** uses native egress-proxy injection outside the VM for supported authentication and a user-bound backend read bridge for application signing or proxy-incompatible authentication. The backend chooses the user, destination, read scope, and object authority. E2B receives authorized current-user financial data under the accepted exposure trade-off and uses default-deny egress with backend-controlled required-provider access; backend tools supply general web research. The [capability decision](0006-composable-agent-capabilities.md) owns **programmatic tool calling** through scripts and broad provider SDK/API access. Skills can supply SDK/API guidance, but backend/provider permissions enforce authority. Ongoing work uses [durable scheduling and queued execution](0004-durable-scheduling-and-queued-execution.md).

## 3. Rationale and alternatives

### 3.1 Shared workers with durable user state

The product needs continuity and user-specific work, rather than one always-running process per user. Shared capacity lets idle users retain their work without retaining an idle runtime. External state also lets another worker continue a later run, while MyStacks remains responsible for storage, authorization, and recovery behavior.

The **existing agentic runtime** approach represented by `mystacks-be` and `hs-llm-service` is the simplicity reference for direct backend chat. MyStacks remains responsible for the required memory, tasks, monitoring, and recovery behavior.

### 3.2 A persistent runtime for every user

A dedicated environment can keep a user's files, local processes, and timers together. It is a viable choice when persistent environment behavior justifies its idle resources, fleet lifecycle, upgrades, and state operations. Current requirements do not require that ownership model or a separate Linux kernel per user.

A future persistent environment remains possible, but integrating its state, lifecycle, and authority would require design work. It is not supplied by the shared runtime automatically.

### 3.3 Adopting a complete agent system

A complete existing agent system may save work on memory, ongoing tasks, and recovery. Building only a custom loop, even inside an isolated environment, leaves those features to MyStacks. Reuse must be evaluated against the required product behavior and trust boundary.

For example, OpenClaw's [security trust model](https://docs.openclaw.ai/gateway/security/trust-model) treats one Gateway as one operator trust domain; shared Gateway authentication does not provide isolation between unrelated customer accounts. Adopting its features would still require a compatible deployment and authorization design.

## 4. Consequences and open decisions

- **Application ownership:** MyStacks integrates Mastra's context, memory, skills, and tool facilities while retaining responsibility for task records, recovery policy, financial behavior, and delivery.
- **User isolation:** every protected state or account operation must use authenticated server context and enforce user/object permissions. Shared execution requires that application boundary even when generated code runs elsewhere.
- **State consistency:** each channel serializes foreground turns. Native partial profile merges preserve distinct fields; the last successful save wins for the same field, including an older turn overwriting a correction or deletion. Background subagents read the profile without changing it.
- **Direct-chat limit:** one active backend coordinator serves concurrent channels with in-process ordering and one foreground turn per channel. The selected Cloud Run API service keeps CPU available after transport acknowledgement. Stop-and-start deployments accept downtime; process interruption may leave an acknowledged turn without a reply, and saved messages do not resume inference. How Cloud Run replacement and possible overlap preserve one active coordinator remains open; an instance limit alone is not an exclusive-ownership guarantee. The [channel-turn decision](0009-channel-turns-and-background-subagents.md) owns the interruption trade-off.
- **Native job restart:** PostgreSQL and Valkey retain state independently of application processes. BullMQ shutdown, reconnection, and stalled-job recovery keep waiting work queued and restart eligible interrupted requested jobs within the shared two-total-attempt ceiling. Completed results are reused; cancelled/revoked work never restarts, and failed/interrupted proactive work waits for the next check. This needs neither a deployment-specific state machine nor a startup script recreating all pending jobs, an empty queue, or reasoning checkpoints. The [scheduling decision](0004-durable-scheduling-and-queued-execution.md#27-whole-job-recovery-and-shared-attempt-allowance) owns the policy; exact native attempt accounting remains open.
- **Capacity:** the worker pool starts with one or two running instances and manual instance-count changes, separately from application job concurrency. Warm capacity avoids provisioning a worker per run; queue backlog, startup, worker replacement, and tool or model latency still affect response time. The worker-pool decision owns the operating trade-offs and interruption limit.
- **Open details:** pinned Mastra/BullMQ packages and adapter APIs, reuse of existing code, Cloud Run project/region/resource configuration and single-coordinator handoff, Tiger Cloud plan/region/size/backups and cross-cloud connectivity, Valkey networking/authentication and provisioning, schemas, provider authentication compatibility with native egress-proxy injection, trusted run-to-read-bridge authorization, required-provider egress configuration, pending-completion representation, sweep interval, handled boundary, crash behavior and deduplication, native attempt accounting, definitive send-failure retries, SDK cancellation integration, profile budgets, compaction thresholds and models, retention for other record types, GCS configuration and run-scoped transfers, provider data rights, and exact execution limits remain undecided. Useful analysis data is retained conservatively and automatic pruning is deferred. Completion recovery does not guarantee exactly-once main-agent turns or replies. The [worker-pool decision](0017-cloud-run-worker-pool.md) owns capacity tuning from measurements.
- **Product limits:** shared execution does not strengthen monitoring guarantees or expand financial authority.
