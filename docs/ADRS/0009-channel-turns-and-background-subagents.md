# Channel turns and background subagents

## 1. Status and scope

**Status: ACCEPTED Phase 1 execution direction.** One active ordinary API/backend process coordinates chat across all users. Different channels execute concurrently, with one foreground main-agent turn at a time per channel. Normal chat runs directly in that process; subagent results trigger fresh main-agent turns, and the main agent owns every agent-authored user reply. API/backend deployments use simple stop-and-start replacement, accepting brief interruptions. The API/coordinator hosting baseline is a Cloud Run Service with instance-based billing for CPU after acknowledgement; background consumers use the separate [Cloud Run worker pool](0017-cloud-run-worker-pool.md). Exclusive coordinator ownership and handoff during Cloud Run replacement remain unresolved. Overall architecture, framework integration, and exact configuration remain tentative.

The [runtime design](../design/runtime.md) owns detailed execution boundaries, examples, and verification. The [task design](../design/tasks.md) owns saved user tasks, recurring runs, and proactive policies. The [channel scope and shared memory decision](0008-channel-scoped-work-and-shared-memory.md) owns account-wide personal context and channel-scoped conversations and work. This record owns the runtime decisions and their rationale.

The [Apple messaging decision](0021-apple-messages-with-bird.md) selects Bird as the Apple Messages for Business MSP, with Photon as a backup integration plan. iMessage is the priority channel and supports chat, one-off analysis/background work, schedules, and proactive reports. WhatsApp supports user-initiated chat and one-off requested analysis/background work; its schedules, proactive reports, and template messaging are deferred. These capability limits do not change current-channel job/task/result access. The [conversation ownership decision](0022-human-support-conversation-ownership.md) selects Bird Conversations as the Apple staff UI and backend enforcement of native ownership and explicit staff handback. Exact native integration, support staffing/hours/SLAs, and WhatsApp transport/staff integration remain open.

## 2. Decision

### 2.1 Direct normal chat with an explicit interruption limit

The backend verifies and binds the sender, deduplicates the inbound event, stores the message, and promptly acknowledges transport receipt. When AI owns the conversation, normal chat executes directly in the single active API/backend chat coordinator without a durable BullMQ chat queue. The backend enforces native conversation ownership before automated replies; a new inbound message cannot resume AI after human takeover. User messages and background completion events enter the same channel-turn handler, which remains callable independently of the transport. The coordinator is an ordinary backend process, not a separate agent service or a runtime assigned to each user.

Deployments stop the active API/backend process and start its replacement. Phase 1 accepts brief chat and traffic interruptions during that replacement. Process or deployment interruption can leave an acknowledged chat message without a reply; stored messages alone do not resume inference. Custom traffic switching, zero-downtime deployment, and distributed chat coordination are deferred until observed need or user impact justifies them.

Use a **GCP Cloud Run Service with instance-based billing** so CPU remains available after the transport response, under [Cloud Run's billing settings](https://docs.cloud.google.com/run/docs/configuring/billing-settings). This hosting choice does not settle exclusive ownership: how to preserve one active coordinator and in-process channel ordering during replacement or possible instance overlap remains open. A [Cloud Run instance limit](https://docs.cloud.google.com/run/docs/configuring/max-instances-limits) alone does not guarantee exclusive ownership. The [scaffolding delivery](../design/scaffolding.md) selects initial service settings; lifetime handling and exclusive-coordinator verification remain open. Identity, authorization, deduplication, and channel ordering remain required.

### 2.2 One foreground turn per channel

Each linked channel has one logical event stream or inbox and one active foreground main-agent turn. Different channels may have active turns concurrently in the shared coordinator. Initial ordering may use in-process coordination. A turn consumes pending user messages, internal completion events, or both, with permitted channel context. It can include several model/tool rounds and end with a reply, delegation acknowledgement, or no unnecessary message. A model round can request several tools; their results feed a later round. A turn is neither one model invocation nor necessarily one user message.

Quick work runs inline. For substantial work, the main agent starts background subagents, receives accepted job IDs, acknowledges as appropriate, and ends the turn. The main agent must not occupy the foreground waiting for background results. Messages and completion events arriving during an active turn remain pending for a later turn; Phase 1 does not require mid-turn injection or steering.

Steering an active background run is deferred. A new chat message does not automatically redirect or cancel it; supported status and cancellation tools remain available.

This is logical ordering, not a separate physical queue, process, or VM for each channel. Other channels retain their separate context and work under the account/channel boundary.

### 2.3 Native completion events and main-owned replies

Subagents return internal findings, data, evidence, or artifact references rather than directly sending user messages. The worker saves the completed job state, result, and pending-completion state in PostgreSQL before completing its BullMQ job. **The chat coordinator subscribes to native BullMQ `QueueEvents` completion notifications from all workers.** On notification, it resolves trusted stored work bindings. For user-requested work, these include account, originating channel, original-request, and job bindings; the coordinator queues a logical completion event for that channel through the same channel-turn handler used by inbound chat. Notification supplies neither authorization nor channel ordering. BullMQ uses the selected [dedicated Memorystore for Valkey queue store](0020-managed-valkey-queue-storage.md) through its Redis-compatible backend; pinned versions and integration validation remain open.

Proactive completion uses the same subscriber and coordinator to handle one saved account-level investigation under the [task design's delivery policy](../design/tasks.md). Its qualifying result can serve eligible verified linked iMessage while the proactive insights setting remains enabled. WhatsApp proactive delivery is deferred, and linking WhatsApp does not enable it. Exact completion records and dispatch mechanics remain open; the main agent owns every agent-authored reply.

If the channel is idle and AI-owned, the event starts a new main-agent turn. Otherwise it remains pending without interrupting a foreground turn or human conversation. Requested analyses and user-created schedules continue and save results during human takeover; automated reports wait for explicit staff handback. The main agent then handles pending results with correct timestamps, current evidence, and delivery/authorization checks. Proactive starts are skipped while automated delivery is unavailable, and already-running proactive findings wait for handback and are considered only if still useful and eligible. Fresh input includes the original request where applicable, a compact result summary, result references, and current permitted channel context; this is not a resumed model call. The continuation reads saved outputs in its own execution run rather than inheriting a child's live E2B sandbox, files, or processes. If it needs shell or code, it lazily creates its own sandbox. Completion does not create a user instruction or expand permission.

Within the original authorized purpose, the main agent can read result details when needed, check financial tools, run E2B calculations, combine available children, start further top-level work, reply, or end quietly while another child continues. Event notification and selective reading of saved results work together; no model polling, busy-waiting, or foreground waiting for completion is required. The main agent's actual reply enters normal channel history for follow-ups. Scheduled and proactive agent output follows the same reply boundary, subject to its separate eligibility and silence policies.

**Event notification** signals that work is ready; the coordinator reads authoritative job state and results from PostgreSQL, following the [event-notification pattern](https://martinfowler.com/articles/201701-event-driven.html#EventNotification). [BullMQ `QueueEvents`](https://docs.bullmq.io/guide/events/) uses the Redis Streams API with bounded, automatically trimmed retention. Keep **pending/handled state for saved completions**. On startup and periodically, the coordinator checks pending saved completions and sends them through the same ordered channel handler with current authorization, cancellation, channel, and delivery checks. An empty check makes no model call; recovery reuses saved research rather than re-enqueuing completed analysis. Exact record schemas, sweep interval, handled boundary, crash behavior, and deduplication mechanics remain open. This policy does not guarantee exactly-once main-agent turns or replies.

For outbound delivery, use provider-supported idempotency, deduplication, or delivery-status checks where available. If submission remains ambiguous after a timeout, record the uncertainty and do not blindly resend automatically. Keep the saved result available when the user asks. Notification or delivery failure never reruns completed analysis. Phase 1 accepts that a report may occasionally not arrive automatically; retry details for definitive send failures remain open.

### 2.4 One-level delegation and bounded outstanding work

The configurable initial maximum is five outstanding main-agent-spawned subagent runs per chat, counting queued and running runs. Terminal runs do not count. At capacity, the main agent reports the limit rather than accepting another delegation, whether the user requested delegation or the main agent chose it. A new subagent spawned by a main-agent continuation uses the same quota.

Scheduler-started recurring and proactive runs are excluded from this delegation quota. Each user-created scheduled occurrence starts one independent background agent run; distinct occurrences of the same saved task can run in parallel without checking whether the previous occurrence is queued or running. The [task design](../design/tasks.md) owns saved-schedule limits, due-occurrence admission, scheduled retries, and the separate proactive policy. The [worker-pool decision](0017-cloud-run-worker-pool.md) owns configurable execution limits and basic capacity evidence; exact limit values remain provisional.

Only main-agent turns can delegate. The subagent tool subset and backend authorization prevent nested subagents. A later main-agent turn may start another top-level run without creating another delegation level.

Background research, subagent, and proactive runs receive useful authorized provider APIs, backend web research, E2B shell/file/Python/JavaScript tools, and shared personal-memory read access. The Mastra loop stays in the shared worker; each attempt lazily creates one sandbox if needed and reuses it across calls. The [credential decision](0002-backend-owned-financial-credentials.md) keeps raw provider secrets outside sandbox environments, files, and prompts through **credential brokering**: native egress-proxy injection outside the VM for supported authentication, or a user-bound backend read bridge for application signing or proxy-incompatible authentication. Runs receive authorized current-user financial data under the accepted exposure trade-off. E2B uses default-deny egress with backend-controlled required-provider access. Runs cannot change settings, connections, personal memory, or saved user tasks, or directly send messages. Backend/provider checks enforce these capability limits without arbitrarily reducing investigation ability.

Under the [analysis retention decision](0023-analysis-data-retention-and-object-storage.md), save useful provider inputs actually used, reusable intermediate calculations, final results, and supporting evidence before sandbox destruction. Private Google Cloud Storage holds retained datasets/workspace files; PostgreSQL holds records, small structured results, metadata, and file references. Keep account/channel/run ownership, type, saved/retrieval/source-as-of times, provider/connection, size, and storage reference metadata, allowing unknown source time. Backend-controlled native SDK access and run-scoped transfers may restore chosen authorized files into a later fresh sandbox without broad cloud credentials or unrestricted bucket access. Be conservative about discarding useful data; automatic pruning is deferred, subject to provider data rights. Saved data does not make evidence current, imply exact replay or reasoning checkpoints, or create a continuous portfolio-history archive.

### 2.5 Job records without a parent-request lifecycle

Application-owned tables in the [shared PostgreSQL database](0013-shared-postgresql-storage.md) record real job states, results, and stable original-request correlation needed for routing, status, cancellation, and admission. Mastra owns separate tables for its messages and memory; backend authorization governs both. BullMQ owns timing, dispatch, claims, and configured job retries using the dedicated Valkey queue store; Mastra executes the claimed run. Saved recurring tasks retain their own lifecycle, distinct from execution runs.

The main agent reasons from context and actual child statuses to decide whether the user's request is answered. Phase 1 defines no overall-request finished flag, mandatory dependency graph, workflow checkpoint, or parent cancellation hierarchy. A status claim must use actual job-status tools. Cancellation requested does not mean execution has stopped; current permission, channel, cancellation, and delivery checks still apply.

The [scheduling decision](0004-durable-scheduling-and-queued-execution.md) owns background recovery. Stop old application processes and start new ones while independently hosted PostgreSQL and Valkey retain their state. Waiting work stays queued; use native BullMQ shutdown, reconnection, and stalled-job recovery rather than recreating pending jobs at startup or requiring an empty queue. Requested background work has **at most two total whole-job attempts**, shared by temporary-failure retries and interrupted or stalled-job recovery. An interrupted unfinished run restarts from the beginning only while still active and authorized and with an attempt remaining, using a fresh E2B sandbox if needed. Reuse saved completed results through completion recovery. Proactive failures and interruptions wait for the next eligible check, and cancelled or revoked work does not restart. Exact native attempt accounting remains open. Phase 1 does not add a deployment-specific state machine or resume in-agent, model, tool, or live-workspace checkpoints. Ordinary non-interruption one-off error retry classification remains open within the two-attempt ceiling.

### 2.6 Cancellation and truthful status

The backend records a cancellation request, cancels waiting work, and requests that a running worker stop through native SDK mechanisms where available. Acknowledge the request promptly; confirm stopped execution or a terminal cancelled state only when waiting work has stopped or the running worker has confirmed it stopped. In-flight provider requests may still finish and incur cost. Suppress unsent result delivery after the request, including late completions, while preserving channel-scoped controls and unrelated work. A message already submitted to its provider may not be recallable. Status remains queryable; a second routine completion notification is not mandatory. Exact statuses, schemas, and native abort mechanisms remain implementation choices.

## 3. Rationale and alternatives

**Direct chat keeps the initial execution path small.** A durable chat queue, replay engine, outbox, or checkpoint system would strengthen interruption recovery but adds mechanisms beyond the accepted Phase 1 guarantee. The accepted reply-loss limit keeps that trade-off explicit. Demonstrated reliability, capacity, rate-limit, or other concrete requirements can justify revisiting dispatch while preserving the agent logic and required correctness checks.

**One coordinator keeps initial ordering and deployment simple.** Concurrent channels share one backend process without distributed coordination or custom traffic switching. The trade-off is that process capacity bounds foreground work and stop-and-start deployments briefly interrupt chat and traffic. Cloud Run Service supplies the selected hosting baseline, and instance-based billing accepts allocated CPU cost for work after HTTP acknowledgement. It does not resolve coordinator ownership during replacement; that fit must be settled before claiming the topology works on Cloud Run. Observed load or user impact, rather than a hypothetical scaling requirement, justifies revisiting the accepted topology and deployment policy.

**Ordered turns keep one conversation coherent.** Serializing foreground turns avoids concurrent inference using incompatible channel context. Background subagents free that foreground for new questions, while pending events preserve turn boundaries without requiring mid-turn steering.

**Main-owned replies preserve the full request.** Child findings may need fresh evidence, calculations, or another child's result before they answer the user. Posting every child report directly would expose incomplete work and split response authority. A fresh main-agent turn can assess current context and permissions and produce one useful chat reply when appropriate.

**Native queue events reuse the background transport.** `QueueEvents` brings completions from all workers to the coordinator without an application HTTP callback endpoint, authentication scheme, and retry protocol. Native events give prompt notice while startup and periodic pending-completion checks recover missed wakeups from PostgreSQL. The trade-off is bounded stream retention plus small database checks and pending/handled state. Empty checks need no model call, and selective result reads preserve completed research without model polling or exactly-once claims.

**Uncertain delivery favors avoiding duplicate reports.** Provider-supported deduplication and status checks can resolve a send where available. When submission remains uncertain, recording it and retaining the result avoids a blind resend that could duplicate the report. The accepted cost is that some reports do not arrive automatically; delivery recovery never repeats analysis.

**Native job recovery keeps application restarts small.** Independent state stores preserve waiting work while BullMQ handles shutdown, reconnection, and stalled jobs. Whole-job restart accepts repeated work within the shared two-attempt ceiling instead of maintaining reasoning checkpoints or a deployment recovery system. The queue store's accepted downtime and recent-write-loss limits remain those of the [Valkey decision](0020-managed-valkey-queue-storage.md).

**Cancellation separates the user's control from provider timing.** Recording the request suppresses unsent output promptly while native stop requests address execution where supported. Acknowledging the request does not falsely claim that in-flight provider work stopped, avoided charges, or recalled an already-submitted message.

**Actual jobs provide enough execution state.** Context and job-status tools support agent-led completion decisions without a second parent workflow lifecycle. The five-run limit bounds main-agent delegation while scheduler-started occurrences follow their own admission policy. One-level delegation keeps admission and tool authority enforceable at the main-agent boundary.

## 4. Consequences and open implementation choices

- **Shared infrastructure:** retain the shared Mastra regular `Agent` direction, fresh trusted per-run context, separate run-owned E2B workspaces, and credential brokering with backend-bound user and read authority. API/chat and background workers use the same backend codebase with distinct entrypoints and deployments; logical channel ordering remains independent of worker-pool instance count. The [scaffolding delivery](../design/scaffolding.md) selects the initial runtime/model and staging settings.
- **Continuation:** the single chat coordinator subscribes to native `QueueEvents` and recovers pending saved completions on startup and periodically through the same trusted ordered channel handler. Subscriber lifecycle integration, record schemas, sweep interval, handled boundary, crash behavior, and deduplication remain open; this record does not promise durable chat replay or exactly-once turns or replies.
- **Durability:** background results and required files persist outside disposable workers and sandboxes. PostgreSQL uses the [dedicated TimescaleDB-enabled Tiger Cloud service](0013-shared-postgresql-storage.md); the scaffold selects its initial target plan, region, and size, while creation/URL are deferred. Backup/recovery and cross-cloud connectivity require verification; detailed product schemas, native attempt accounting, and remaining one-off failure retry classification remain open. The [analysis retention decision](0023-analysis-data-retention-and-object-storage.md) selects private GCS for useful retained files and PostgreSQL for records, small structured results, metadata, and references. Retain useful analysis data conservatively, subject to provider data rights; automatic pruning is deferred. Native SDK access, run-scoped file transfers, and exact GCS configuration remain open. Valkey hosting and its accepted availability and persistence limits follow the [queue-store decision](0020-managed-valkey-queue-storage.md). Definitive send-failure retry details remain open within the selected uncertain-delivery policy.
- **Authority:** subagent output is untrusted evidence within its assigned purpose. Backend capability checks, current permissions, channel validity, native AI conversation ownership, recorded cancellation requests, and delivery controls apply to normal and recovered completions. Exact cancellation statuses and native abort mechanisms remain open.
- **Capacity:** five outstanding main-agent-spawned queued or running subagents is the initial configurable per-chat limit. Scheduler-started runs are excluded. Configurable execution limits and per-run duration, model usage, and outcome evidence follow the worker-pool decision; exact values remain provisional, and per-user dollar budgets are deferred.
- **Hosting:** background consumers use the selected Cloud Run worker pool with manual instance scaling and native job recovery. Its shutdown warning cannot guarantee completion of an active long-running job. The API/coordinator uses Cloud Run Service with instance-based billing and accepts stop/start downtime. The scaffold selects the initial GCP project, region, and resource settings. Production capacity and verified exclusive coordinator ownership/handoff during replacement or possible overlap remain open; an instance limit alone does not settle that constraint.
