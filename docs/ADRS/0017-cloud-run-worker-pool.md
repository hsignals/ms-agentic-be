# Cloud Run worker pool for background execution

## 1. Status and scope

**Status: ACCEPTED initial hosting, deployment separation, manual worker scaling, and measurement-first capacity policy.** MyStacks uses a Google Cloud Run Service for API/chat with instance-based billing and a separate Cloud Run worker pool for background queue consumers. The single active coordinator's exclusive ownership and handoff during Cloud Run replacement remain unresolved. The overall architecture remains tentative, and this decision does not claim an implemented or provisioned service.

The [architecture](../architecture.md) owns execution responsibilities. The [channel-turn decision](0009-channel-turns-and-background-subagents.md) owns direct chat, coordinator ownership, completion recovery, cancellation, and main-agent continuations; the [scheduling decision](0004-durable-scheduling-and-queued-execution.md) owns task admission and retry policies. BullMQ uses a dedicated GCP Memorystore for Valkey instance under the [queue-store decision](0020-managed-valkey-queue-storage.md); pinned versions and integration validation remain open. The [shared PostgreSQL decision](0013-shared-postgresql-storage.md) selects a dedicated TimescaleDB-enabled Tiger Cloud service for separate ordinary application and Mastra tables. E2B provides run-owned shell, file, and code execution workspaces while the shared API/worker processes run Mastra's agent loop. The [scaffolding delivery](../design/scaffolding.md) selects the initial staging plan, region, and size; backup configuration, cross-cloud connectivity, and provisioning validation remain open.

## 2. Decision

### 2.1 Separate background deployment in one backend codebase

Use a **Cloud Run worker pool** for main-agent-delegated subagents, requested scheduled occurrences, and proactive investigations. The worker pool runs continuous background consumers without an HTTP ingress endpoint; it does not host incoming API/chat traffic. Google documents worker pools as [continuous background resources without a load-balanced endpoint](https://docs.cloud.google.com/run/docs/deploy-worker-pools).

Keep the same backend codebase with distinct **API/chat and worker entrypoints**. The deployments may reuse one container image with different entrypoints; this decision does not require separate repositories or a microservices rewrite. Both paths use the same protected application operations and trusted account/channel bindings.

Each foreground invocation or background job attempt lazily creates one E2B sandbox if shell or code is needed and reuses it across calls. A sandbox is separate from a Cloud Run instance: a worker can serve multiple isolated runs, and its lifetime does not preserve their live workspaces. Required results and files persist outside E2B before sandbox destruction. The [sandbox decision](0003-sandboxed-code-execution.md) owns the workspace boundary; the [credential decision](0002-backend-owned-financial-credentials.md) keeps raw provider secrets outside sandbox environments, files, and prompts through **credential brokering**. Native egress-proxy injection outside the VM supports compatible provider authentication; application signing or proxy-incompatible authentication uses a user-bound backend read bridge. Authorized current-user financial data remains available in E2B under the accepted exposure trade-off. Required-provider egress is backend-controlled and default-deny; general web research uses backend tools.

Normal chat continues directly in the backend after verification, persistence, and transport acknowledgement, without a durable chat queue. Initially, **one active ordinary API/backend process** handles all users and channels concurrently, with one foreground main-agent turn per channel. User messages and background completions enter the same channel handler under the [channel-turn decision](0009-channel-turns-and-background-subagents.md).

Use a **Cloud Run Service with instance-based billing** for API/chat so CPU is available after transport acknowledgement, under [Cloud Run's billing settings](https://docs.cloud.google.com/run/docs/configuring/billing-settings). The chat coordinator uses simple stop/start deployment and accepts brief traffic interruptions. How Cloud Run replacement and possible instance overlap preserve one active coordinator and in-process channel ordering remains open; a [service instance limit](https://docs.cloud.google.com/run/docs/configuring/max-instances-limits) alone does not guarantee exclusive ownership. No distributed ownership mechanism or custom zero-downtime deployment is selected. This coordinator constraint does not limit the separate worker pool to one instance.

Use `mystacks-be` as a **deployment reference** for GitHub Actions, Workload Identity Federation, Artifact Registry immutable images, migrations, health checks, separate entrypoints and identities, and Secret Manager. This is an independent project with its own deployments, PostgreSQL, queue store, identities, secrets, configuration, pipeline, and resources. No shared `mystacks-be` or `hs-core` resource or dependency is selected. The [scaffolding delivery](../design/scaffolding.md) owns the initial staging project, regions, and resources; exact provisioning and permissions remain implementation work.

### 2.2 Small running capacity with manual scaling

Start with **one or two running container instances**; the [initial staging configuration](../design/scaffolding.md#41-initial-configuration) selects one. Adjust that count manually as demand requires. Cloud Run supports [changing the instance count without redeployment and bills requested instances even when idle](https://docs.cloud.google.com/run/docs/configuring/workerpools/manual-scaling). Worker instances receive CPU throughout their running lifetime under the [container contract](https://docs.cloud.google.com/run/docs/container-contract).

The **pool instance count** controls running containers. The **worker job concurrency** controls how many queued jobs an application worker processes concurrently; BullMQ documents [local concurrency and multiple workers](https://docs.bullmq.io/guide/workers/concurrency) as separate controls. Neither value is the five-outstanding-subagents-per-chat admission limit. Select job concurrency, CPU, and memory from observed run demand and model/provider quotas; this decision establishes no user-capacity claim.

Manual scaling is the initial operating choice. Google also documents [external-metric autoscaling through a separately deployed autoscaler](https://docs.cloud.google.com/run/docs/configuring/workerpools/crema-autoscaling); adopting that mechanism requires a concrete capacity need and its own configuration.

Use **configurable execution limits** to bound run length and resource use, reusing native SDK controls where they meet the requirement. The backend records each run's duration, model usage, and actual outcome. Operators observe queue delay and resource use alongside those records to adjust worker instance count and job concurrency manually. Exact limits remain provisional until representative jobs provide evidence. A per-user spending budget system is deferred until actual usage justifies it.

### 2.3 Durable results and main-agent continuation

Workers claim background jobs, execute Mastra runs, and save actual status and internal results in application-owned PostgreSQL records. The coordinator resolves completion through trusted stored bindings. User-requested work returns to its originating channel; proactive completion serves the selected eligible destinations from one saved investigation under the task delivery policy. An idle destination channel starts a new main-agent turn; a busy channel retains the completion for a later turn. This is a separate execution run that reads saved child outputs and creates its own sandbox only if needed, without inheriting child processes or interpreter state. The main agent owns every agent-authored user reply.

Workers persist results and pending-completion state before completing BullMQ jobs. The single active API/backend coordinator subscribes to **native BullMQ `QueueEvents` completion notifications** and resolves the saved result through trusted bindings. PostgreSQL remains authoritative for job state and results. On startup and periodically, the coordinator checks pending saved completions and routes them through the same ordered channel handler with current authorization, cancellation, and delivery checks. Empty checks make no model calls, and recovery reuses completed research. The [channel-turn decision](0009-channel-turns-and-background-subagents.md) owns pending/handled completion state and uncertain-send policy. Exact listener integration, record schemas, sweep interval, handled boundary, crash behavior, and deduplication remain open; this does not establish exactly-once turns or replies.

### 2.4 Instance lifecycle and interrupted jobs

A running instance avoids provisioning a container for every job, but startup, replacement, queue backlog, sandbox startup, and provider latency can still delay execution. A Cloud Run instance lifecycle is distinct from a BullMQ job lifecycle.

Cloud Run can interrupt a processing worker and sends `SIGTERM` **10 seconds before `SIGKILL`**, as specified in its [worker-pool container contract](https://docs.cloud.google.com/run/docs/container-contract). That interval cannot guarantee completion of an expected 5–10-minute run during deployment or replacement.

Stop old application processes and start new ones while independently hosted PostgreSQL and Valkey retain their state. Waiting jobs stay in BullMQ. Use its native [graceful shutdown](https://docs.bullmq.io/guide/workers/graceful-shutdown), [reconnection behavior](https://docs.bullmq.io/guide/going-to-production), and [stalled-job recovery](https://docs.bullmq.io/guide/jobs/stalled) within the [scheduling decision's](0004-durable-scheduling-and-queued-execution.md) recovery policy, without requiring an empty queue or recreating pending jobs at startup. The [Valkey decision](0020-managed-valkey-queue-storage.md) owns queue-store downtime and possible recent unflushed-write loss; application restart does not strengthen those limits.

Reuse a completed result through pending-completion recovery without rerunning successful work. Otherwise, when interrupted requested background work remains active and authorized, restart the whole job from the beginning with a fresh E2B sandbox if needed, within **at most two whole-job attempts in total**. That shared budget includes temporary-failure retries and interrupted or stalled-job recovery. Cancelled work and work whose authority has been revoked do not restart. A failed or interrupted proactive investigation waits for the next eligible check.

The design does not add a deployment-specific state machine or in-agent checkpoints, replay, or resumption. Exact native BullMQ attempt accounting and integration, cancellation statuses and abort mechanisms, and duplicate-result handling remain open within the accepted policy. Cancellation records the request, stops waiting work, requests a native stop for running work where supported, and suppresses unsent late results. In-flight provider requests may finish and incur cost; only confirmed stopped execution can be reported as terminal cancelled.

## 3. Rationale and trade-offs

Independent background capacity from the beginning keeps long-running queued work separate from API/chat capacity. Continuous consumers fit the queue-driven execution model while retaining the shared backend runtime and application boundaries. Manual scaling keeps the initial operating model small until observed load justifies more machinery.

**Cloud Run Service supports the selected API execution model.** Instance-based billing provides CPU after the transport response and accepts allocated CPU cost for that work. The service and worker pool share deployment conventions while retaining separate lifetimes and identities. Reusing `mystacks-be` conventions avoids inventing another deployment approach; independent resources preserve this project's ownership and configuration. Exclusive coordinator ownership during Cloud Run replacement still requires a decision before the hosting configuration can satisfy the one-active-process constraint.

**Independent state and native queue recovery keep deployment small.** Waiting jobs survive application stop/start, eligible interrupted work restarts within the shared attempt ceiling, and saved completions return through normal handling. This accepts interruption, possible repeated whole-job work, and the queue store's selected failure limits rather than adding deployment recovery machinery. The [channel-turn decision](0009-channel-turns-and-background-subagents.md) records the separate trade-offs for pending-completion recovery, cancellation, and uncertain outbound delivery.

**Measure representative work before fixing capacity limits.** Configurable bounds and run-level measurements make resource use visible while the workload is still being established. The policy accepts provisional limits and manual tuning in exchange for avoiding a per-user spending budget system before actual usage establishes its need. Native execution controls provide the initial bounds; measurement does not depend on a paid tracing service or select extra optimization machinery.

A combined API/chat and worker deployment would have fewer deployment settings, but would tie their instance capacity and process lifecycle together. The selected split accepts an extra entrypoint and deployment plus permissions, network connectivity, and shutdown operations. Running worker instances incur idle cost, and replacement still has startup delay. Worker code and configuration deployments create [new Cloud Run revisions](https://docs.cloud.google.com/run/docs/deploy-worker-pools); they do not guarantee that active application jobs finish uninterrupted.

## 4. Remaining decisions and acceptance evidence

- **Configuration:** apply the [selected staging baseline](../design/scaffolding.md) and settle worker job concurrency, identities and permissions, and connectivity to Valkey, Tiger Cloud PostgreSQL, E2B, required providers, and backend operations. The GCP application to Tiger Cloud's AWS/Azure hosting crosses a cloud boundary. Measure representative jobs before fixing execution limits. Valkey uses the selected single-node Memorystore baseline with private VPC connectivity and TLS; networking, authentication, provisioning, backup policy, pinned versions, and integration validation remain open. Tiger Cloud availability, backup settings, and cross-cloud connectivity require validation; so do native egress-proxy compatibility and provider limits, trusted run-to-read-bridge authorization, and required-provider egress configuration.
- **API/chat:** settle exact Cloud Run Service configuration, service lifetime handling, exclusive coordinator ownership and handoff during replacement or overlap, and integration of the selected `QueueEvents` listener and pending-completion handling. Preserve one active coordinator and in-process channel ordering; an instance limit alone does not meet that contract.
- **Recovery:** settle exact native BullMQ attempt accounting, completion record schemas, sweep interval, handled boundary, crash behavior and deduplication, cancellation statuses and native abort mechanisms, definitive send-failure retry details, and remaining one-off failure retry classification within the accepted whole-job restart, result-reuse, and proactive policies.
- **Capacity evidence:** exercise both entrypoints, queue claiming, independent instance-count and job-concurrency settings, retained results, and a completion returning to a new ordered main-agent turn. Verify scheduling, priorities, `QueueEvents`, retries, reconnection, and restarts against the chosen BullMQ and Valkey integration. Cover missed wakeups, startup and periodic recovery without empty-check model calls, current authorization and cancellation checks, uncertainty after a send timeout, and the shared two-attempt ceiling across failure and stalled/interrupted recovery. Record run duration, model usage, and outcome; use queue-delay and resource-use observations to tune capacity manually. Observe deployment/replacement interruption and exclusive coordinator ownership before claiming recovery or capacity guarantees. These checks are required evidence, not completed validation.
