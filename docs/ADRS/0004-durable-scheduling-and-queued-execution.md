# Durable scheduling and queued execution

## 1. Status and scope

**Status: ACCEPTED durable scheduling, shared background queue and relative priorities, native whole-job recovery, BullMQ with managed Valkey queue storage, native completion events with pending-completion recovery, backend record ownership, Phase 1 task and proactive-message behavior, and separate Cloud Run worker-pool hosting; TENTATIVE framework integration.** MyStacks stores ongoing task definitions and background run states and results in its backend database. Due and explicitly requested background work uses shared workers. The selected BullMQ and Valkey integration requires version, integration, and operational validation; the overall architecture remains tentative.

This decision supports daily digests, user-defined informational tasks, and proactive checks under the [requirements](../requirements.md). The [architecture](../architecture.md) owns detailed flows and state ownership; this record owns the scheduling trade-off.

The [Apple messaging decision](0021-apple-messages-with-bird.md) selects Bird as the MSP for MyStacks' Apple Messages for Business account. iMessage is the priority channel for chat, one-off requested analysis/background work, user-created schedules, and proactive reports. WhatsApp supports user-initiated chat and one-off requested analysis/background work; its schedules, proactive reports, and template messaging are deferred. Scheduling requests from WhatsApp receive an explanation and direction to linked iMessage, without creating, managing, or retargeting iMessage tasks. Photon is a backup integration plan, without automatic failover or an assumed same-number/thread migration.

## 2. Decision

### 2.1 Persistent definitions and new runs

The backend database retains ongoing work's **intent, current status, stable account, originating channel, and trigger**, plus background run records, statuses, internal results, and original-request correlation. Saved recurring tasks remain distinct from their execution runs. When a worker claims due work, it starts a new run with trusted context and the instructions that apply when it starts. The schedule and queue wait between runs; an LLM need not keep running or remember to wake itself.

Shared workers wait for queued work, claim ready jobs, and execute MyStacks application code. Each eligible user-created scheduled occurrence starts one background Mastra agent run with trusted account, resource, channel, and thread context. Agents can compose authorized provider reads, backend web research, and E2B shell, file, Python, and JavaScript execution. The agent loop stays in the shared worker. Each background attempt lazily creates one sandbox if needed and reuses it across calls; concurrent runs never share that live workspace. Every eligible proactive check also invokes a bounded agent investigation. Both paths operate within resource budgets. Channel scope does not require separate channel runtimes, queues, or deployments.

Workers persist internal findings, data, evidence, or artifact references and actual run state in PostgreSQL before completing the BullMQ job. **Native BullMQ [QueueEvents](https://docs.bullmq.io/guide/events/) supplies completion notifications.** The existing single active API/chat coordinator subscribes, resolves trusted routing from stored run records, and submits completion through the same channel handler used by inbound chat. Requested work uses its originating channel; proactive findings can serve only eligible linked iMessage while proactive insights are enabled. Each channel has one foreground main-agent turn: an idle AI-owned channel starts a new turn, and a busy or human-owned channel retains completion. Explicit staff handback permits the main agent to assess pending results under the ownership contract below. The main agent owns the user reply and can investigate further or combine children within the original authorized purpose. Completion grants no new instruction or permission. A separate overall-request lifecycle is not part of this design. The [channel-turn decision](0009-channel-turns-and-background-subagents.md) owns the completion-event trade-off, and the [runtime design](../design/runtime.md) owns channel-turn details.

**Saved completions retain pending/handled state in PostgreSQL.** QueueEvents remains the normal wakeup path. On startup and periodically, the coordinator checks for pending saved completions and submits them through that same ordered channel handler, applying current authorization, cancellation, and delivery checks. Empty checks make no model calls. Recovery reuses completed research; it does not re-enqueue completed analysis. Exact record schemas, check intervals, the handled boundary, crash behavior, and duplicate-handling mechanics remain open. This does not guarantee exactly-once main-agent turns or replies.

The configurable initial limit is **five queued or running subagents spawned by the main agent per chat**. Terminal jobs do not count. Scheduler-started requested occurrences and proactive investigations are excluded; a new subagent spawned by a main-agent continuation does count. When the delegation limit is reached, the assistant reports capacity instead of accepting a sixth. Only main-agent turns may delegate additional subagents, and subagents cannot start nested subagents or directly send user messages. Saved recurring tasks have a separate enabled-task quota under section 2.5.

Users can list, inspect, change, pause, resume, and cancel only the current channel's ongoing tasks. They can list independent jobs, check status, and request cancellation only in their originating channel; results stay there too. Backend handlers enforce account and channel ownership rather than trusting model-selected identifiers. Phase 1 chat cannot select another destination, transfer work, or retarget results. Account-wide personal memory and financial access do not expand task access; the [channel and memory decision](0008-channel-scoped-work-and-shared-memory.md) owns that boundary.

Task edits apply to future runs; active runs keep their original instructions unless explicitly cancelled. Before protected reads and delivery, the orchestration layer must still enforce current financial permissions, channel validity, applicable task pause/cancel state, native AI conversation ownership for sending, and delivery authority. Pausing stops future runs and holds automatic results not yet sending. Resuming continues at the next scheduled time without a missed-update backlog. Cancelling ends recurrence and requests cancellation of all queued and running occurrences of that task; past results remain available in the owning channel. The instruction snapshot is a logical requirement, not a selected persistence schema.

The backend records cancellation requests, cancels waiting work, and asks a running worker to stop through native SDK controls where available. It acknowledges the **cancellation request** promptly, but confirms execution stopped or records terminal cancellation only when waiting work has stopped or the running worker is known to have stopped. In-flight provider calls may finish and incur cost. From the cancellation request onward, suppress unsent result delivery, including late completions; a message already submitted to a provider may not be recallable. Status stays queryable without a mandatory second routine notification. Exact statuses, schemas, and native abort integration remain open, and cancellation retains the same account and originating-channel controls.

Website onboarding detects and saves the device timezone **once** as the personal default. The app does not continuously detect timezone or track travel; redetection on later website visits is deferred. The user can explicitly change the personal default timezone in the web app or chat. A timezone named in a task request applies only to that task without changing the default. A changed default applies to new tasks; existing tasks keep their assigned timezone unless explicitly edited. Ask for an unknown timezone and for a morning time when not already known, then confirm the chosen time and timezone.

Channel disconnection pauses its scheduled tasks, future runs, and pending unsent automatic results without fallback. Tasks and history remain; relinking the same channel leaves tasks paused until an explicit resume from that channel. Already-started sends cannot be recalled, and active attempts and one-off jobs retain honest cancellation and outcome semantics.

When a financial source is explicitly disconnected, a task continues only if remaining authorized data still fulfills its intended request. Otherwise, pause the affected task and explain why once in its originating channel. Reconnecting the source leaves the task paused until the user explicitly resumes it from that channel, at the next scheduled time without a missed-check backlog. A temporary provider outage is distinct from explicit disconnection: an isolated provider failure remains eligible for automatic recovery and does not automatically cancel the task.

The account's **proactive insights** setting enables or disables eligible linked iMessage delivery, enabled by default subject to applicable channel permissions. Website and supported chat controls expose the same account setting; clear supported requests change it immediately. WhatsApp cannot be selected, and linking WhatsApp does not enable proactive work. Disabling insights stops future proactive investigations and suppresses unsent proactive messages. Disconnecting iMessage prevents delivery without falling back to WhatsApp. Each qualifying finding follows one account-level investigation. Chat replies and requested work retain their originating channel, and relinking iMessage leaves its paused scheduled tasks paused until explicit resume from that channel.

The [conversation ownership decision](0022-human-support-conversation-ownership.md) selects Bird Conversations as the Apple staff UI. The backend enforces native conversation ownership: human takeover pauses automated replies and task reports until staff explicitly return control, and a new inbound message does not resume AI. Requested analyses and user-created schedules continue and save results; takeover alone does not cancel or restart them. Proactive starts are skipped while automated delivery is unavailable, and already-running findings cannot interrupt the human conversation. On explicit handback, the main agent handles pending requested results and considers proactive findings only if still useful and eligible, using correct timestamps, current evidence, and required authorization/delivery checks. Exact native integration, staffing/hours/SLAs, and WhatsApp transport/staff integration remain open.

Initiative uses the user's connected portfolio, goals, and remembered interests to judge relevance flexibly. Send only a meaningfully new and useful finding supported by strong evidence and worth the user's attention, with a concise explanation of why it matters. **High precision takes priority over recall:** accept missed marginal events to avoid spam, suppress uncertain, minor, repetitive, or low-value findings, and stay quiet when none qualifies. Resurface a finding only after an important change or new useful evidence. Explicitly scheduled work follows the user's request and its own controls; the initiative attention filter must not suppress requested results, including daily summaries on quiet or no-change days.

### 2.2 Initial BullMQ baseline and shared PostgreSQL records

The initial baseline uses BullMQ Job Schedulers for recurring jobs and **GCP Memorystore for Valkey through BullMQ's Redis-compatible backend** for schedule and queue state. The [queue-storage decision](0020-managed-valkey-queue-storage.md) owns the selected dedicated instance and its durability and availability trade-offs. Pinned versions and client integration still require validation. The library supplies timing and job claiming; MyStacks defines product behavior. See [BullMQ Job Schedulers](https://docs.bullmq.io/guide/job-schedulers/).

The design uses current scheduling APIs, without a custom scheduler engine or a legacy `QueueScheduler` service. BullMQ documents [`QueueScheduler` as deprecated](https://docs.bullmq.io/guide/queuescheduler).

The shared PostgreSQL database owns saved task definitions, run statuses and results, and pending/handled completion state in application-owned tables. The backend registers recurring schedules and derives BullMQ timing state from saved definitions. Their update and recovery contract must be explicit without creating two independently editable definitions. Record schemas and detailed consistency mechanics remain open. Valkey stores queue and schedule data; it does not start a stopped application service.

The [analysis retention decision](0023-analysis-data-retention-and-object-storage.md) selects private Google Cloud Storage for retained datasets/workspace files and PostgreSQL for records, small structured results, metadata, and file references. Retain useful provider inputs actually used, reusable intermediate calculations, final results, and supporting evidence conservatively, subject to provider data rights; automatic pruning is deferred. Save useful retained files before E2B destruction with account/channel/run ownership, type, saved/retrieval/source-as-of times, provider/connection, size, and storage reference metadata; unknown source time is allowed. Backend-controlled native SDK access and run-scoped transfers may restore chosen authorized files into a later fresh sandbox without broad cloud credentials or unrestricted bucket access. Storage follows purpose rather than mandatory size thresholds. It supports follow-ups without exact replay, durable reasoning checkpoints, fresh-data claims from old evidence, or a continuous portfolio-history archive.

Under this baseline, BullMQ owns timing, queue dispatch, job claims, and configured job-level retries. Mastra executes the claimed run. A Mastra scheduler or workflow retry mechanism must not independently schedule or retry that same queued operation. Any model or API retries within a run must have a distinct scope. Requested scheduled failures follow section 2.5, and whole-job recovery follows section 2.7. Proactive investigation failures and interruptions have no whole-investigation automatic retry under section 2.4.

**DBOS is a future alternative only when concrete benefits justify adoption.** It is outside the current implementation scope. Any later adoption must define the background execution and recovery responsibilities it takes over while preserving Mastra agent execution and MyStacks-owned task intent, authorization, channel ordering, completion routing, and delivery policy. It would not replace the whole application or strengthen its accepted guarantees by itself.

### 2.3 Shared warm capacity

Workers are warm application processes in a [Cloud Run worker pool](0017-cloud-run-worker-pool.md), deployed separately from API/chat using the same backend codebase and distinct entrypoints. The pool has no HTTP ingress. Use the initial staging allocation selected by the [scaffolding delivery](../design/scaffolding.md), and adjust its count manually as measured use requires; production capacity remains a separate decision. These processes can run multiple jobs; they are not newly created infrastructure jobs for each task. Pool instance count and BullMQ worker job concurrency are separate controls, as are the product's per-chat quotas. BullMQ supports worker concurrency and [multiple workers across machines](https://docs.bullmq.io/guide/workers/concurrency).

Available warm capacity avoids provisioning a worker for each run. Busy queues, capacity changes, replacement-worker startup, sandbox startup, and provider or model latency can still delay work. BullMQ's recurring job production can also slow when the previous job has not begun processing. [Job Scheduler behavior](https://docs.bullmq.io/guide/job-schedulers/)

The worker-pool decision owns capacity configuration, operating evidence, idle-instance billing, and the short shutdown warning; deployment cannot guarantee that an expected 5–10-minute run finishes. Instance replacement and job recovery are distinct responsibilities. Section 2.7 defines native interruption recovery; exact shutdown integration and duplicate-result handling remain open within that policy.

### 2.4 Bounded proactive investigations

The backend schedules only accounts with proactive insights enabled and verified linked iMessage currently eligible for automated delivery, then rechecks those conditions and authority when queued work actually starts. Human ownership makes automated delivery unavailable, so skip proactive starts while it holds. Each eligible check investigates a defined financial scope once for the account, with useful authorized read, research, code-execution, and shared personal-memory read tools. It cannot change settings, connections, memory, or saved tasks, start nested subagents, or directly send user messages. Phase 1 has no data-change prefilter or rule-trigger prerequisite for invoking the agent. Exact scopes, calculations, and thresholds remain open; execution limits follow the worker-pool decision.

Target **approximately five investigations per eligible account per day**, randomly spaced within **09:00–21:00 in the saved user timezone**. Times vary across users and days or occurrences rather than using fixed daily cron times. This configurable default spreads load and is not an exact quota or a user intensity setting. The window constrains actual investigation starts only: a 20:58 start may deliver at 21:03. Only one proactive investigation per account may be active; skip overlapping occurrences and do not catch up missed checks after downtime. A BullMQ [custom repeat strategy](https://docs.bullmq.io/guide/job-schedulers/repeat-strategies) or next-due timing is a provisional integration option, not a selected algorithm or separate scheduler service.

If nothing qualifies, remain quiet. A candidate returns through main-agent continuation within the defined scope and read-only proactive purpose. Each qualifying finding can go to eligible verified linked iMessage. Before each eventual send, recheck proactive insights, native AI conversation ownership, eligibility, channel validity, and delivery authority. Disabling proactive insights suppresses future investigations and unsent proactive messages while leaving requested schedules under their own controls.

Keep account-level proactive finding and notification history **separate from personal memory**. Record actual iMessage messages and send times with supporting findings and evidence, distinguishing candidates, failed or uncertain deliveries, and accidental retries from successful notifications. Later investigations use this history after proactive insights are disabled and later enabled; each delivered message enters only iMessage history, and channel transcripts and saved tasks do not become shared memory. The main agent judges meaningful usefulness and change, while the backend handles eligibility, authorization, recognized duplicate delivery attempts, and delivery policy. This does not promise perfect semantic deduplication or exactly-once external delivery.

If an investigation fails or is interrupted, record the outcome internally and wait for the next scheduled check, without a whole-investigation automatic retry or a routine user failure message. Delivery failure must not rerun the investigation. Requested work follows sections 2.5 and 2.7; uncertain outbound delivery follows section 2.8. Existing channel, timezone, edit, pause/resume, and financial-source-disconnection contracts remain in force.

### 2.5 Requested schedules and independent occurrences

Backend scheduling tools admit user-created schedules only from iMessage and enforce a configurable **one-hour minimum interval** uniformly for Phase 1 user-created recurring schedules. For a shorter request, explain the limit and offer hourly without silently changing the schedule. Normal chat and explicitly requested one-off work are unaffected; the interval does not claim hourly freshness from every data provider.

Each iMessage chat may have **at most five enabled user-created recurring tasks**. Paused tasks do not count, and backend scheduling tools enforce the enabled-task quota when creating, enabling, or resuming a task. This quota concerns saved schedules, independently of the main-agent delegation limit.

Each eligible occurrence starts one background agent run, independent of the main-agent delegation quota. **Do not check whether the same task's previous run is queued or running.** Distinct occurrences can run in parallel; overlap does not skip, replace, defer behind, or cancel either run. Do not add overlap locks or leases to prevent that allowed concurrency. Same-occurrence job and delivery duplicate handling remains a separate concern.

The expected **5–10-minute** execution time compared with minimum hourly recurrence is an operating assumption, not a deadline, timeout, or guarantee. Eligible due work is accepted into execution subject to current pause/cancel state, verified channel, and financial authority; actual worker start depends on capacity. Exact-time, exactly-once, outage catch-up, and unlimited-worker guarantees are not added. Native BullMQ schedule production still requires integration verification.

A requested scheduled execution gets **one automatic retry for a known temporary failure**, within the shared attempt allowance in section 2.7. BullMQ owns the whole-job retry; inner tool/SDK retries have a distinct scope. If the retry fails, the main agent gives a concise failure explanation and the recurring schedule stays enabled. Exact temporary-failure classification and retry delay remain open. Foreground chat and message transport retain separate policies.

### 2.6 One shared concurrent queue with relative priorities

Use **one shared background execution queue across users**, consumed by the common Cloud Run worker pool. The queue carries these three work classes with explicit relative priorities:

| Work class | Priority |
| --- | --- |
| Main-agent-delegated subagents | Highest |
| User-created scheduled occurrences | Normal |
| Proactive investigations | Lowest |

Normal chat continues directly in the backend, outside this queue. Workers process multiple jobs concurrently under the configured job concurrency and pool capacity; a shared queue does not serialize execution. Each job retains its trusted account/channel context, authority checks, admission rules, and work-class retry policy.

**Non-preemptive priority** orders waiting jobs without interrupting active work or reserving execution slots for any class. All three classes intentionally share capacity, so active proactive work may delay a newly delegated subagent. Sustained higher-priority demand may delay or starve lower-priority work. These are accepted initial limits without a latency or fairness guarantee.

Under the BullMQ baseline, assign an explicit positive priority to every job in all three classes. BullMQ processes lower positive values first, while an omitted priority or `0` runs ahead of positive priorities; see [BullMQ prioritized jobs](https://docs.bullmq.io/guide/jobs/prioritized). Exact numeric values remain open. The configured mapping must preserve the order above rather than rely on BullMQ's default.

### 2.7 Whole-job recovery and shared attempt allowance

Application deployment stops the old processes and starts new ones while independently hosted PostgreSQL and Valkey retain their state. Waiting jobs stay in the queue. Use BullMQ's native [graceful shutdown](https://docs.bullmq.io/guide/workers/graceful-shutdown), [reconnection](https://docs.bullmq.io/guide/going-to-production#automatic-reconnections), and [stalled-job recovery](https://docs.bullmq.io/guide/jobs/stalled). Deployment accepts downtime; it does not require an empty queue, a deployment-specific recovery state machine, or a startup script that recreates every pending job.

Treat each user-requested background job, including a one-off job or one scheduled occurrence, as one whole-job execution unit with **at most two total execution attempts**. If a worker interruption leaves analysis unfinished, restart it **from the beginning** only while the work remains active and authorized and an attempt remains. An interrupted execution consumes an attempt. The new attempt creates a fresh E2B sandbox if shell or code is needed. Cancellation or loss of authority prevents restart. Phase 1 does not checkpoint or resume inside agent, model, tool, or live-workspace steps.

Interruption restarts and the known-temporary-failure retry in section 2.5 consume the **same allowance**; they cannot produce a third attempt. For non-interruption errors in one-off jobs, retry eligibility remains open within this two-attempt ceiling.

Reuse a completed analysis result and required saved outputs for completion handling and delivery. A main-agent continuation is a separate execution run that reads those outputs rather than inheriting the child's sandbox or processes. A completion-event or delivery failure must not rerun successful research or calculation. Proactive failure or interruption follows section 2.4: record the outcome internally and wait for the next scheduled check without retrying the whole investigation.

The integration must map BullMQ retries and stalled-job recovery to this shared allowance; setting `attempts=2` alone is not evidence that all interruption and retry paths respect the ceiling. Exact native accounting, abort integration, and duplicate-completion handling remain open. This policy does not promise exactly-once execution or delivery.

### 2.8 Uncertain outbound delivery

Use provider-supported idempotency, deduplication, or delivery-status checks when available. If submission remains ambiguous after a timeout, record the uncertain outcome and **do not blindly resend automatically**. Keep the saved result available when the user asks, subject to current authorization and channel controls. A failed or uncertain send never reruns completed analysis. This policy accepts that an occasional report may not arrive automatically rather than risk duplicate messages after an ambiguous submission. Retry eligibility and timing for definitive send failures remain open.

## 3. Rationale and alternatives

Durable scheduling separates a user's standing instructions from the lifetime of any process. Shared workers allocate execution capacity to active work while users' schedules and context remain stored between runs.

**One queue keeps the initial execution path and capacity allocation simple.** Relative priorities favor explicitly delegated conversational work, then requested schedules, ahead of independent initiative while reusing the same execution code and Valkey instance. The trade-off is shared contention and possible lower-priority starvation. Split queues with allocated worker capacity are an alternative when observed contention justifies isolating capacity; different queue names alone do not reserve resources. A split can retain the same execution code and Valkey instance, but adds queue and capacity allocation decisions. The initial design accepts contention rather than adding that allocation before it is needed.

**Whole-job restart keeps recovery at the queue boundary.** It accepts repeated model/provider work and lost intermediate progress instead of adding checkpoints for individual agent steps. The shared two-attempt ceiling bounds repeated execution, while keeping completed results separate from delivery avoids repeating successful analysis after a send failure.

**Pending saved completions cover missed wakeups.** Startup and periodic checks let the coordinator handle a result saved while it was unavailable, using the same channel order and current checks as the native event path. This adds durable completion state and a bounded check without promising exactly-once turns or adding another execution-recovery system.

**Saved timezones keep schedule meaning stable.** One-time detection and explicit updates avoid treating travel or a later website visit as an instruction to move existing tasks. Users accept that travel requires an explicit timezone update; task-specific overrides affect only that task, and existing tasks retain their assigned zone unless edited. Automatic redetection is deferred.

An always-on runtime for every user with local timers is a viable alternative. It keeps timers and local state together, but carries idle compute, fleet health, upgrades, and state-recovery costs. A suspended or stopped process cannot rely on a local timer to execute due work.

**BullMQ keeps the initial execution boundary small.** Its queue and concurrency model supports the shared-worker direction without selecting a separate durable-workflow operating model. The trade-off is that MyStacks must still settle task-to-queue consistency, attempt accounting, and completion-recovery details within the accepted limits. Its Redis-compatible integration with managed Valkey requires validation.

DBOS may be reconsidered when a concrete benefit, such as reducing the application work needed for a required recovery behavior, outweighs its integration and operating costs. Possible benefits alone do not make it a planned migration. A managed scheduler or another queue is also an alternative only when its recurrence, execution, and operational contract provides a justified improvement while preserving accepted behavior.

Proactive usefulness depends on interpreting personal relevance and new evidence, so every eligible check receives a bounded agent investigation. Checking destination eligibility first avoids investigating when the account cannot receive an insight. Randomized local daytime starts spread load and bound initiation without delaying a useful result merely because it finishes after the window. Skipping overlap and missed occurrences favors fresh, low-noise findings over a catch-up backlog. Waiting for the next check after investigation failure accepts delayed findings in exchange for less repeated work and fewer notices. One account-level investigation serves eligible iMessage. Sent-notification history supports repeat handling after proactive insights are disabled and later enabled without mixing channel conversations into shared personal memory.

Requested occurrences keep the user's recurrence independent of unusually long earlier runs. Expected 5–10-minute execution against minimum hourly recurrence supports this simple operating model without a previous-run coordination mechanism. The enabled-schedule quota bounds saved recurring demand, while the main-agent delegation quota controls a different source of outstanding work. One temporary-failure retry provides bounded recovery without cancelling future occurrences.

## 4. Consequences and open decisions

- **Capacity planning:** the [worker-pool decision](0017-cloud-run-worker-pool.md) owns execution limits and operating evidence. Tune capacity from queue and resource usage; stored user or task totals alone cannot establish concurrent capacity.
- **Timing:** requested tasks retain their assigned schedules within the one-hour minimum. Proactive timing follows section 2.4. Exact supported recurrence forms, daylight-saving mechanics, native schedule production, randomized timing integration, and overdue requested work outside pause/resume remain open. Queueing does not promise strict start times or exactly-once execution or delivery. Preserve best-effort checks and delivery, accepted missed events, and precision ahead of recall.
- **Storage:** saved task, run, and pending/handled completion records use ordinary application-owned tables in the [shared PostgreSQL database on a dedicated TimescaleDB-enabled Tiger Cloud service](0013-shared-postgresql-storage.md). Decide their schemas and the definition-to-queue update contract. The [queue-storage decision](0020-managed-valkey-queue-storage.md) owns Valkey hosting and operating configuration; the [scaffolding delivery](../design/scaffolding.md) selects the initial Tiger Cloud target plan, region, and size. Database creation/URL are deferred; backup/recovery and cross-cloud connectivity still require verification.
- **Requested-run behavior:** preserve independent occurrences, the scheduled temporary-failure retry in section 2.5, and native whole-job recovery within the shared two-attempt allowance in section 2.7. After retry failure, main reports concisely and recurrence stays enabled. Define exact temporary-failure classification and delay, one-off non-interruption retry eligibility, BullMQ attempt and stalled-job accounting, native abort integration, the dispatch-start boundary, and duplicate-completion handling. Cancellation follows section 2.1. Proactive investigations retain the distinct skip-overlap and failure-wait policy in section 2.4.
- **Chat continuity:** ordinary chat initially executes directly through the single active backend chat coordinator under the [channel-turn decision](0009-channel-turns-and-background-subagents.md), outside the background queue. An acknowledged chat turn may remain unanswered after process interruption; persisted messages alone do not resume inference. The selected Cloud Run Service baseline provides CPU after transport acknowledgement. How replacement and possible instance overlap preserve one active coordinator remains open; an instance limit alone does not establish exclusive ownership.
- **Delivery:** the main agent owns text-first, concise, precise chat replies, with the main finding, key numbers, and needed reasoning. Follow-up questions can deepen substantial calculations and research using available sources. Section 2.8 owns uncertain delivery. Decide definitive send-failure retries, duplicate-handling details, and pending-completion representation while preserving actual delivery outcomes, the proactive insights setting, native conversation ownership, channel history, and task boundaries.
- **Initiative methods:** the qualitative relevance and attention policy is accepted. The [current-evidence decision](0019-current-portfolio-evidence.md) requires fresh or near-fresh account evidence for current-exposure conclusions while preserving periodic detection and useful requested answers. Architecture and evidence must establish exact financial scopes, provider calculations, attention and material-change thresholds, maximum evidence ages, precision measurement and any numeric target, and detailed repeat handling. Provider polling and permitted-use constraints remain explicit validation gaps under the [provider decision](0018-managed-financial-data-providers.md), without silently changing accepted schedule frequencies. No numeric precision target is guaranteed, and these methods must preserve requested results and best-effort monitoring limits.
- **Operational fit:** worker hosting uses the separate Cloud Run worker pool with manual instance scaling. The [scaffolding delivery](../design/scaffolding.md) selects its initial region, instance count, and resources. Production capacity, job-concurrency tuning, verified permissions/network connectivity, execution-limit values, and provider/model quota handling remain separate choices under the worker-pool decision. Pending-completion recovery is selected; its exact schema, check interval, handled boundary, crash behavior, event cursor/replay and retention settings, and duplicate-handling mechanics remain open. Scheduler-started requested and proactive runs remain outside the main-agent delegation quota. Validate the selected BullMQ and managed Valkey versions and integration.
- **Channel integration:** Bird is the Apple MSP and Bird Conversations is the staff UI under the [messaging](0021-apple-messages-with-bird.md) and [ownership](0022-human-support-conversation-ownership.md) decisions. Native API/webhook product/version/configuration, ownership and explicit handback mapping, Apple account approval/experience review, permitted financial notification scope, and required notices/opt-outs remain validation items in [TODO](../TODO.md). WhatsApp transport/staff integration remains open; its schedules, proactive reports, and template messaging are deferred.
