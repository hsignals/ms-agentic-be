# Durable scheduling and queued execution

## 1. Status and scope

**Status: ACCEPTED durable scheduling, backend record ownership, and Phase 1 task and proactive-message behavior; TENTATIVE framework integration; PROVISIONAL BullMQ and Redis choice.** MyStacks stores ongoing task definitions and background run states and results in its backend database. Due and explicitly requested background work uses shared workers, with BullMQ and Redis as the recurrence and queueing candidate pending integration and operational validation. The overall architecture remains tentative.

This decision supports daily digests, user-defined informational tasks, and proactive checks under the [requirements](../requirements.md). The [architecture](../architecture.md) owns detailed flows and state ownership; this record owns the scheduling trade-off.

## 2. Decision

### 2.1 Persistent definitions and new runs

The backend database retains ongoing work's **intent, current status, stable account, originating channel, and trigger**, plus background run records, statuses, internal results, and original-request correlation. Saved recurring tasks remain distinct from their execution runs. When a worker claims due work, it starts a new run with trusted context and the instructions that apply when it starts. The schedule and queue wait between runs; an LLM need not keep running or remember to wake itself.

Shared workers wait for queued work, claim ready jobs, and execute MyStacks application code. Each eligible user-created scheduled occurrence starts one background Mastra agent run with trusted account, resource, channel, and thread context. Agents can use predefined reads, calculations, or deeper research. Every eligible proactive check also invokes a bounded agent investigation. Both paths operate within resource budgets. Channel scope does not require separate channel runtimes, queues, or deployments.

Workers return internal findings, data, evidence, or artifact references rather than send child reports directly. A completion event, provisionally through BullMQ [QueueEvents](https://docs.bullmq.io/guide/workers), lets the backend invoke the channel handler with trusted stored references. Requested work uses its originating channel; proactive findings support delivery to all selected eligible channels without repeating the investigation. An idle channel starts a new main-agent turn; a busy channel retains the completion for a later turn. The main agent can investigate further or combine children before composing the user reply within the original authorized purpose. Completion grants no new instruction or permission. A separate overall-request lifecycle is not part of this design. The [runtime design](../design/runtime.md) owns channel-turn details.

The configurable initial limit is **five queued or running subagents spawned by the main agent per chat**. Terminal jobs do not count. Scheduler-started requested occurrences and proactive investigations are excluded; a new subagent spawned by a main-agent continuation does count. When the delegation limit is reached, the assistant reports capacity instead of accepting a sixth. Only main-agent turns may delegate additional subagents, and subagents cannot start nested subagents or directly send user messages. Saved recurring tasks have a separate enabled-task quota under section 2.5.

Users can list, inspect, change, pause, resume, and cancel only the current channel's ongoing tasks. They can list independent jobs, check status, and request cancellation only in their originating channel; results stay there too. Backend handlers enforce account and channel ownership rather than trusting model-selected identifiers. Phase 1 chat cannot select another destination, transfer work, or retarget results. Account-wide personal memory and financial access do not expand task access; the [channel and memory decision](0008-channel-scoped-work-and-shared-memory.md) owns that boundary.

Task edits apply to future runs; active runs keep their original instructions unless explicitly cancelled. Before protected reads and delivery, the orchestration layer must still enforce current financial permissions, channel validity, applicable task pause/cancel state, and delivery authority. Pausing stops future runs and holds automatic results not yet sending. Resuming continues at the next scheduled time without a missed-update backlog. Cancelling ends recurrence and requests cancellation of all queued and running occurrences of that task; past results remain available in the owning channel. The instruction snapshot is a logical requirement, not a selected persistence schema.

Website onboarding detects and saves the device timezone **once** as the personal default. The app does not continuously detect timezone or track travel; redetection on later website visits is deferred. The user can explicitly change the personal default timezone in the web app or chat. A timezone named in a task request applies only to that task without changing the default. A changed default applies to new tasks; existing tasks keep their assigned timezone unless explicitly edited. Ask for an unknown timezone and for a morning time when not already known, then confirm the chosen time and timezone.

Channel disconnection pauses its scheduled tasks, future runs, and pending unsent automatic results without fallback. Tasks and history remain; relinking the same channel leaves tasks paused until an explicit resume from that channel. Already-started sends cannot be recalled, and active attempts and one-off jobs retain honest cancellation and outcome semantics.

When a financial source is explicitly disconnected, a task continues only if remaining authorized data still fulfills its intended request. Otherwise, pause the affected task and explain why once in its originating channel. Reconnecting the source leaves the task paused until the user explicitly resumes it from that channel, at the next scheduled time without a missed-check backlog. A temporary provider outage is distinct from explicit disconnection: an isolated provider failure remains eligible for automatic recovery and does not automatically cancel the task.

The account's **proactive insight delivery channels** may include one, both, or none of its linked messaging channels. Website and chat expose the same selection, and every newly linked channel is selected by default. Clear chat requests change that selection immediately; when an activation request leaves the destination materially ambiguous, clarify which linked channels to select. Selecting none stops future proactive investigations and suppresses unsent proactive messages. Removing or disconnecting a channel prevents pending sends there and never enables an unselected one. Each qualifying insight goes to all selected, currently eligible verified channels after one account-level investigation, without repeating research per destination. This setting routes only proactive insights; chat replies and requested work retain their originating channel, and linking a channel leaves its paused scheduled tasks paused until explicit resume from that channel.

Initiative uses the user's connected portfolio, goals, and remembered interests to judge relevance flexibly. Send only a meaningfully new and useful finding supported by strong evidence and worth the user's attention, with a concise explanation of why it matters. **High precision takes priority over recall:** accept missed marginal events to avoid spam, suppress uncertain, minor, repetitive, or low-value findings, and stay quiet when none qualifies. Resurface a finding only after an important change or new useful evidence. Explicitly scheduled work follows the user's request and its own controls; the initiative attention filter must not suppress requested results, including daily summaries on quiet or no-change days.

### 2.2 Provisional queue and shared PostgreSQL records

The candidate uses BullMQ Job Schedulers for recurring jobs and Redis for the schedule and queue state used by BullMQ. The library supplies timing and job claiming; MyStacks must define product behavior and configure the required durability. See [BullMQ Job Schedulers](https://docs.bullmq.io/guide/job-schedulers/).

The design uses current scheduling APIs, without a custom scheduler engine or a legacy `QueueScheduler` service. BullMQ documents [`QueueScheduler` as deprecated](https://docs.bullmq.io/guide/queuescheduler).

The shared PostgreSQL database owns saved task definitions and run statuses and results in application-owned tables. The backend registers recurring schedules and derives BullMQ timing state from saved definitions. Their update and recovery contract must be explicit without creating two independently editable definitions. Record schemas and detailed consistency mechanics remain open. Redis stores queue and schedule data; it does not start a stopped service.

Under this provisional choice, BullMQ owns timing, queue dispatch, job claims, and configured job-level retries. Mastra executes the claimed run. A Mastra scheduler or workflow retry mechanism must not independently schedule or retry that same queued operation. Any model or API retries within a run must have a distinct scope. Requested scheduled execution follows section 2.5; proactive investigation failures have no whole-investigation automatic retry under section 2.4. One-off background retry details remain open.

### 2.3 Shared warm capacity

Workers are warm application processes that can run multiple jobs and can be distributed across hosts. They are not newly created infrastructure jobs for each task. BullMQ supports worker concurrency and [multiple workers across machines](https://docs.bullmq.io/guide/workers/concurrency).

Available warm capacity avoids provisioning a worker for each run. Busy queues, capacity changes, replacement-worker startup, sandbox startup, and provider or model latency can still delay work. BullMQ's recurring job production can also slow when the previous job has not begun processing. [Job Scheduler behavior](https://docs.bullmq.io/guide/job-schedulers/)

### 2.4 Bounded proactive investigations

The backend schedules only accounts with at least one selected, verified linked destination that is currently eligible, then rechecks eligibility and authority when queued work actually starts. Each eligible check investigates a defined financial scope once for the account, regardless of destination count, with useful authorized read, research, code-execution, and shared personal-memory read tools. It cannot change settings, connections, memory, or saved tasks, start nested subagents, or directly send user messages. Phase 1 has no data-change prefilter or rule-trigger prerequisite for invoking the agent. Exact scopes, calculations, thresholds, and numeric time/cost budgets remain open.

Target **approximately five investigations per eligible account per day**, randomly spaced within **09:00–21:00 in the saved user timezone**. Times vary across users and days or occurrences rather than using fixed daily cron times. This configurable default spreads load and is not an exact quota or a user intensity setting. The window constrains actual investigation starts only: a 20:58 start may deliver at 21:03. Only one proactive investigation per account may be active; skip overlapping occurrences and do not catch up missed checks after downtime. A BullMQ [custom repeat strategy](https://docs.bullmq.io/guide/job-schedulers/repeat-strategies) or next-due timing is a provisional integration option, not a selected algorithm or separate scheduler service.

If nothing qualifies, remain quiet. A candidate returns through main-agent continuation within the defined scope and read-only proactive purpose. Each qualifying finding goes to all selected, currently eligible verified channels. Before each eventual send, recheck that destination's current selection, eligibility, channel validity, and delivery authority. Selecting no proactive insight delivery channels suppresses future investigations and unsent proactive messages while leaving requested schedules under their own controls.

Keep account-level proactive finding and notification history **separate from personal memory**. Record actual sent messages and times for each channel with supporting findings and evidence, distinguishing candidates and failed or uncertain deliveries from successful notifications. Intended copies across selected channels are distinct from accidental retries to the same channel. Later investigations use this history even after the proactive insight delivery channels change; each delivered copy enters only its destination channel's history, and channel transcripts and saved tasks do not become shared memory. The main agent judges meaningful usefulness and change, while the backend handles eligibility, authorization, recognized duplicate delivery attempts, and delivery policy. This does not promise perfect semantic deduplication or exactly-once external delivery.

If an investigation fails, record the failure internally and wait for the next scheduled check, without a whole-investigation automatic retry or a routine user failure message. Delivery failure must not rerun the investigation. Requested schedules follow their distinct execution policy in section 2.5; one-off and transport retry behavior remain open. Existing channel, timezone, edit, pause/resume, and financial-source-disconnection contracts remain in force.

### 2.5 Requested schedules and independent occurrences

Backend scheduling tools enforce a configurable **one-hour minimum interval** uniformly for Phase 1 user-created recurring schedules. For a shorter request, explain the limit and offer hourly without silently changing the schedule. Normal chat and explicitly requested one-off work are unaffected; the interval does not claim hourly freshness from every data provider.

Each chat may have **at most five enabled user-created recurring tasks**. Paused tasks do not count, and backend scheduling tools enforce the enabled-task quota when creating, enabling, or resuming a task. This quota concerns saved schedules, independently of the main-agent delegation limit.

Each eligible occurrence starts one background agent run, independent of the main-agent delegation quota. **Do not check whether the same task's previous run is queued or running.** Distinct occurrences can run in parallel; overlap does not skip, replace, defer behind, or cancel either run. Do not add overlap locks or leases to prevent that allowed concurrency. Same-occurrence job and delivery duplicate handling remains a separate concern.

The expected **5–10-minute** execution time compared with minimum hourly recurrence is an operating assumption, not a deadline, timeout, or guarantee. Eligible due work is accepted into execution subject to current pause/cancel state, verified channel, and financial authority; actual worker start depends on capacity. Exact-time, exactly-once, outage catch-up, and unlimited-worker guarantees are not added. Native BullMQ schedule production still requires integration verification.

A requested scheduled execution gets **one automatic retry for a known temporary failure**, with at most **two execution attempts per occurrence**. BullMQ owns the whole-job retry; inner tool/SDK retries have a distinct scope. If the retry fails, the main agent gives a concise failure explanation and the recurring schedule stays enabled. Exact temporary-failure classification and retry delay remain open. This numeric policy does not extend to unscheduled one-off jobs, foreground chat, or message transport. A delivery failure must not rerun successful research or calculation.

## 3. Rationale and alternatives

Durable scheduling separates a user's standing instructions from the lifetime of any process. Shared workers allocate execution capacity to active work while users' schedules and context remain stored between runs.

**Saved timezones keep schedule meaning stable.** One-time detection and explicit updates avoid treating travel or a later website visit as an instruction to move existing tasks. Users accept that travel requires an explicit timezone update; task-specific overrides affect only that task, and existing tasks retain their assigned zone unless edited. Automatic redetection is deferred.

An always-on runtime for every user with local timers is a viable alternative. It keeps timers and local state together, but carries idle compute, fleet health, upgrades, and state-recovery costs. A suspended or stopped process cannot rely on a local timer to execute due work.

A managed scheduler and queue is another viable alternative if its recurrence, delivery, and operational contract fits the product. BullMQ and Redis are provisional because their familiar queue and concurrency model may meet the need without a custom scheduling engine; the detailed fit and operating configuration still require validation.

Proactive usefulness depends on interpreting personal relevance and new evidence, so every eligible check receives a bounded agent investigation. Checking destination eligibility first avoids investigating when the account cannot receive an insight. Randomized local daytime starts spread load and bound initiation without delaying a useful result merely because it finishes after the window. Skipping overlap and missed occurrences favors fresh, low-noise findings over a catch-up backlog. Waiting for the next check after investigation failure accepts delayed findings in exchange for less repeated work and fewer notices. One account-level investigation serves the selected channels without duplicate research. Per-channel sent-notification history supports intended copies and repeat handling when the proactive insight delivery channels change without mixing channel conversations into shared personal memory.

Requested occurrences keep the user's recurrence independent of unusually long earlier runs. Expected 5–10-minute execution against minimum hourly recurrence supports this simple operating model without a previous-run coordination mechanism. The enabled-schedule quota bounds saved recurring demand, while the main-agent delegation quota controls a different source of outstanding work. One temporary-failure retry provides bounded recovery without cancelling future occurrences.

## 4. Consequences and open decisions

- **Capacity planning:** stored users or tasks do not equal concurrent runs. Size workers from task frequency, run duration, due-time bursts, and model/provider quotas; user totals alone cannot establish capacity.
- **Timing:** requested tasks retain their assigned schedules within the one-hour minimum. Proactive timing follows section 2.4. Exact supported recurrence forms, daylight-saving mechanics, native schedule production, randomized timing integration, and overdue requested work outside pause/resume remain open. Queueing does not promise strict start times or exactly-once execution or delivery. Preserve best-effort checks and delivery, accepted missed events, and precision ahead of recall.
- **Storage:** saved task and run records use application-owned tables in the [shared PostgreSQL database](0013-shared-postgresql-storage.md). Decide their schemas, the definition-to-queue update contract, and Redis persistence, backup, and recovery configuration within that ownership.
- **Requested-run behavior:** preserve independent occurrences and the two-attempt temporary-failure policy in section 2.5. After retry failure, main reports concisely and recurrence stays enabled. Define exact temporary-failure classification and delay, one-off retry details, cancellation mechanics, the dispatch-start boundary, interruption, and restart behavior. Proactive investigations retain the distinct skip-overlap and failure-wait policy in section 2.4.
- **Chat continuity:** ordinary chat initially executes directly in the backend rather than through a durable BullMQ chat queue. An acknowledged chat turn may remain unanswered after process interruption; persisted messages alone do not resume inference. Hosting must support work after transport acknowledgement, with its CPU and lifetime choices still open.
- **Delivery:** the main agent owns text-first, concise, precise chat replies, with the main finding, key numbers, and needed reasoning. Follow-up questions can deepen substantial calculations and research using available sources. Decide transport retries, duplicate handling, uncertainty, and pending-completion routing when the proactive insight delivery channels change while preserving per-channel outcomes, current selection, channel history, and task boundaries.
- **Initiative methods:** the qualitative relevance and attention policy is accepted. Architecture and evidence must establish exact financial scopes, provider calculations, attention and material-change thresholds, freshness rules, precision measurement and any numeric target, and detailed repeat handling. No numeric precision target is guaranteed, and these methods must preserve requested results and best-effort monitoring limits.
- **Operational fit:** select worker hosting, global capacity, warm capacity, queue visibility, numeric resource budgets, and provider/model quota handling. Scheduler-started requested and proactive runs remain outside the main-agent delegation quota. BullMQ and Redis remain replaceable until integration and operating validation settle the technology choice.
