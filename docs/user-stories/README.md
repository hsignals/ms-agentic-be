# Phase 1 user stories

## 1. Scope and status

This catalogue covers the **complete Phase 1 user experience** for the MyStacks personal investing agent. The [requirements](../requirements.md) own accepted product scope. Progressive onboarding, read-only financial information, portfolio understanding, conversational work, ongoing tasks, proactive information, and long-term personalization are part of that scope.

**Accepted experiences and remaining proposals are identified in each story.** Acceptance bullets do not settle choices marked open in the requirements or their owning document. The [technical designs](../design/README.md) distinguish agreed execution decisions from provisional integrations within an **overall architecture still under review**. Milestones remain unchosen.

**The core Phase 1 user-story discussion is complete.** Remaining decisions below concern provider-dependent detail, implementation and operating policy, or explicitly lower-priority and deferred capabilities. The architecture round must preserve the agreed behavior while resolving those details.

| Area | Accepted experience | Remaining discussion |
| --- | --- | --- |
| Onboarding | Phone/SMS signup, button-based iMessage or WhatsApp linking, then optional financial connections; persistent dashboard with the same Add account/Add more flow for new and returning users; website-only connection removal and channel settings; EVM verification and eligible-wallet reuse for low-priority Hyperliquid. | Provider and wallet coverage, supported sender identities, device handoff compatibility, low-priority phone changes and recovery, and retention details. |
| Portfolio | Website previews and user-requested chat answers; USD values with native quantities; provider-backed, best-effort calculations that distinguish balance changes from investment returns. | Provider-supported metrics, valuation and performance formulas, cash-flow inputs, and history coverage. |
| Conversation | Concise text answers, separate channel context, and up to five outstanding main-agent-spawned subagents per chat. Returned work lets the main agent continue analysis and reply while other requests remain usable. | Research-source selection, global capacity, and exact interruption mechanics; file analysis and images are low priority. |
| Tasks and proactive messages | Five enabled user schedules per chat, minimum hourly cadence, independent occurrences that may overlap, and one retry for temporary scheduled-execution failure. Proactive checks retain their separate randomized daytime, high-precision policy and account-wide control. | Investigation scopes, evidence thresholds, recurrence/DST, transient-error classification and retry delay, delivery retries, budgets, and repeat-suppression implementation. |
| Memory | Shared personal context with automatic updates from clear new user statements, clarification of material ambiguity, distinguishable interpretations, and chat controls to inspect, correct, and forget. | Selection, retention, concurrent-write ordering, and completion mechanisms. |

**Low priority:** Hyperliquid support (`US-ONB-11`), financial file analysis (`US-CHAT-04`), image replies, phone-number changes and lost-number/email recovery (`US-ONB-09`), alternate display currencies (`US-PORT`), and in-flight steering (`US-CHAT-05`). **Deferred:** extensive deep-research reports and polished website report artifacts, automatic timezone re-detection on later website visits, account deletion (`US-ONB-10`), QR linking, WhatsApp-based login, and cross-channel work or destination selection from chat. Export remains proposed.

Phase 1 excludes specific buy, sell, or rebalance recommendations and financial execution. Wallet addresses, Binance, and Hyperliquid are the required connection categories. Supported account types, assets, balances, and positions depend on the provider or connector and are shown before connection confirmation. EVM wallets require wallet-control verification before connection and tracking. Hyperliquid setup reuses eligible verified wallets without another signature or lets the user verify another supported wallet. Connections cover the user's own supported accounts. Additional exchanges and brokerage coverage remain future product directions.

These areas are parts of one experience. Chat may guide a user to website connection setup, answer portfolio questions, create a recurring check in that channel, and correct shared personal memory. The website manages source and channel links. The product must preserve consistent authority, evidence, and user control across those transitions.

## 3. Shared experience principles

- **Signup before chat:** phone/SMS signup precedes channel linking and optional financial setup. Phone verification is the only required MyStacks signup information; name, goals, and preferences are optional. Each stable account has one primary verified number, with number changes and recovery at low priority.
- **Progressive financial setup:** the persistent website dashboard offers the same Add account flow to new and returning users, with Add more and Continue to chat after connection. Users may skip financial setup, retry incomplete setup, or add more without restarting onboarding.
- **Separate linked channels:** iMessage and WhatsApp require separately verified links through prepared messages opened by buttons. Matching contact details do not link or merge accounts. Each channel has its own history, context, jobs, tasks, and results; personal memory and financial connections are shared account-wide.
- **Chat and website responsibilities:** portfolio questions, current-channel task controls, personal memory, and proactive on/off happen in chat. Website controls manage financial connections, channel linking/disconnection, and preferred proactive routing. Chat links to those settings. Cross-channel task control and destination selection are deferred.
- **Text-first reporting:** answers, research summaries, scheduled results, and proactive messages lead with the finding, key numbers, and necessary explanation or evidence. Short paragraphs and bullets keep them readable in chat; follow-ups provide deeper detail without imposing a fixed word limit. Image replies are low priority; deep-research reports and polished website artifacts are deferred.
- **Wallet-control verification:** only a successful readable-message proof creates a verified EVM connection. Routine reads and monitoring then continue without daily signatures or an open wallet; disconnecting stops new reads.
- **Honest coverage:** answers use available information without inventing values or implying unsupported completeness. The website shows source availability, and unavailable data is distinct from a verified zero balance. Chat explains unavailable information when the user asks about it, without routine missing-data disclaimers.
- **Portfolio value:** the website shows a useful preview while other sources load; users request portfolio answers in chat. USD is the default display currency, with native quantities retained and alternate currencies low priority.
- **Consistent evidence:** provider data and reusable calculation definitions support previews, chat, reports, and scheduled work without a Phase 1 MyStacks indexer. Balance changes remain distinct from investment returns; exact supported calculations depend on available evidence.
- **Useful continuation:** chat stays usable during independent background work. The main agent may have five queued or running subagents it spawned per chat; scheduler-started runs are outside that delegation quota. Each chat can list, check, and cancel only its own jobs. Returned work lets the main agent continue reasoning and reply without another user message. Subagents cannot spawn children or change user settings. Stop acknowledgements report what is known; exact interruption mechanics remain open, and steering is low priority.
- **Flexible tasks:** clear supported requests create or manage informational finance tasks in their originating channel, within the minimum one-hour interval and five-enabled-task quota. Paused tasks do not count. Scheduled occurrences may run independently in parallel. Edits affect future runs; pause holds future runs and pending delivery, resume uses the next scheduled time without backlog, and cancel ends recurrence and requests cancellation of all its queued and running occurrences. Channel disconnection pauses its tasks; relinking requires explicit resume from that channel.
- **Scheduling:** detect and save device timezone once during onboarding. Users explicitly change their default in the web app or chat; a task-specific timezone affects only that task, and existing tasks keep their assigned zone unless edited. Confirm time and zone and clarify a missing preferred time. A known temporary scheduled-execution failure gets one retry; if the work still fails, the main agent explains it without cancelling recurrence or repeating identical notices.
- **Source changes:** after a financial source disconnects, a task continues only if remaining authorized data fulfills its request. Otherwise pause it and explain why once. Source restoration leaves it paused until explicit resume from its channel, using the next scheduled time without backlog. Temporary provider outages follow failure recovery.
- **Proactive control:** agent-initiated messages default to on with an account-wide chat on/off setting. An investigation requires this setting and a verified linked destination; turning it off also suppresses unsent proactive findings. The first linked channel becomes preferred, changed on the website. Disconnecting it switches proactive delivery to the remaining channel or pauses delivery if none remains, preserving the on/off setting. Scheduled tasks retain fixed channel delivery and do not follow that fallback.
- **Proactive cadence:** target approximately five randomized investigation starts between 9 AM and 9 PM in the user's saved timezone. Results may arrive after that window. Skip overlapping or missed checks; record investigation failures internally and wait for the next scheduled check.
- **Precision-first initiative:** portfolio evidence, goals, and remembered interests guide relevance. Send only meaningfully new findings supported by strong evidence that meet attention criteria; explain why they matter. Accept lower recall, suppress uncertain, minor, repetitive, and low-value findings, and stay quiet when nothing qualifies. Explicitly scheduled updates follow their own intent.
- **Automatic memory:** useful personal context is remembered and reused across linked channels when relevant. Users can inspect, correct, or forget it in any authorized linked chat; corrections and forgetting apply account-wide.
- **Memory updates:** clear new user statements update older facts automatically. Ask about unclear conflicts when they materially affect the answer, and keep assistant interpretations distinguishable from user-confirmed facts.
- **User control:** task changes, paused notifications, corrected memory, and disconnected sources must have clear effects. Disconnecting and deleting retained information are distinct actions.
- **Informational authority:** user instructions, remembered preferences, and new skills cannot expand Phase 1 financial authority.

## 4. Decisions to discuss by area

| Area | Product decisions still needed |
| --- | --- |
| Entry and account continuity | Supported sender identities and device handoff, verification mechanics, low-priority phone changes and recovery, and launch geographic scope. Authentication provider selection belongs to architecture. |
| Source connections | Supported wallet networks and types, EVM cross-chain proof policy, Hyperliquid wallet eligibility, visible permissions and provider-dependent coverage limits, and connection limits. |
| Financial meaning | Provider-supported metrics, price sources, performance and cash-flow formulas, risk methods, historical coverage, and claim-specific freshness within the agreed USD and evidence rules. |
| Conversation and analysis | Response-time expectations, research-source selection, global capacity, and exact in-flight cancellation within the five main-agent-spawned subagent limit per chat. Formats and artifact access for low-priority file/image capabilities remain later design work. |
| Tasks and initiative | Defined investigation scopes, evidence thresholds, recurrence/DST mechanics, repeat suppression, budget outcomes, transient-error classification and retry delay, and delivery mechanisms. |
| Memory and data controls | Selection and retrieval, retention, concurrent-write ordering, correction/forgetting completion mechanisms, and proposed export. Account deletion is deferred. |

The stories expose these choices with concrete user outcomes. Technology and rollout choices must not silently decide them.
