# Proactive task and delivery design

## 1. Scope and standing decisions

This design covers **Phase 1 digests, periodic risk checks, natural-language ongoing tasks, independent initiative, and notification controls**. The [user stories](../user-stories/tasks.md) own observable acceptance; the [requirements](../requirements.md) own product scope, and the [architecture](../architecture.md) owns shared execution boundaries.

**Status: accepted core Phase 1 task and proactive-message UX; technical design tentative pending the architecture round.** Accepted product behavior below constrains the implementation; logical records and execution mappings remain design proposals.

iMessage is the interface for saved task creation, management, results, and follow-up questions. WhatsApp supports user-initiated chat and one-off requested analysis/background work; its saved schedules, proactive tasks/reports, and template messaging are deferred. When asked to schedule from WhatsApp, explain the unsupported capability and direct the user to linked iMessage. WhatsApp cannot create or manage iMessage tasks or transfer work there. The [Apple messaging decision](../ADRS/0021-apple-messages-with-bird.md) owns this capability split and selects Bird as the Apple Messages for Business MSP, with Photon as a backup integration plan. The stable account owns task records, but conversations, current context, independent jobs, scheduled tasks, and results remain within their originating channel. Task tools expose only supported current-channel work; protected backend handlers enforce both account and channel authority. Personal memory, financial connections, and portfolio evidence remain account-wide under the [channel and memory decision](../ADRS/0008-channel-scoped-work-and-shared-memory.md).

Scheduled-task and independent-job results stay in their creating channel. Phase 1 chat cannot select another destination, transfer, or retarget requested work, including on an explicit user request. Website settings own channel connections. Website and supported chat controls expose the same account-wide **proactive insights** enabled/disabled setting. It applies only to eligible linked iMessage and is enabled by default subject to applicable channel permissions. WhatsApp cannot be selected, and linking WhatsApp does not enable proactive work. Chat replies and requested work retain their originating channel.

**Accepted:** standing requests and background run records persist outside workers; tasks remain informational and financially read-only; current permissions, task state, and destination are checked before publication. Requested tasks keep their agreed schedules. Proactive investigations target approximately five randomized starts per eligible account per day within 09:00–21:00 in the saved user timezone. Timing remains best effort, and missed events are accepted. High precision takes priority over recall for initiative, accepting missed marginal events to avoid spam.

**Agreed ownership, BullMQ with Valkey, completion recovery, and application hosting:** the shared [PostgreSQL database](../ADRS/0013-shared-postgresql-storage.md) uses a dedicated TimescaleDB-enabled Tiger Cloud service and owns saved task definitions, background run records, statuses, and results in ordinary application-owned tables. BullMQ owns timing, queue dispatch, claims, and configured job retries; Mastra executes agent work. Native BullMQ QueueEvents normally notifies the single active API/chat coordinator when background work completes; startup and periodic checks recover pending saved completions. BullMQ uses a new dedicated GCP Memorystore for Valkey instance through its Redis-compatible backend. Each eligible user-created scheduled occurrence starts one background agent run, and every eligible proactive check invokes a bounded agent investigation. Agents can compose authorized provider reads, backend web research, and E2B shell, file, Python, and JavaScript execution. The API/chat coordinator uses a Cloud Run Service with CPU available after HTTP acknowledgement; background consumers use a separate [Cloud Run worker pool](../ADRS/0017-cloud-run-worker-pool.md) with manual instance scaling and configurable execution limits. The [scheduling decision](../ADRS/0004-durable-scheduling-and-queued-execution.md#27-whole-job-recovery-and-shared-attempt-allowance) owns whole-job recovery. Channel scope does not require a separate runtime, queue, or deployment per channel. Record schemas, framework integration, recovery details, exclusive coordinator ownership during Cloud Run replacement, worker region and resources, Tiger Cloud and GCS configuration, exact Bird API/webhook and ownership integration, WhatsApp transport/staff integration, and exact execution limits remain open.

## 2. Durable concepts and ownership

### 2.1 Distinct records

| Concept | Responsibility |
| --- | --- |
| **Standing task** | The backend database retains stable account, creating channel, intent, current status, covered resources, and trigger. The creating channel fixes result delivery. Keep settings independent of any one run. |
| **Schedule** | The saved task defines requested recurrence and assigned timezone. The backend registers and updates the corresponding BullMQ timing state; account-level proactive timing follows section 4.5. |
| **Queue job** | BullMQ dispatches and claims work for a due occurrence or other authorized background request. The job refers to trusted backend run context rather than owning a second task definition. |
| **Background run** | The backend database retains original-request correlation, the instructions used when the run starts, account/channel binding, progress, evidence references, internal result, actual status, and cancellation requests separately from confirmed stopped execution. Saved completions retain pending/handled state for coordinator recovery. Retrying a job does not create another standing request. Requested work uses the shared two-attempt allowance in section 4.7; exact attempt accounting and schemas remain open. |
| **Delivery** | Record a proposed message, its eligibility decision, authorized channel binding, and dispatch outcome separately from successful analysis. Task results cannot be rebound to another channel. Proactive insights deliver only through eligible linked iMessage. |
| **Notification settings** | Retain the account-wide proactive insights enabled/disabled setting shared by website and supported chat controls. Disabling it stops proactive investigations and unsent delivery. Fixed task destinations remain separate. |
| **Proactive finding and notification history** | Retain account-level findings, supporting evidence, actual sent messages and times, and delivery outcomes separately from personal memory. Distinguish candidates and completed investigations from successful notifications and accidental retries. |

These boundaries do not require separate services or a separate database for every concept. Durable financial evidence stays in the [portfolio boundary](portfolio.md); conversation continuation and Mastra context follow the [runtime design](runtime.md).

### 2.2 Backend definitions and queue execution

Use **one shared background execution queue across accounts**, consumed by the common Cloud Run worker pool. Main-agent-delegated subagents have highest priority, user-created scheduled occurrences have normal priority, and proactive investigations have lowest priority. Normal foreground chat executes directly outside this queue. The [scheduling ADR](../ADRS/0004-durable-scheduling-and-queued-execution.md) owns this decision and its trade-offs.

Under the BullMQ baseline, the backend assigns an explicit priority to every job class through the native queue options; exact numeric values remain configuration details. Priority chooses among waiting jobs and does not interrupt active runs or reserve worker capacity. Several jobs can execute concurrently. Each run retains its own trusted context, permissions, admission rules, and retry policy regardless of queue sharing.

**Shared-capacity delay is accepted initially.** A chat-delegated job can wait while all worker slots are occupied, and sustained higher-priority demand can delay lower-priority work. If observed contention justifies reserved capacity, split queues and allocate worker capacity to them while reusing execution code and Valkey. Separate queue names alone do not reserve resources.

The **backend database owns saved task definitions and background run states and results**. The backend registers recurring schedules and updates BullMQ timing state from those definitions. BullMQ owns due-time production, queue dispatch, claims, and the retries configured for each job class. Mastra executes a claimed agent run; it does not independently schedule or retry the same queued operation.

The task-to-queue update contract must make failed updates observable without allowing independently editable task definitions in two stores. Detailed consistency and recovery implementation remain open within the whole-job policy in section 4.7. Valkey stores queue and schedule data; warm worker processes perform the work. Valkey does not start a stopped service; the selected Cloud Run worker pool supplies running consumer instances.

Use existing BullMQ scheduling infrastructure under this baseline. Its [Job Schedulers](https://docs.bullmq.io/guide/job-schedulers/) produce the next job when the preceding job begins processing; that behavior does not establish the application's per-account proactive overlap policy. A [custom repeat strategy](https://docs.bullmq.io/guide/job-schedulers/repeat-strategies) or next-due timing may support randomized starts, but the exact integration requires verification. No separate custom scheduler service or legacy `QueueScheduler` is selected.

The [scheduling decision](../ADRS/0004-durable-scheduling-and-queued-execution.md#22-initial-bullmq-baseline-and-shared-postgresql-records) owns BullMQ's baseline status and the conditions for considering DBOS. DBOS remains a future alternative outside the current implementation scope.

### 2.3 Worker capacity and lifecycle

Use the same backend codebase with distinct API/chat and worker entrypoints and deployments; they may reuse a container image. The worker pool has no HTTP ingress and initially runs one or two container instances, with the exact initial count still to be configured. Adjust the count manually as needed. **Pool instance count and application worker job concurrency are separate controls**, independent of the per-chat admission quotas. Neither setting alone establishes user capacity. The API/chat entrypoint uses a Cloud Run Service with instance-based billing so CPU remains available after HTTP acknowledgement. The single active coordinator remains required; exclusive ownership during Cloud Run replacement or possible instance overlap is unresolved, and an instance limit alone does not establish it.

The [worker-pool decision](../ADRS/0017-cloud-run-worker-pool.md) owns configurable execution limits, duration/model-usage/outcome records, capacity tuning from queue and resource usage, idle-instance billing, startup and replacement delays, and the shutdown contract. Exact limits remain provisional; per-user spending budgets are deferred. The shutdown warning cannot guarantee completion of an expected 5–10-minute run. A managed instance lifecycle is distinct from a BullMQ job lifecycle. Section 4.7 defines whole-job recovery; exact shutdown mechanics, BullMQ attempt and stalled-job accounting, and duplicate-result handling remain open within that policy.

The shared API or worker process runs the Mastra agent loop. If an execution attempt needs shell or code, it lazily creates one E2B sandbox and reuses its files across successive calls during that attempt. Other runs, including concurrent occurrences for the same user, own separate sandboxes. PostgreSQL holds task/job records, small structured results, and file metadata/references; private Google Cloud Storage holds useful retained datasets/workspace files. Save useful provider inputs actually used, reusable calculations, final results, and supporting evidence before sandbox destruction, subject to provider data rights. A later authorized run may restore chosen files into a fresh sandbox without inheriting processes or interpreter state. Automatic pruning is deferred under the [analysis retention decision](../ADRS/0023-analysis-data-retention-and-object-storage.md); the [runtime design](runtime.md#52-e2b-execution-and-checked-results) owns execution and scoped transfers. Retention does not make old evidence current or create a continuous history archive.

## 3. Task creation and logical lifecycle

### 3.1 From language to a standing request

Mastra interprets an ongoing request and uses an authorized task tool to read or change structured state. After the orchestrator verifies the channel sender, trusted backend context binds the stable account and current channel/thread. Model-provided identifiers do not establish access or choose the channel. Protected handlers validate account and channel ownership, covered resources, and supported trigger values. The runtime receives authorized context without needing to interpret the channel's sender identity. The shared regular `Agent` receives fresh trusted per-run `RequestContext`; the [runtime design](runtime.md) owns history and memory integration.

When a request is clear and supported, create the task immediately and confirm its purpose, chosen time, and timezone in the creating channel. Website onboarding detects and saves the device timezone **once** as the personal default. The app does not continuously detect timezone or track travel; redetection on later website visits is deferred. The user can explicitly change the personal default in the web app or chat. A timezone named in a task request applies to that task without changing the personal default. A changed default applies to new tasks; existing tasks keep their assigned timezone unless explicitly edited.

Backend scheduling tools admit user-created schedules only from iMessage and enforce a configurable **one-hour minimum interval** for every user-created recurring schedule in Phase 1. If a user requests a shorter interval, explain the limit and offer hourly without silently replacing the requested schedule. Normal chat and explicitly requested one-off work are unaffected. This minimum does not assert that every provider refreshes its data hourly.

Each iMessage chat may have **at most five enabled user-created recurring tasks**. Paused tasks do not consume this saved-schedule quota. Backend scheduling tools enforce it when creating, enabling, or resuming a task; when it would be exceeded, explain the capacity limit instead of enabling the task. This quota is separate from background execution admission.

Ask for the timezone when unknown; for “every morning,” ask for a time if no morning time is known. Resolve other material ambiguity in intent, timing, or source coverage before making the change. Memory can help interpret personal preferences, but it does not hold copies of task records, results, transcripts, or financial evidence and does not establish delivery authority. Unsupported work remains visibly unsupported.

Daily digests, risk checks, and initiative use shared execution and delivery boundaries while keeping their distinct admission, timing, and failure policies. Each qualifying proactive insight can reach **eligible verified linked iMessage** after one account-level investigation. A clear website or supported chat change updates the same proactive insights setting immediately. Disabling it prevents future investigations and unsent findings. Disconnecting iMessage prevents delivery without falling back to WhatsApp. An independent finding is not authority to expand financial access or notification permissions.

Users list and inspect only current-channel tasks in chat, including purpose, schedule, and active or paused status. Clear requests to change, pause, resume, or cancel a task apply immediately and receive a concise confirmation; an ambiguous task reference requires clarification.

### 3.2 Independent jobs and chat controls

For substantial work, the main agent explicitly starts background subagents, receives accepted job IDs, and ends its foreground turn after any useful acknowledgement. It does not occupy the channel while waiting for completion. New questions and job-status requests can proceed in later turns while background work continues. Each job receives its own context, authorized account resources, and originating-channel binding; ordinary new messages do not silently steer it.

The configurable initial admission limit is **five outstanding subagent runs spawned by the main agent per chat**, counting queued and running runs. Terminal jobs do not count. If five main-agent-delegated runs are outstanding, the assistant reports capacity instead of accepting a sixth. Scheduler-started requested occurrences and proactive investigations are excluded. A later new subagent spawned by a main-agent continuation counts as main-agent delegation, including when that continuation follows scheduled work. Saved recurring task definitions follow the separate enabled-task quota in section 3.1.

Only main-agent turns can delegate additional subagents; the scheduler can start the runs defined by configured schedules. Backend capability checks and the subagent tool subset enforce one level of delegation. Background subagents retain useful authorized read, research, and code-execution tools plus shared personal-memory read access. They cannot change settings, connections, personal memory, or saved user tasks, start nested subagents, or send user messages directly.

From the originating channel, the user can list its jobs, ask for status, and request cancellation of a selected job. The backend records the cancellation request, cancels waiting work, and requests that a running worker stop through native SDK mechanisms where available. Chat acknowledges the request promptly and confirms stopped execution or terminal cancellation only when known. In-flight provider requests may finish and incur cost. The request suppresses unsent result delivery, including late completions; a message already submitted to a provider may not be recallable. Status remains queryable without a mandatory second routine notification. Exact statuses and abort mechanisms remain implementation details. **Steering a running job is low priority and deferred.** Changing standing-task settings is distinct from steering an active attempt.

A job and its results retain their originating-channel binding. Channel disconnection does not authorize transfer or an invented cancellation outcome for a one-off job or active task attempt.

Original-request correlation supports routing, status, cancellation, and admission. The main agent uses channel context and actual job-status tools to decide whether the user's request is answered. A separate overall-request lifecycle, parent completion flag, or mandatory dependency graph is not part of this design; saved recurring tasks and their individual runs retain their own lifecycle.

### 3.3 Logical state transitions

**Proposed lifecycle vocabulary:** active, paused, and cancelled standing tasks; eligible and claimed jobs; running, completed, failed, cancelled, interrupted, or skipped attempts; pending, held, suppressed, dispatching, sent, failed, or uncertain deliveries. Exact persisted states remain a schema decision. Completion, failure, and cancellation are the user-visible terminal job outcomes; section 4.7 governs recovery after interruption.

- Creating a task allows future runs. Pausing retains its standing intent, stops future runs, and holds automatic results whose sending has not begun. Resuming continues at the next scheduled time without a missed-update backlog.
- Editing a task changes future runs. An active run continues its original instructions unless explicitly cancelled, while current financial permissions, channel validity, pause/cancel state, and delivery authority remain enforced. A future-only edit does not itself invalidate the active attempt; the instruction snapshot does not select a schema or versioning mechanism.
- Cancelling ends recurring work and records cancellation requests for all queued and running occurrences of that task. Suppress unsent results from those occurrences, including late completions, while retaining the actual execution outcome separately from the request. Useful past results remain available within their channel under the conservative retention policy and provider data rights; automatic pruning is deferred.
- Disconnecting a channel pauses its scheduled tasks, future runs, and pending unsent automatic results without fallback. Relinking the same channel keeps tasks paused until an explicit resume from that channel. Already-started sends cannot be recalled; active attempts retain honest cancellation and outcome semantics.
- Explicitly disconnecting a financial source allows a task to continue only if remaining authorized data still fulfills its intended request. Otherwise, pause the affected task and explain why once in its originating channel. Reconnecting the source leaves the task paused until the user explicitly resumes it from that channel, at the next scheduled time without a missed-check backlog.
- A temporary provider outage is distinct from explicit disconnection. An isolated provider failure remains eligible for automatic recovery and does not automatically cancel the task.
- Attempt success makes a result available; it does not prove delivery. An unavailable provider response or interrupted worker must not become a successful result or a zero balance.

Task pause, human conversation ownership, proactive insights, source disconnection, and worker shutdown affect different responsibilities. Chat must show their actual effects rather than collapse them into a single success state. Under the [conversation ownership decision](../ADRS/0022-human-support-conversation-ownership.md), Bird Conversations is the Apple staff UI and the backend enforces native ownership and explicit staff handback. Human takeover pauses automated replies and reports while requested analyses and user-created schedules continue and save results. A new inbound message does not resume AI. Proactive investigations do not start while automated delivery is unavailable; running findings wait for explicit handback and renewed usefulness/eligibility checks. Human takeover alone does not cancel or restart work.

### 3.4 Independent requested occurrences

Each eligible occurrence of a user-created schedule starts **one background agent run**, admitted independently of the main-agent delegation quota. Do not check whether the same task's previous run is queued or running. Distinct occurrences can run in parallel: overlap does not skip, replace, defer behind, or cancel either run. Do not add previous-run queries, overlap locks, or leases to prevent distinct occurrences from running together. Duplicate handling for the same occurrence remains a separate responsibility.

Accepting an eligible due occurrence means admitting it to the execution system; actual worker start depends on available capacity. Current pause/cancel state, verified channel, financial authority, and normal lifecycle checks still apply. This does not establish exact-time execution, exactly-once behavior, outage catch-up, or unlimited workers. Native schedule-production behavior requires integration verification without a bespoke scheduler or replay engine.

Expected execution of around **5–10 minutes**, compared with the one-hour minimum recurrence, is an operating assumption rather than a timeout or guarantee. An unusually long run may overlap the next occurrence, and both remain valid. Proactive investigations retain their separate one-active-per-account and skipped-overlap policy.

## 4. Execution and publication

### 4.1 Queued work and main-agent completion

1. The backend registers recurring work or accepts an authorized background request. BullMQ makes due work available and a warm worker claims its queue job. Queue eligibility does not guarantee an exact start time.
2. The worker resolves trusted account, channel, original-request, job, and run references, checks current authority and applicable task state, and binds protected reads to that user and authorized objects through backend-controlled credential brokering or the user-bound backend read API. Proactive work must pass the actual-start checks in section 4.5 before investigation.
3. Each eligible user-created scheduled occurrence executes one background Mastra agent run. It can use authorized provider APIs, backend research, and E2B shell, file, and code tools as needed. Requested one-off work retains its ordinary execution path. Every eligible proactive check runs a bounded agent investigation.
4. The worker saves progress, evidence, the internal result or references, and the actual run outcome in PostgreSQL **before completing the BullMQ job**, with pending/handled state for saved completion processing. A result can be findings or data rather than a finished report. Native BullMQ [QueueEvents](https://docs.bullmq.io/guide/events/) supplies the completion notification; PostgreSQL remains authoritative for the run state and result.
5. The single active API/chat coordinator subscribes to QueueEvents, resolves trusted routing and result references from stored run records, and submits completion through the same channel handler used by inbound chat. Requested work uses its originating channel; proactive findings are eligible only for linked iMessage while proactive insights are enabled. An idle AI-owned channel starts a **new main-agent turn**; a busy or human-owned channel retains completion instead of injecting it into current inference or sending a report. On explicit staff handback, the main agent assesses pending results with correct timestamps and current evidence; proactive findings also require continued usefulness and eligibility. Fresh input includes the original request, result or references, and current permitted channel context.
6. The main agent owns every agent-authored user reply. It can use financial tools or its own lazily created E2B sandbox, combine completed children, delegate further top-level work, reply, or end quietly while awaiting another completion. It reads authorized saved child outputs rather than inheriting a child's live workspace. Completion supplies internal work, not a new user instruction or added permission. It does not resume a suspended model call or require a polling model loop.
7. Before each send, the delivery boundary rechecks current permissions, task state, cancellation requests, channel validity, native AI conversation ownership, provider sending restrictions, the proactive insights setting where applicable, and delivery authority. A cancellation request suppresses unsent results even if the worker finishes later. Task results remain bound to their creating channel. Each actual main-agent reply enters only its destination channel's normal history for follow-up questions.
8. Save delivery outcomes separately from investigation success. A proactive history entry records its iMessage notification as sent only when that outcome is known; candidates, failure, uncertainty, and accidental retries remain distinct. Section 4.7 governs provider-supported duplicate prevention and uncertain submission.

The [channel-turn decision](../ADRS/0009-channel-turns-and-background-subagents.md) owns the single active backend chat coordinator and the completion-event trade-off: channels run concurrently with one foreground main-agent turn per channel, and user messages and background completions enter the same channel handler. The [runtime design](runtime.md) owns continuation details. Alongside normal QueueEvents wakeups, the coordinator checks pending saved completions on startup and periodically, resolving trusted routing and passing them through the same ordered channel handler with current authorization, cancellation, and delivery checks. Empty checks invoke no model; recovery reuses saved research. Exact record schema, sweep interval, handled boundary, crash behavior, and duplicate handling remain open. This does not guarantee exactly-once main-agent turns or replies.

Normal chat initially runs directly in the backend after inbound verification, persistence, and prompt transport acknowledgement; it does not use a durable BullMQ chat queue. Simple stop/start deployment accepts brief interruptions. Process or deployment interruption may leave an acknowledged turn without a reply. Saved messages alone do not resume inference. Background run persistence does not extend that guarantee to ordinary chat.

### 4.2 Requested checks and evidence reuse

Scheduled agent runs may use **programmatic tool calling** to compose backend reads or provider reads through credential brokering with calculations. E2B code can loop, paginate, and make concurrent reads without a model round trip for each intermediate request; the Mastra agent loop remains in the backend, and this pattern does not require a particular model vendor's API. These reads and calculations do not replace the occurrence's agent run. Proactive checks always invoke an agent after eligibility; Phase 1 has no cheaper data-change prefilter or rule-trigger prerequisite for that invocation. Public market observations may still be collected once and reused when their freshness and coverage satisfy each claim. Reuse must retain source and as-of evidence; it must not turn an old observation into a current one.

Private account evidence remains user-authorized. A shared public price does not establish account access, portfolio membership, or permission to share private results. The [portfolio design](portfolio.md) owns evidence boundaries and claim-specific reuse. Under the [credential decision](../ADRS/0002-backend-owned-financial-credentials.md), raw provider credentials remain outside E2B. **Credential brokering** uses the native egress proxy to inject authentication outside the VM where supported; a user-bound backend read bridge handles incompatible authentication, including SnapTrade Commercial HMAC signing. The backend controls the user credential, permitted destination, read operations, and account or object scope. Application-wide authority and OAuth refresh handling remain backend-owned; an external vendor secret store or proxy may handle provider credentials outside the VM. Raw credentials stay out of sandbox code and files, prompts, skills, job inputs, persistent model memory, and traces. A narrow run authorization or opaque placeholder may be present in code; its mechanism remains open. Sandbox code receives and may disclose the user's authorized data, an accepted necessary trade-off for analysis. Cross-user data or credential access is forbidden.

Current portfolio analysis and account-specific proactive conclusions request the latest relevant provider evidence at analysis time, allowing brief appropriate reuse under the [current-evidence decision](../ADRS/0019-current-portfolio-evidence.md). Account-state freshness is separate from market-price freshness; applying a fresh price to old holdings does not establish current exposure. Source-data time remains separate from retrieval time. If timely account evidence is unavailable, proactive work avoids conclusions that depend on current exposure; requested tasks provide supported results with concise material limitations. Delayed evidence can still support bounded historical or reporting claims. Exact maximum ages and reuse windows remain open.

Approximately five daily proactive checks remain periodic detection, not continuous monitoring. Provider polling and permitted-use constraints must be reconciled with that cadence, hourly requested schedules, and chat under the [provider decision](../ADRS/0018-managed-financial-data-providers.md) and [integration TODO](../TODO.md#3-financial-provider-integration). They do not silently change the accepted frequencies or authorize stale evidence for current claims. Scheduled, proactive, and chat work use the same trusted financial connectors, including on-demand Hyperliquid REST reads through Webshare at low priority.

### 4.3 Low-noise notification eligibility

An eligible message must be in scope, supported by sufficient evidence for its claim, useful under the task's intent or initiative policy, and allowed by current notification settings. Unknown data cannot support an “all clear” claim. Evidence retains unavailable sources and uncertainty; useful partial answers describe their actual scope without routine missing-data warnings and explain material limits on the requested conclusion concisely.

**Accepted initiative policy:** judge relevance flexibly using the user's connected portfolio, goals, and remembered interests. Send only a meaningfully new and useful finding supported by strong evidence and worth the user's attention, with a concise explanation of why it matters. Prioritize high precision over recall, accepting missed marginal events to avoid spam. Suppress uncertain, minor, repetitive, or low-value findings; stay quiet when none qualifies. Resurface a finding only after an important change or new useful evidence.

**Explicitly scheduled work follows the user's request and its own controls.** The initiative attention filter must not suppress requested task results; send an explicitly requested daily summary or digest even on quiet or no-change days. Internal eligibility policies do not add user-facing fewer/more settings.

The main agent judges semantic usefulness and meaningful change from evidence. The backend enforces eligibility, authorization, recognized duplicate-delivery handling, and delivery policy. Architecture and evidence must establish exact attention and material-change thresholds, claim-specific and provider freshness rules, precision measurement and any numeric target, and detailed repeat handling. No numeric precision target, perfect semantic deduplication, or exactly-once external delivery is guaranteed.

Monitoring, data access, model work, generated-code analysis, and delivery use configurable execution limits under the worker-pool decision. Exact values remain provisional, and exhaustion behavior remains open: defer eligible work, produce a useful partial result, or record a visible failure are candidate outcomes. Per-user spending budgets are deferred.

### 4.4 Text-first results

All replies and reports, including task updates, are **text-first, concise, precise, and readable in chat**. Give the main finding, key numbers, and reasoning needed to understand the result; follow-up questions can deepen the analysis. This presentation keeps substantial calculations, research using available sources, and background jobs in scope. Image replies are low priority; deep research reports and polished web artifacts are deferred.

### 4.5 Proactive eligibility and randomized starts

Each proactive investigation has a defined financial scope. The exact scope catalogue, metrics, provider calculations, and attention thresholds need research; these scopes do not limit the finance-related jobs a user can request. Every eligible check runs an agent investigation under configurable execution limits whose exact values remain provisional.

Before scheduling an investigation, the backend requires enabled proactive insights and verified linked iMessage that is currently eligible for automated delivery. When queued work actually starts, the backend rechecks those conditions and current account authority. Human ownership makes automated delivery unavailable, so skip proactive starts while that condition holds. **Disabling proactive insights suppresses future investigations and unsent proactive messages**, including results from an investigation already running. Requested analyses and user-created schedules continue during human takeover and save results while reports wait for explicit handback; their other controls remain in force.

Target **approximately five investigations per eligible account per day**, randomly spaced within **09:00–21:00 in the saved user timezone**. Times vary by user and day or occurrence rather than using fixed daily cron times, spreading load across accounts. This is a configurable product default, not an exact daily quota or a user intensity setting. Exact randomized timing and daylight-saving mechanics require integration verification; no jitter range or algorithm is selected. If the timezone is unknown, obtain it before using a local start window.

The window governs **actual investigation starts only**. A queued occurrence cannot begin an investigation outside the window. Work starting at 20:58 may finish and send at 21:03, subject to the usual settings and authority checks; finishing after 21:00 does not itself hold or suppress its message.

Only **one proactive investigation per account** may be active. Skip an overlapping occurrence, and do not build a missed-occurrence catch-up backlog after downtime. Scheduler-started proactive runs are excluded from the per-chat main-agent delegation quota; the proactive per-account rule still applies. The backend's exact cross-worker enforcement and randomized next-due integration remain implementation decisions.

### 4.6 Proactive evidence, history, and completion

The investigation receives its defined scope, authorized account evidence, permitted context, shared personal-memory read access, and account-level proactive finding and notification history. Its tool subset must preserve useful provider reads, backend web research, and E2B shell, file, and code execution while preventing settings, connection, memory, and saved-task mutation, nested delegation, and direct user messages. The same credential-brokering and user-bound backend read boundary applies as in section 4.2. E2B uses default-deny egress with backend-controlled required-provider access; general web research remains in backend tools.

Store proactive history **separately from personal memory**. Record what was actually sent to iMessage, when, and the supporting finding and evidence, while retaining candidates, internal results, and failed or uncertain deliveries as distinct outcomes. Distinguish sent messages from accidental retries. Later investigations can assess meaningful change and repetition after proactive insights are disabled and enabled again. This account-level history does not copy channel transcripts or user tasks into shared memory.

If no finding qualifies, remain quiet. A candidate returns internal evidence through the completion path in section 4.1; main-agent continuation decides whether and how to respond within the defined financial scope and original read-only proactive purpose. One account-level investigation supplies the finding for eligible verified linked iMessage. Completion grants no new user authority. Before each eventual send, the backend rechecks proactive insights, native AI conversation ownership, eligibility, channel validity, and delivery authority. A result saved during human takeover cannot interrupt support; after explicit staff handback, the main agent considers it only if still useful and eligible, with correct timestamps and current evidence. Exact pending-completion and dispatch mechanics remain open within these checks and channel context boundaries.

### 4.7 Execution failures and delivery boundaries

The [scheduling decision](../ADRS/0004-durable-scheduling-and-queued-execution.md#27-whole-job-recovery-and-shared-attempt-allowance) owns whole-job recovery. Deployments stop old application processes and start new ones while independently hosted PostgreSQL and Valkey retain their state. Use native BullMQ shutdown, reconnection, and stalled-job recovery: waiting jobs remain queued, and eligible interrupted requested work follows the shared attempt allowance. Deployments need neither an empty queue nor a script that recreates every pending job.

Every user-requested background job, including a one-off job or one scheduled occurrence, has **at most two total execution attempts**. If a worker interruption leaves analysis unfinished, restart the whole job **from the beginning** only while it remains active and authorized and an attempt remains. The interrupted attempt counts. If shell or code is needed, the new attempt creates a fresh E2B sandbox. Work with a cancellation request or without current authority does not restart. Phase 1 does not checkpoint or resume inside agent, model, tool, or live-workspace steps.

A user-requested **scheduled execution** receives **one automatic retry for a known temporary failure** within that same allowance. An interruption restart and a temporary-failure retry cannot produce a third attempt. BullMQ owns whole-job retries; inner tool or SDK retries must have a distinct scope. Exact temporary-failure classification and retry delay remain open. After exhaustion, return the failure to the main agent for a concise explanation, avoid repeated identical notices, and keep the recurring schedule enabled.

For non-interruption errors in one-off background jobs, retry eligibility remains open within the two-attempt ceiling. Foreground chat and message transport have separate policies. Reuse completed analysis results for completion handling and delivery; a completion-event or message delivery failure must not rerun successful research or calculation.

If a proactive investigation fails or is interrupted, **record the outcome internally and wait for the next scheduled check**. Do not automatically retry the whole investigation or send a routine user failure message. A delivery failure must not rerun the investigation. Definitive delivery-failure retry details remain open.

Use provider-supported idempotency, deduplication, or delivery-status checks where available. If submission remains ambiguous after a timeout, record uncertainty and do not blindly resend automatically. Keep the result available when the user asks; an occasional report may not arrive automatically. Delivery failure or uncertainty never reruns completed analysis.

Exact BullMQ attempt and stalled-job accounting, native abort mechanisms, and duplicate-completion handling remain open within these limits. The two-total-attempt ceiling includes temporary-failure retries and interruption recovery; configuring `attempts: 2` alone does not establish that all native stalled-job paths meet it. Execution and delivery do not promise exactly once.

### 4.8 Concrete scheduling examples

| Situation | Result |
| --- | --- |
| An eligible account reaches a randomized 14:26 check. | The backend rechecks eligibility and starts a bounded agent investigation. No useful finding means silence; a supported candidate wakes a new main-agent turn that can inspect further evidence and compose the final reply. |
| A proactive investigation starts at 20:58 and its main-agent continuation is ready at 21:03. | Sending through eligible iMessage is allowed after proactive insights, AI conversation ownership, and authority checks. The start window does not hold the result until morning. |
| A user disables proactive insights before a queued check starts, or while an investigation runs. | The first case starts no investigation. The second suppresses all unsent proactive messages. The user's requested daily digest continues under its own controls. |
| iMessage and WhatsApp are linked when an investigation finds a qualifying insight. | Investigate once for the account and deliver only through eligible iMessage while proactive insights are enabled. WhatsApp linking does not enable proactive work. |
| A user disables proactive insights or disconnects iMessage while a proactive message is pending. | Do not send that pending insight or fall back to WhatsApp. Requested schedules follow their separate controls; channel disconnection pauses them until explicit resume after relinking. |
| A check becomes due while another proactive investigation for that account is active, or several occurrences are missed during downtime. | Skip the overlap and retain no missed-occurrence catch-up backlog. The next normal eligible check can run. |
| A proactive provider read fails; separately, a user-requested daily digest has a known temporary execution failure. | Record the proactive investigation failure internally and wait for its next check. Retry the requested digest once; if it fails again, the main agent gives a concise failure explanation and the schedule stays enabled. Delivery failure does not rerun successful research or calculation. |
| Nothing meaningfully changes after a prior proactive notification, but an explicitly requested daily summary is due. | Account-level proactive history supports silence on the repeated finding. The requested summary still arrives and may plainly report no change. |
| A user asks for an update every 15 minutes. | Explain the one-hour minimum and offer hourly. Create the hourly schedule only after the user accepts it; normal chat and one-off work remain available. |
| A chat has five enabled schedules and one paused schedule. | A sixth enabled schedule is refused. The paused task consumes no quota; resuming it requires an enabled slot, which can be freed by pausing an enabled task. |
| Five main-agent-spawned jobs are queued or running when a saved schedule becomes due. | Admit the scheduled occurrence independently and start its one agent run when worker capacity is available. A new child later delegated by the main-agent continuation must pass the main-agent quota. |
| An hourly task's 09:00 run is still active when its 10:00 occurrence becomes due. | Admit the 10:00 run without checking the 09:00 run's status; both may continue in parallel. Such duration exceeds the expected 5–10 minutes but is permitted. |
| A requested scheduled occurrence has a temporary failure, then succeeds on its retry. | Use at most two execution attempts for that occurrence and pass the successful result through normal main-agent continuation. The next scheduled occurrence remains enabled. |
| A worker is interrupted during the first attempt of an active, authorized one-off job. | Restart the whole job from the beginning as its second and final attempt, without resuming an individual agent, model, or tool step. |
| A scheduled occurrence has a temporary failure, then its retry is interrupted. | Both attempts are consumed. Do not start a third; the main agent gives a concise failure explanation and the recurring schedule stays enabled. |
| A worker stops after saving a completed analysis result, before delivery. | Recover the pending saved completion on coordinator startup or a periodic check and pass it through the ordered channel handler with current checks. Reuse analysis; record any uncertain send without blindly resending. |
| A user requests cancellation while an investigation is running, then a late result arrives. | Acknowledge the request promptly, suppress its unsent result, and confirm stopped execution only when known. A provider request already in flight may finish. |
| A requested job has a cancellation request or loses required authority before interruption recovery. | Do not restart it. Retain its actual outcome and current authority rather than infer that execution stopped when cancellation was requested. |
| A proactive investigation is interrupted. | Record the outcome internally and wait for the next scheduled check without retrying the whole investigation. |
| Staff take over while a requested analysis runs or an iMessage schedule becomes due. | Continue requested work and save results; automated reports wait. New inbound messages do not resume AI, and takeover alone does not cancel or restart work. |
| A proactive check becomes due during human takeover, or a running investigation produces a finding. | Skip the new investigation. Keep an existing finding from interrupting support; after explicit staff handback, the main agent considers it only if still useful and eligible. |
| A user requests a saved schedule in WhatsApp. | Explain that WhatsApp schedules are unsupported and direct the user to linked iMessage; do not create or manage iMessage work from WhatsApp. One-off requested work remains supported. |
