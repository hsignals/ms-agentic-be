# Assistant and Memory Technical Design

## 1. Status and design boundary

**Status: tentative Phase 1 technical design, pending the overall design round.** The [requirements](../requirements.md) own product outcomes; the [architecture](../architecture.md) owns shared execution boundaries. The recorded framework direction uses Mastra's regular `Agent`, fresh trusted `RequestContext` for each run, durable account-scoped state, and E2B for remote shell, files, and code execution. **BullMQ uses a dedicated GCP Memorystore for Valkey queue store; pinned versions and integration validation remain open.** One PostgreSQL database for application and Mastra state, with separate tables, uses a dedicated TimescaleDB-enabled Tiger Cloud service under the [shared PostgreSQL decision](../ADRS/0013-shared-postgresql-storage.md); its plan, region, size, and backup configuration remain open. A Cloud Run Service with instance-based billing hosts API/chat, and a separate [Cloud Run worker pool](../ADRS/0017-cloud-run-worker-pool.md) hosts background consumers with manual scaling. Exclusive coordinator ownership during Cloud Run replacement, GCP project, region, exact resource configuration, models, schemas, and unresolved policies remain open.

The design supports [assistant stories US-CHAT-01–07](../user-stories/assistant.md) and [memory stories US-MEM-01–04](../user-stories/memory.md). Phase 1 permits financial information, analysis, concise reports in chat, memory, informational tasks, and staffed human support; it excludes specific buy, sell, or rebalance recommendations and financial execution.

**Phase 1 is text-first, with iMessage as the priority channel.** iMessage supports chat, one-off analysis/background work, user-created schedules, and proactive reports. WhatsApp supports user-initiated chat and one-off requested analysis/background work; WhatsApp schedules, proactive reports, and template messaging are deferred. Available-source research, significant calculations, E2B execution, and background jobs support concise results in chat. Image replies are optional later work at low priority. Extensive deep-research reports, polished webpage artifacts, full report pages, and long-form report exports are deferred; Phase 1 has no separate web chat or report experience. User-supplied file analysis remains low priority. The [Apple messaging decision](../ADRS/0021-apple-messages-with-bird.md) owns the capability split and Bird MSP selection.

The [channel scope and shared memory ADR](../ADRS/0008-channel-scoped-work-and-shared-memory.md) owns the accepted product boundary: personal memory and financial connections are account-wide; conversation history, compaction, jobs, scheduled tasks, and results belong to their originating channel.

The [channel turns and background subagents ADR](../ADRS/0009-channel-turns-and-background-subagents.md) owns the accepted Phase 1 decisions for one active API/backend chat coordinator, direct chat execution, ordered channel turns, simple stop-and-start deployment, native completion notifications, main-agent replies, and one-level background delegation. These decisions and the worker-pool decision constrain the remaining framework and deployment mappings below.

## 2. Trusted entry and agent execution

### 2.1 Run identity and context

- The MyStacks orchestration layer authenticates a verified channel sender, resolves its stable account and channel conversation, and authorizes that mapping before invoking the runtime. Launch channels are iMessage and WhatsApp; future SMS channels remain separate channel integrations.
- Each invocation receives a **fresh trusted `RequestContext`** and authorized account, current channel, and conversation thread bindings. Background execution resolves its account, originating channel, and current permissions through trusted durable state.
- Model arguments, uploaded content, message text, and queued identifiers cannot establish or replace the account or channel binding. Resource and thread IDs identify state; they do not authorize access. Server-owned context keys are populated only after the binding is authorized.
- Shared agent definitions contain common instructions and capability registration. Private run data must not live in shared mutable agent fields or a shared private-file workspace.

The orchestrator authorizes delivery separately from the runtime's memory binding. Jobs and supported scheduled tasks keep their originating channel as their fixed destination in Phase 1. Under the [task design](tasks.md), the account's **proactive insights** setting enables or disables eligible linked iMessage delivery, enabled by default subject to applicable channel permissions. WhatsApp cannot receive proactive insights, and linking it does not enable them. Disabling proactive insights suppresses future investigations and unsent findings. Chat replies retain their current channel; a login phone number does not implicitly select a thread or destination. The same shared runtime serves linked channels without a separate VM, queue, or runtime deployment per channel, and without requiring Mastra to interpret provider sender identities. Bird carries Apple Messages for Business messages for MyStacks' own account through native APIs/webhooks; iMessage is the product shorthand. Photon is a backup integration plan, without automatic failover or assumed thread migration. Exact Bird product/API version and configuration, WhatsApp adapters, runtime interfaces, and concrete context fields remain open.

### 2.2 Native history and context

**Tentative mapping:** pass trusted account and conversation IDs through Mastra's `memory: { resource, thread }` execution options. Mastra defines resources as owners and threads as conversations, and its native memory loads stored history and persists new messages. Prefer that flow over assembling a second history in the orchestrator. See [Mastra message history](https://mastra.ai/docs/memory/message-history) and [agent execution with memory](https://mastra.ai/reference/agents/generate#with-memory).

The orchestrator owns authenticated routing and authority; Mastra owns the configured history loading, context assembly, persistence, and compaction within those authorized scopes. Each channel's context combines the **account-shared structured personal profile, recent same-channel raw history, a compact summary of older same-channel history, and relevant request or job inputs**. Mastra's native Observational Memory supplies channel compaction under the [native context decision](../ADRS/0010-native-channel-context-compaction.md). Phase 1 does not select vector recall or cross-channel history search. Exact token budgets and compaction models remain open; section 6 owns the memory details.

### 2.3 Skills, tools, and authority

The runtime uses Mastra's native agent, skill, tool, and context facilities. Curated skills guide reasoning and can supply provider SDK/API documentation; registered tools expose trusted backend operations, web search and page reading, and the E2B execution workspace. Through **programmatic tool calling**, generated programs compose broad authorized provider SDK/API reads with shell, file, Python, and JavaScript tools instead of needing a bespoke tool for each analysis. Programs can use loops, pagination, concurrency, filtering, and calculations without sampling the model after each read. Model-directed commands and code execute only in E2B, while the Mastra reasoning loop stays in the shared API or worker process. E2B does not host the full agent. The [agent capabilities ADR](../ADRS/0006-composable-agent-capabilities.md) owns the capability rationale; prompts and skills cannot grant permissions.

Programmatic tool calling names the architectural pattern, rather than selecting a model or enabling a vendor-specific API feature. [Claude's documentation](https://platform.claude.com/docs/en/agents-and-tools/tool-use/programmatic-tool-calling) describes one vendor implementation; the MyStacks contract remains shared Mastra orchestration with programs executing in E2B.

Protected tool handlers or the financial tools API authorize the current user, account, and object on every protected path. Job and task tools expose only current-channel work, and backend handlers enforce both account and current channel for reads, writes, and result access. Channel ownership is server-bound rather than a model argument; prompts and capability registration do not replace these checks. Shared personal memory uses validated account-scoped backend operations.

Chat controls cover supported current-channel jobs and tasks, shared personal memory and preferences, and the proactive insights setting. Supported chat controls and the website update the same account setting. Backend scheduling tools admit schedules only from iMessage. When asked to schedule from WhatsApp, explain the unsupported capability and direct the user to linked iMessage; do not create, manage, transfer, or retarget iMessage work from WhatsApp. WhatsApp one-off requested work remains supported under normal provider sending restrictions. The website owns financial connections and channel linking and disconnection. Chat can explain those website controls and link to them; it cannot transfer work or change channel links. Proactive insights do not select a destination for chat replies or user-requested work.

The tool surface provides read-only financial access. Output policy also applies to explanations, research, reports, artifacts, and messages, so a read-only tool cannot justify a specific investment recommendation. The exact enforcement mechanism remains open; its observable behavior must meet US-CHAT-06.

**All admitted financial operations must be read-only, and raw provider credentials must stay outside the sandbox.** For supported HTTPS/provider authentication, **credential brokering** uses a native egress proxy to attach credentials outside the sandbox. Trusted proxy policy and provider-enforced credential scope must restrict access to the run's current user, read-only operations, and authorized objects. Do not pass raw provider credentials through sandbox environment variables, files, or generated code. Application-wide financial keys, OAuth client secrets, refresh tokens and refresh handling, database credentials, model keys, and E2B management keys stay in trusted backend processes. Raw provider credentials must not be intentionally placed in prompts, skills, job payloads, persistent model memory, or traces.

When application signing, cross-user authority, or proxy-incompatible authentication prevents that scope, keep the authority in the backend and expose a thin, user-bound read API bridge for programmatic calls from E2B. It may cover broad provider operations, but cannot sign arbitrary requests, forward unrestricted traffic, or expose app-wide user listing. SnapTrade Commercial requires this boundary because its user ID and secret are not standalone authority. Trusted run/user bindings, read-only operation checks, and provider/backend object checks enforce scope. A narrowly scoped run credential or opaque placeholder may identify access; neither replaces those checks. The exact run-to-bridge authentication mechanism remains open and is separate from model-facing tool dispatch.

Generated code naturally receives the current user's authorized financial data for the task. **This data exposure is an explicitly accepted, necessary trade-off** for flexible analysis. No run may access another user's private data or credentials. Credential brokering keeps raw provider credentials outside the VM but does not prevent financial-data disclosure through program outputs or allowed outbound requests, and a provider response may expose an injected credential. [E2B's secrets facility](https://docs.e2b.dev/secrets) supports native outbound HTTPS injection outside the sandbox; [Vercel's sandbox firewall](https://vercel.com/docs/sandbox/concepts/firewall#credentials-brokering) documents the same pattern without changing the selected hosting. The proxy provider may process raw credentials outside the sandbox VM.

Trusted API and background-worker processes share the financial adapter code and may resolve and decrypt credentials after trusted user, connection, and requested-object authorization. They configure credential brokering or use the credentials through the backend read API bridge. Application-wide keys use GCP Secret Manager; durable per-user provider credentials remain encrypted in PostgreSQL using GCP KMS. The [credential decision](../ADRS/0002-backend-owned-financial-credentials.md) owns credential handling, provider-specific scope, and the accepted exposure trade-off. Exact IAM, provider fields, key configuration, encryption mechanism, and native integration remain open.

### 2.4 Direct chat and channel turns

After verifying the sender and account/channel binding, deduplicating the inbound event, and storing the user message, the backend promptly acknowledges transport receipt. **One active ordinary API/backend process coordinates chat across all users in Phase 1.** When AI owns the conversation, normal chat executes directly there, without a durable BullMQ chat queue. The backend enforces current native conversation ownership; a new inbound message cannot resume AI during human takeover. User messages and background completion events enter the same channel-turn handler, which remains callable independently of the messaging transport. The coordinator is part of the backend, not a separate agent service or a runtime assigned to each user.

Each linked channel has one logical event stream or inbox and **one foreground main-agent turn at a time**. Different channels execute concurrently in that coordinator. Initial ordering may use in-process coordination; it does not select a physical queue, process, or VM per channel. Identity checks, deduplication, authorization, and channel ordering remain required.

A foreground turn is one main-agent processing cycle. It can consume pending user messages, internal completion events, or both, with relevant authorized channel context. It can make several model/tool rounds: one model round may request multiple tools, whose results feed another round. A turn can end with a reply, a delegation acknowledgement, or no unnecessary user-facing message. It is neither one model invocation nor necessarily one user message.

Quick work runs inline. For substantial work, the main agent starts background subagents, receives accepted job IDs, acknowledges as appropriate, and ends the foreground turn. It must not occupy the foreground while waiting for background completion. User messages arriving during an active foreground turn are stored as pending for a later turn and may be handled together. Phase 1 does not require mid-turn steering.

**Accepted deployment and interruption limit:** stop the active API/backend process and start its replacement, accepting brief chat and traffic interruptions. Process or deployment interruption can leave an acknowledged chat message without a reply; persisting a message alone does not resume inference. Phase 1 does not add durable chat workflows, checkpoints, an outbox, or a replay engine. Custom traffic switching, zero-downtime deployment, and distributed chat coordination are deferred until observed need or user impact justifies them.

The API/coordinator hosting baseline is a **GCP Cloud Run Service with instance-based billing**, which provides CPU after the transport response under [Cloud Run's billing settings](https://docs.cloud.google.com/run/docs/configuring/billing-settings). How replacement and possible instance overlap preserve one active coordinator and in-process channel ordering remains open. A [Cloud Run instance limit](https://docs.cloud.google.com/run/docs/configuring/max-instances-limits) alone does not guarantee exclusive ownership. Exact service configuration and lifetime handling remain open; stop/start downtime is accepted.

Use `mystacks-be` only as a deployment reference for GitHub Actions, Workload Identity Federation, Artifact Registry immutable images, migrations, health checks, separate entrypoints and identities, and Secret Manager. This is an independent project with its own deployments, PostgreSQL, queue store, identities, secrets, configuration, pipeline, and resources. No shared `mystacks-be` or `hs-core` resource or dependency is selected. The [hosting decision](../ADRS/0017-cloud-run-worker-pool.md) owns these deployment boundaries.

### 2.5 Human support and reply ownership

The runtime must support the accepted [human support story](../user-stories/assistant.md#27-us-chat-07--reach-human-support-during-support-hours): a user can request a real person in chat and reach staffed support during published hours, with human replies delivered to the originating channel. Support hours and their time zone must be visible. Acknowledging or forwarding the request means the handoff is pending until a human joins. Outside those hours, the reply gives the next opening and how the request or contact will be handled without inventing a response-time promise.

**Bird Conversations is the staff UI for Apple Messages for Business.** The backend enforces one conversation owner through Bird's native ownership integration. When staff take over, automated replies and task reports pause until staff explicitly return control; a new inbound message does not resume AI. Exact native events/API mapping remains open, and the backend must not create a competing conversation ownership source of truth. Staff receive only the issue and authorized account and originating-channel context needed to help; the handoff cannot expose another channel's history, tasks, or results. The user must be able to distinguish human and AI replies. The handoff grants no financial execution authority.

During human takeover, requested analyses and user-created schedules continue and save results; their automated reports remain pending. Human takeover does not itself cancel or restart work. Proactive investigations do not start while automated delivery is unavailable. If a proactive run already started, its result cannot interrupt the human conversation. On explicit handback, the main agent handles pending requested results and considers proactive findings only if still useful and eligible, using correct timestamps, current evidence, and required delivery/authorization checks.

The [conversation ownership decision](../ADRS/0022-human-support-conversation-ownership.md) owns this contract. Support hours, staffing, SLAs, out-of-hours handling, staff context access, and exact Bird ownership and handback integration remain open in [TODO](../TODO.md). WhatsApp human support remains required; selecting Bird for Apple alone does not select WhatsApp transport or staff integration. Apple account approval/experience review, exact permitted financial notification scope, and required notice/opt-outs remain validation items under the [Apple messaging decision](../ADRS/0021-apple-messages-with-bird.md).

## 3. Evidence and conversational answers

### 3.1 Shared financial evidence

The [portfolio design](portfolio.md) owns the account-wide financial connections and evidence contract used by the website connection preview, user-requested chat answers, reports, and digests. Runtime consumers preserve that contract through calculations and presentation, including the evidence needed to interpret aggregation and conversions.

The runtime distinguishes financial observations, research claims, supplied documents, assumptions, and hypothetical results. A source document or retrieved passage is evidence to examine, not an instruction that can change authority or tool access.

Available evidence can support a useful partial answer without routine missing-data warnings. The response must describe its actual scope and must not convert missing information into zero or no risk. Explain material limits on a requested conclusion concisely and offer the closest useful supported answer. Personalization memory does not supply current holdings, prices, or permissions.

Under the [current-evidence decision](../ADRS/0019-current-portfolio-evidence.md), current portfolio analysis requests the latest relevant provider evidence through authorized backend or direct provider reads, allowing brief appropriate reuse. Account-state and market-price freshness are separate; fresh prices cannot make old holdings current, and retrieval time cannot replace source-data time. Delayed data may support bounded historical or reporting claims. Proactive work avoids current-exposure conclusions that depend on unavailable timely evidence, while requested answers remain best effort. Exact age limits and reuse windows remain open. Background completion does not itself establish that the evidence is still current when the main agent uses it.

### 3.2 Request scope and text-first responses

The runtime resolves ambiguity when it materially changes the requested answer, authorized data, or calculation. Otherwise it can state a reasonable assumption and provide useful information. It combines relevant tools and skills within the wealth and assets domain rather than routing every question through a closed intent catalog.

Every answer, research summary, report, scheduled result, and proactive insight leads with the answer or main finding. The response includes key numbers and the relevant reasoning and evidence needed to understand the result, using short paragraphs or bullets that read naturally in the channel. Follow-up messages provide deeper detail. Concision must preserve important reasoning and evidence rather than impose a rigid word count or append routine missing-information warnings.

Response length does not limit execution depth: supported research can examine available sources, calculations can require substantial generated-code work, and background jobs can continue independently before returning a concise result. The [chat-first report decision](../ADRS/0016-chat-first-reports.md) owns the presentation trade-off and deferral of extensive reports and polished web artifacts.

For longer work, the assistant briefly acknowledges the request and describes the intended work, including useful initial information when available. It must clearly distinguish completed findings from work still underway. The main agent chooses inline work or explicit background delegation within the foreground-turn boundary; exact latency targets remain open.

## 4. Continued work and durable outcomes

### 4.1 Background ownership and durable outcomes

Longer work runs as an explicitly delegated background subagent job while the main chat remains usable. Each job has task-scoped instructions and context under its account and originating channel. Ordinary new chat does not silently become input to that job.

The shared PostgreSQL database owns saved task definitions, background run records, statuses, small structured results, and file metadata/references in application tables, separate from Mastra state tables. Private Google Cloud Storage holds retained datasets and workspace files under the [analysis retention decision](../ADRS/0023-analysis-data-retention-and-object-storage.md). A background run retains its original request correlation, authorized input references, task context, progress, and outcome outside the serving worker and disposable sandbox. Results and retained files are inspectable only within their originating channel. Exact record schemas and file-transfer integration remain open.

Scheduled work uses only its originating channel's conversation, tasks, and results alongside authorized shared personal memory and financial evidence. It cannot retrieve another channel's history or work.

Under the **selected BullMQ baseline**, BullMQ owns timing, queue dispatch and claims, and configured job retries; Mastra executes the claimed run. Backend registration creates recurring schedules, and running worker processes execute due work. The dedicated Memorystore for Valkey instance holds queue and schedule data through BullMQ's Redis-compatible backend; it does not start a stopped service. A second independent scheduler or retry owner must not manage the same work. The [task design](tasks.md) owns saved user tasks, their distinct execution runs, and proactive scheduling and failure policies. The [scheduling decision](../ADRS/0004-durable-scheduling-and-queued-execution.md#22-initial-bullmq-baseline-and-shared-postgresql-records) keeps DBOS as a future alternative only when concrete benefits justify adoption, outside the current implementation scope.

The [queue-store decision](../ADRS/0020-managed-valkey-queue-storage.md) selects **one custom-pico node (1.25 GB), cluster mode disabled, zero replicas, AOF flushed every second, `maxmemory-policy=noeviction`, private VPC connectivity, and TLS**. Accept maintenance and node-recovery downtime and possible loss of recent unflushed writes on queue-store failure. AOF does not provide zero-data-loss or exactly-once execution. This initial size makes no future-capacity guarantee; increase memory from measured pressure, add a replica only for observed availability need, and consider clustering only for demonstrated single-node throughput or capacity limits. Exact versions, client integration, region, networking and authentication, provisioning and backup policy, and validation remain open. No separate Redis instance or custom recovery orchestration is selected.

The background consumers share **one background execution queue** for main-agent-delegated, user-created scheduled, and proactive runs, following the [task design's priority and shared-capacity policy](tasks.md#22-backend-definitions-and-queue-execution). They run in a **Cloud Run worker pool separate from API/chat**. Both deployments use the same backend codebase with distinct entrypoints and may reuse one container image. The worker pool has no HTTP ingress. Start with one or two running instances and manually adjust their count as needed; the exact initial count, resources, and application worker job concurrency remain configuration choices. Pool instance count is separate from job concurrency and per-chat admission quotas.

The [worker-pool decision](../ADRS/0017-cloud-run-worker-pool.md) owns idle-instance billing, independent capacity, configurable execution limits, and lifecycle trade-offs. Startup and replacement can delay ready work, and the short shutdown warning cannot guarantee that an expected 5–10-minute job finishes. Stop old application processes and start new ones while independently hosted PostgreSQL and Valkey retain their state. Waiting jobs stay queued; native BullMQ shutdown, reconnection, and stalled-job recovery handle execution within the [scheduling decision's](../ADRS/0004-durable-scheduling-and-queued-execution.md) policy. Deployment does not require an empty queue, a script recreating pending jobs, or a deployment-specific recovery state machine. Exact native attempt accounting and duplicate-result handling remain implementation details within that policy.

The main agent decides from context and actual child job statuses whether the user's request has been answered. There is **no separate overall-request or parent-task lifecycle**, finished flag, mandatory dependency graph, workflow checkpoint, or parent cancellation hierarchy. Stable original-request correlation supports routing and controls; it does not create a parent workflow. Claims about what is still running must use actual job-status tools rather than remembered assumptions.

A one-off analysis does not create a saved recurring task. Phase 1 background recovery restarts an eligible unfinished whole job from the beginning with a fresh E2B sandbox if execution needs one; it does not resume in-agent, model, tool, or live-workspace checkpoints. Saved completed results remain reusable under current authority. Durable job records and saved outputs provide continuity; a live E2B workspace lasts only for its execution run.

### 4.2 Internal results and new main-agent turns

**The main agent owns every agent-authored user reply.** Subagents return internal findings, data, evidence, or artifact references; these need not be ready-to-send reports. The completion flow uses native BullMQ events:

1. The worker saves the completed job state, result, and pending-completion state in PostgreSQL.
2. After that save succeeds, the worker completes its BullMQ job, producing a native completion event.
3. The chat coordinator's `QueueEvents` subscriber receives completions from all workers and resolves trusted stored work bindings.
4. For user-requested work, the coordinator uses stored account, originating-channel, original-request, and job bindings to queue a logical completion event for that channel through the same channel-turn handler used by inbound chat. The application enforces routing, ordering, and current authority.

Proactive completion uses the same subscriber and coordinator for one saved account-level investigation under the [task design's delivery policy](tasks.md). Its qualifying result can serve eligible linked iMessage while proactive insights remain enabled, without WhatsApp delivery or automatic fallback. Exact completion records and dispatch mechanics remain open; the main agent owns every agent-authored reply.

**Native `QueueEvents` is the normal completion wakeup path.** [BullMQ's events guide](https://docs.bullmq.io/guide/events/) documents notifications across workers and the Redis Streams API with bounded, automatically trimmed retention. PostgreSQL remains authoritative for job state and results. Keep **pending/handled state for saved completions**; on startup and periodically, the coordinator checks pending saved completions and routes them through the same ordered channel handler with current authorization, cancellation, channel, and delivery checks. An empty check makes no model call. Recovery reuses completed research without re-enqueuing its analysis. Exact record schemas, sweep interval, handled boundary, crash behavior, and deduplication mechanics remain open, alongside subscriber lifecycle integration and in-process ordering details. This policy does not guarantee exactly-once main-agent turns or replies.

If the channel is idle and AI-owned, the logical completion event starts a **new main-agent turn**. If a foreground turn is active or a human owns the conversation, the completion remains pending without entering current inference or sending an automated report. Explicit staff handback lets the main agent assess pending requested results with correct timestamps and current evidence; proactive findings also require continued usefulness and eligibility. Fresh continuation input includes the original request where applicable, a compact result summary, saved-result references, and current permitted channel context. It does not resume a suspended model call or inherit the child's live sandbox or processes. If this new run needs shell or code execution, it creates its own sandbox and reads authorized saved outputs. Completion is internal evidence, not a new user instruction or added permission.

Within the original authorized purpose, the main agent can read saved result details when needed, call financial tools or E2B, combine available results from several children, delegate further top-level work, reply, or end quietly while another child continues. Event notification and selective reads of saved details are complementary. The main agent does not poll, busy-wait, or hold the foreground waiting for completion. Its actual reply enters normal channel history for follow-ups; child output is not separately posted to the user.

Scheduled and proactive agent work follows the same main-owned reply boundary. The task design owns eligibility, repeat handling, notification history, and policies that require silence. A proactive result does not expand the main agent's authority beyond that investigation's authorized purpose.

### 4.3 Admission limits and subagent capabilities

The configurable initial limit is **five outstanding main-agent-spawned subagent runs per chat**, counting queued and running runs. Terminal runs do not count. If five such runs are outstanding, the main agent reports capacity instead of accepting a sixth delegation, whether the user explicitly requested delegation or the main agent chose it. A new subagent spawned by a main-agent continuation counts toward this same limit.

Scheduler-started recurring and proactive runs are excluded from the main-agent delegation quota. Each user-created scheduled occurrence starts one background agent run independently of that quota. Distinct occurrences of the same saved task are independent: admission does not check whether an earlier occurrence is queued or running, and both can continue in parallel. Eligible due occurrences enter the execution system; actual worker start depends on available capacity and existing lifecycle and authority checks. The [task design](tasks.md) owns the saved-schedule quota, minimum interval, scheduled retry policy, and separate proactive overlap and failure policy. The worker-pool decision owns configurable execution limits and basic capacity evidence; exact limit values remain open.

Only main-agent turns can start background subagents. **Subagents cannot nest:** their tool subset excludes delegation, and backend authorization enforces that boundary. A later main-agent turn can start another top-level run; delegation remains one level deep.

Research, subagent, and proactive runs receive useful authorized read, research, and code-execution tools and shared personal memory read access. Their capability subset must preserve investigation ability. They cannot change settings, connections, personal memory, or saved user tasks, and they cannot directly send user messages. Backend handlers enforce these limits independently of prompts and tool registration.

### 4.4 Progress, failure, cancellation, and delivery

The user can leave chat while longer work continues and receive its result in the originating channel later. In that channel, the user can list jobs, ask for status, inspect results, and cancel a selected job. Another linked channel cannot list or control that work or retrieve its result. Progress messages contain meaningful updates. Jobs reach completion, failure, or cancellation; the user must distinguish these terminal outcomes from work in progress and useful partial output. A tool error or exhausted execution limit must not become an unsupported success claim. Exact status names, progress presentation, and limit values remain open.

The [scheduling decision](../ADRS/0004-durable-scheduling-and-queued-execution.md) limits requested background work to **two total whole-job attempts**, including temporary-failure retries and interrupted or stalled-job recovery. If an unfinished run is interrupted, restart it from the beginning only while the work is still active and authorized and an attempt remains. Reuse a saved completed result instead of rerunning analysis; completion notification or message delivery failure does not restart completed work. Proactive investigation failure or interruption waits for the next eligible check. Cancelled or revoked work does not restart. Exact native attempt accounting and ordinary non-interruption one-off error retry classification remain open within the two-attempt ceiling.

**Accepted chat control:** a user can ask the assistant to stop longer work. The backend records the cancellation request, cancels waiting work, and requests that a running worker stop through native SDK mechanisms where available. Acknowledge the request promptly; only confirm stopped execution or a terminal cancelled state when waiting work has stopped or the running worker has confirmed it stopped. In-flight provider requests may finish and incur cost. After the request, suppress unsent result delivery, including late completions, without cancelling unrelated work. Status remains queryable; a second routine completion notification is not mandatory. Exact statuses, record schemas, native abort mechanisms, and retained partial artifacts remain open. **Steering a running job is low priority and deferred.** A new chat message remains ordinary conversation unless it explicitly invokes a supported job control. Changing a standing task's settings is separate from steering its active attempt.

Before delivering an outcome, the orchestration layer rechecks current permissions, originating-channel validity, native AI conversation ownership, provider sending restrictions, and delivery authority; task results also use current pause and cancellation state. A future-only task edit does not itself invalidate an active attempt using its original instructions. The [task design](tasks.md) owns pauses, edits, retries, and repeated delivery. Disconnecting a channel pauses its scheduled tasks, future runs, and pending deliveries without rerouting them; relinking retains history and work but requires the user to resume tasks from that channel. Cancellation or delivery checks cannot recall an already-started send, and one-off jobs retain the outcome and cancellation guarantees above.

Use provider-supported idempotency, deduplication, or delivery-status checks where available. If submission remains ambiguous after a timeout, record the uncertainty and do not blindly resend automatically. Keep the saved result available when the user asks; delivery failures never rerun completed analysis. Phase 1 accepts occasional reports not arriving automatically. Retry details for definitive send failures remain open under the [channel-turn decision](../ADRS/0009-channel-turns-and-background-subagents.md).

### 4.5 Turn and round examples

These examples use illustrative request text and placeholder market values, not current prices or provider data. They describe logical turns and rounds without selecting framework methods or a storage schema.

**Quick question with several rounds:** the user asks, “What are my connected accounts worth now?”

| Foreground turn | Model/tool round | Work |
| --- | --- | --- |
| Turn 1 | Round 1 | The main agent requests balances and positions from relevant financial tools; several tool calls can share this round. |
| Turn 1 | Round 2 | After reading those results, it requests the supported prices or conversions needed for valuation. |
| Turn 1 | Round 3 | It checks scope and units, then replies with the supported total and key evidence. The turn ends. |

**Background gathering with an intervening question:** the user asks for a portfolio concentration analysis that needs substantial gathering.

| Event | Channel behavior |
| --- | --- |
| Turn 1 | The main agent delegates portfolio gathering, receives accepted job ID A, acknowledges the work, and ends the turn. |
| User asks, “What is ETH's price, and is my analysis still running?” | Turn 2 calls the price and job-status tools, answers with the returned price placeholder and A's actual status, then ends. A continues independently. |
| A completes | The worker saves A's result and pending-completion state in PostgreSQL, then completes the BullMQ job. The coordinator receives `QueueEvents` completion, resolves trusted bindings, and queues a logical completion event; the idle channel starts Turn 3 with the original request, a compact summary, a result reference, and current permitted context. |
| Turn 3 | The main agent reads A's details as needed, checks financial evidence with tools if needed, calls E2B to calculate concentration, reads and checks the calculation result in a later round, and sends the concise analysis. Required outputs persist before the sandbox terminates. |

**Two children with separate completion turns:** the main agent needs portfolio evidence and relevant research for one user question.

| Event | Channel behavior |
| --- | --- |
| Turn 1 | The main agent delegates A for portfolio evidence and B for research, receives both accepted job IDs, acknowledges, and ends. |
| A completes | After A's result is saved and its BullMQ job completes, `QueueEvents` wakes the coordinator to queue the channel event. Turn 2 receives A's summary and result reference, reads details as needed, and checks B's actual status. Because B is still running and no update is useful, the turn ends quietly. The foreground remains free. |
| B completes | The same save, BullMQ completion, notification, and channel-event flow starts Turn 3. It receives B's summary and result reference, reads the children's authorized details as needed, combines the evidence, uses tools or E2B if needed, and replies. |

Each child has its own job state and original-request correlation. Context and actual job statuses let the main agent judge completion without a parent workflow record. Neither child creates another child.

**Messages and completions arriving during a foreground turn:** while Turn 1 is reading financial tool results, the user sends a correction and a worker saves its result in PostgreSQL before completing the BullMQ job. The coordinator receives `QueueEvents` completion, resolves the stored bindings, and queues the originating channel's logical completion event. The backend stores the user message and keeps both inputs pending while Turn 1 continues. After Turn 1 ends, Turn 2 can consume both with current permitted context, address the correction, and assess the compact summary and referenced result. No second foreground turn overlaps Turn 1, and background work never holds the foreground waiting for completion.

**Concurrent channels in one process:** two linked channels have active foreground turns concurrently in the single API/backend coordinator. Each turn uses its own trusted account/channel context and pending events. Another message or completion for either channel waits for that channel's active turn, without blocking the other channel.

**Replacement and interrupted background work:** stopping and starting application processes briefly interrupts chat and traffic; an acknowledged foreground message may require a user retry. Independently hosted PostgreSQL and Valkey retain their state, and waiting jobs remain queued. If a requested background job's first attempt is interrupted before a completed result is saved, native BullMQ recovery restarts the eligible whole job from the beginning as its second and final attempt. A prior temporary-failure retry would already consume that allowance. If a completed result was saved, startup or periodic pending-completion recovery reuses it through the same ordered handler. A cancelled or revoked job does not restart, and an interrupted proactive investigation waits for the next eligible check. The Cloud Run configuration that preserves one active coordinator during replacement remains open.

**Missed wakeup and uncertain delivery:** a worker saves a result and its pending-completion state, but the coordinator misses the queue event. A startup or periodic check finds that saved completion and routes it through the same current authorization, cancellation, and delivery checks. The main agent uses the saved research. If the provider send times out and provider-supported checks cannot establish submission status, the backend records uncertainty and avoids a blind automatic resend. The saved result remains available when the user asks.

**Cancellation while a provider request runs:** the user asks to stop job A. The backend records cancellation and promptly acknowledges that request, requests a native stop where supported, and suppresses A's unsent late result. It does not claim that A stopped until confirmed; the provider request may finish and incur cost. The user can query A's status, and unrelated jobs continue.

## 5. Analysis execution and optional files

### 5.1 Supplied-file ownership and interpretation

File analysis is **low priority**. When an upload has no instructions, the assistant asks what the user wants and clarifies intent before analysis. Clear accompanying instructions guide the work without an unnecessary question.

- An upload is bound to its authenticated owner and authorized analysis before storage or processing. Later reads must enforce the same object access boundary.
- The upload boundary validates supported formats and configured file limits. Parsers treat document text, formulas, embedded content, and CSV cells as untrusted input.
- Extracted values retain their source, relevant date, and units. Unsupported sections and ambiguous values remain visible gaps; supplied statements are not live connected-account observations.
- Instructions embedded in uploads or retrieved material cannot grant tools, authorize an action, or override the user's request. Generated code and untrusted executable content must not run in shared workers.

Supported formats, parsing libraries, upload interfaces, size limits, provider data rights, and handling of damaged or encrypted files remain open. Useful retained analysis data follows section 5.2. These decisions must bound US-CHAT-04 without promising universal document support.

### 5.2 E2B execution and checked results

**Shell, file, and generated-code execution are in Phase 1**, including significant calculations without a supplied file. Create **one E2B sandbox lazily per independent execution run** when shell or code is first needed, then reuse it across successive tool calls and model rounds. A foreground main-agent invocation and each background job attempt own separate sandboxes; concurrent runs and different users never share a live workspace. The Mastra agent loop remains in the shared API or worker process. Prefer native Mastra E2B workspace/tools and provider SDKs; exact package and adapter integration remain open. See [Mastra's E2B integration](https://mastra.ai/integrations/sandboxes/e2b).

The workspace supplies real shell commands, file reads and writes, and Python/JavaScript execution. Files remain available between calls during that run, so the agent can inspect inputs, run a calculation, check output, and refine it. Native interpreter contexts may also be reused within the run; shell and Python contexts do not imply shared language globals. Backend tools can fetch selected data and materialize run files, returning compact metadata and paths rather than sending every raw row through model context. Programmatic tool calling can combine provider SDK/API reads, pagination, concurrency, fetching, and analysis in one script through credential brokering or the backend read API bridge, without a model round after each read. Both paths preserve source, as-of, coverage, units, and other financial evidence needed to check the result.

**Sandbox egress is default-deny with backend-controlled access to required provider and backend read-bridge endpoints.** Analysis with no outbound need can remain offline. E2B's [internet access](https://docs.e2b.dev/network/internet-access) is enabled by vendor default, so the backend must configure the selected restriction. General web search and page reading use separate backend research tools. Neither path may reach unauthorized private infrastructure or another user's objects. Domain rules and credential brokering do not guarantee prevention of financial-data exfiltration, and sensitive web-tool queries can disclose data. No unrestricted internet access is selected.

The [credential decision](../ADRS/0002-backend-owned-financial-credentials.md) requires raw provider credentials to remain outside the sandbox, credential brokering for supported HTTPS/provider authentication, and a backend read API bridge for application signing or proxy-incompatible authentication. Trusted run/user, read-only operation, and object authorization apply to both access paths. Data scope, credential brokering, network policy, and resource limits enforce the sandbox boundary; a command-word allowlist or skill instruction does not establish it.

The tool enforces configured execution limits and returns errors, outputs, and any generated files to the runtime. Before using results, the runtime checks that they address the selected inputs and method, with appropriate numerical and unit checks. A successful process exit alone is not a verified financial conclusion.

Before destroying the sandbox, save useful provider inputs actually used, reusable intermediate calculations, final results, and supporting evidence. **Private Google Cloud Storage holds retained datasets and workspace files; PostgreSQL holds records, small structured results, metadata, and file references.** Storage follows purpose rather than a mandatory size threshold, so small tool results need not become files. Examples include provider transaction/trade history, price/position datasets, and cleaned/joined analysis files. Be conservative about discarding useful data, subject to provider data rights; automatic pruning is deferred. This does not require preserving every scratch file or log or promise exact process replay.

Keep account/channel/run ownership, data type, saved time, retrieval time, source as-of time or unknown, provider/connection, size, and storage reference metadata for later identification and cleanup. Saved and retrieval times do not establish source freshness. A later authorized run may restore chosen files into a fresh sandbox; current claims still require current evidence. The backend controls GCS access through native SDKs and run-scoped transfer mechanisms, without broad cloud credentials or unrestricted bucket access for agents or sandboxes. Exact transfer transport, schema, and GCS configuration remain open. The [analysis retention decision](../ADRS/0023-analysis-data-retention-and-object-storage.md) owns the policy; this is not a continuous portfolio-history archive or Phase 1 indexer.

Retained files and enabled artifacts recheck account, originating channel, and permissions; a reference alone grants no access. Failed persistence must not be reported as an available file. Optional visual and artifact formats do not change the text-first reply contract.

Run limits, deadlines, resource budgets, interruption cleanup, artifact formats, provider data rights, and native transfer integration remain open. Useful analysis data is retained conservatively with automatic pruning deferred. A whole-job retry starts from the beginning with a fresh workspace; main-agent continuation uses saved results in a separate run. Sandbox pause does not establish deletion or checkpoint recovery.

### 5.3 Several execution calls in one run

For a portfolio concentration analysis, the shared Mastra loop can make these successive calls in one foreground invocation or one background attempt:

| Step | Work and workspace lifetime |
| --- | --- |
| Gather | A backend read supplies selected evidence and file metadata, or the first shell/code call creates the run's E2B sandbox and a program uses a provider SDK/API through credential brokering or the backend read API bridge to fetch paginated evidence into files. Loops and concurrent reads run without model resampling after each read. |
| Inspect | A shell call uses tools such as `jq`, `grep`, or `sed` to inspect those files; a later Python or JavaScript call reads the same files to calculate concentration. |
| Check and refine | The agent reads compact outputs in the backend loop, checks units and source coverage, and issues another execution call against the same sandbox files if needed. |
| Finish | The backend saves useful retained files to private GCS and results/metadata/references to PostgreSQL under their account/channel before sandbox destruction. A later authorized run may restore chosen files into its own sandbox; an eligible whole-job retry starts over in a fresh sandbox. |

## 6. Memory lifecycle and user control

### 6.1 Native facilities and durable writes

Account-shared personal memory uses **Mastra native schema-based working memory**: a structured profile with a few stable categories and flexible free-text content. Personal facts, goals, and preferences are example categories, with room for useful context that does not fit fixed fields. Exact keys, schema/types, and size and selection budgets remain open. The accepted PostgreSQL database stores application and Mastra state in separate tables under the [shared storage decision](../ADRS/0013-shared-postgresql-storage.md).

The runtime uses native message history and Observational Memory within explicit account and channel-thread scopes. MyStacks owns personal-profile selection and write authority; Mastra's native Observer and Reflector compact channel history. These internal framework routines do not gain authority to update the shared personal profile or alter the one-level research-subagent boundary. Main-agent turns retain native profile updates. Phase 1 does not select vector recall or cross-channel history search.

This small profile is **illustrative, not the final schema**:

```json
{
  "preferences": { "responseStyle": "Concise" },
  "goals": "Build a retirement portfolio over 20 years",
  "notes": "Free-form personal context, including **Markdown**"
}
```

Text fields can contain prose or Markdown. Named-field updates can target a category, but changing one fact inside a text field still requires editing that text. The profile holds personal context; authoritative account configuration, current financial observations, and permissions stay in their backend boundaries.

| Scope | Context and state |
| --- | --- |
| **Stable account** | Shared personal facts, goals, and preferences, plus financial connections and portfolio evidence. Personal memory is one logical resource shared by linked channels. Financial connections and evidence remain in their owning backend boundary. |
| **Channel conversation** | Separate history, current topic, compaction state, independent jobs, scheduled tasks, and results for each linked channel. Transcripts, task records, and results are not merged or mirrored between channels. |
| **Independent job** | Task-scoped instructions, selected inputs, progress, and outcome under the account and originating channel, separate from ordinary chat and other jobs. A job may use authorized shared personal context without copying task records or results into that memory. |

**Native scope direction:** account-resource structured working memory holds useful personal facts; each channel's thread holds its raw history and observational summary. [Mastra working memory](https://mastra.ai/docs/memory/working-memory) supports resource-wide personal context and schema-based profiles; [Observational Memory](https://mastra.ai/docs/memory/observational-memory) supplies per-thread compaction. Exact binding and configuration remain open within these scopes.

For each turn, the runtime assembles the account-shared profile, recent raw messages from that channel, its compact older observations, and relevant authorized request or job inputs. Native history and summaries remain channel-scoped even though the personal profile is shared. The raw stored conversation is retained when it leaves active context; compaction is not transcript deletion.

Mastra checks **token thresholds during agent execution**, rather than keeping a fixed number of messages. The Observer appends observations and the Reflector periodically condenses them. Native buffering can prepare observations in the background as history grows; this work is part of the memory runtime, not a scheduled finance job or a separate application scheduler. The [Observational Memory reference](https://mastra.ai/reference/memory/observational-memory) documents token thresholds and buffering. Its illustrative defaults use an approximately 30,000-token raw-history activation threshold and retain roughly 6,000 raw tokens with `bufferActivation: 0.8`; these are vendor defaults, not selected MyStacks caps. Raw-history, summary, and total model-context budgets, plus Observer and Reflector model choices, remain open.

The assistant **automatically remembers useful personal context**, including facts, goals, preferences, and relevant circumstances learned in either linked channel; users can also explicitly ask it to remember a detail. A clear new user statement automatically updates the applicable older personal fact, goal, or preference without an explicit correction request. These updates apply across linked channels. If conflicting personal statements leave the user's meaning unclear, the assistant asks for clarification only when resolution materially changes the answer; otherwise it answers without treating the disputed fact as settled.

Shared memory must not become a copy of transcripts, task records, or results. Main-agent turns write useful personal context automatically or through explicit user instructions, using native memory facilities under backend-controlled authority. Research and background agents have read access only. The assistant acknowledges only information that was saved, and a correction updates the applicable profile content under the save-order policy in section 6.2. Saved context remains available in a later authorized conversation after worker replacement. Detailed selection, exact schema, and tool configuration remain open within this accepted behavior.

The backend validates account, current channel, and thread bindings before loading history or writing memory. Shared personal context is available from either linked channel, while each conversation keeps its current topic and history. The agent may know which channels exist and explain website controls without loading another channel's transcripts or task logs. A model-supplied item, channel, or thread identifier cannot authorize access.

Retained user-stated or user-confirmed facts and assistant guesses or interpretations must remain distinguishable; the assistant must not present its interpretations as confirmed user facts. Financial observations belong to the financial data boundary. Even the newest user statement about holdings, balances, prices, or access remains user-supplied context and cannot overwrite provider financial evidence or create account permission.

### 6.2 Concurrent updates and correction

Main-agent turns in linked channels may update the same account's personal profile concurrently; background subagents have read access only. Native partial-field updates preserve saved fields outside the supplied update. For the **same field, the last successful save wins**, regardless of user-message order. A slower turn based on an older message can therefore overwrite a newer correction or restore a deleted field. This accepted limit applies across linked channels, as recorded in the [profile save-order decision](../ADRS/0012-last-save-wins-profile-updates.md).

Mastra's [schema-based merge semantics](https://mastra.ai/docs/memory/working-memory#merge-semantics-for-schema-based-memory) deep-merge object fields, replace supplied arrays, and delete fields set to `null`. Supplied text fields are also replaced as whole fields. Facts inside one text or array field do not receive separate merges or conflict ordering; updating one requires supplying that field's new content.

Mastra documents atomic schema-based resource working-memory merges in `@mastra/pg`, using short database row locks; see [working-memory concurrency behavior](https://mastra.ai/docs/memory/working-memory#concurrent-updates). This supports independent-field updates in the selected PostgreSQL store without application-level serialization across channels.

The application does not add a profile lock across channels, per-field timestamps, deletion tombstones, or a custom conflict resolver. Database atomic merging preserves partial-field updates; it does not promise precedence for a newer user message or protection from a later same-field save.

### 6.3 Inspection and profile-only forgetting

**Accepted chat controls:** authorized users can inspect and correct the account-shared personal profile, forget a specific detail, or clear the profile. The same native profile-update tool handles remembering, correction, and forgetting. The main agent infers the affected field or text edit from the user's request and clarifies ambiguity before removing the wrong content. A specific removal preserves unrelated saved facts; “forget everything” clears the saved personal profile. The assistant distinguishes a requested change from a successful save or failure.

The [profile-only forgetting decision](../ADRS/0011-profile-only-forgetting.md) limits this control to the saved personal profile across the account. Channel transcripts and observational summaries remain unchanged. This is not account deletion, financial-data deletion, or erasure of artifacts, backups, or provider records.

**Accepted limit:** a removed fact can remain in current context or retained channel history and summaries, influence an answer, and be learned into the profile again. The agent is instructed not to recreate removed profile content solely from older history, but this is best effort rather than an enforced guarantee. The last-successful-save policy also permits an older in-flight update to restore deleted profile content. The user-facing acknowledgement must explain this scope without promising that the fact can no longer influence answers.

Retention policies for conversation history, profiles, observational summaries, and backups remain open. Useful analysis results and files follow the conservative retention policy in section 5.2, subject to provider data rights, with automatic pruning deferred. Those policies are separate from the accepted profile-only chat control.
