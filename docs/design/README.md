# Phase 1 technical designs

## 1. Scope and authority

**Status: overall architecture under joint review.** This design set supports the **complete Phase 1 experience** described by the [user stories](../user-stories/README.md). It records responsibilities, data and authority boundaries, and execution flows. Agreed product behavior and Phase 1 execution decisions remain distinct from provisional technology integrations and open implementation choices. None of these documents claims a running implementation.

The [architecture](../architecture.md) and [ADRs](../ADRS/) own the accepted shared Mastra runtime, backend application authority, direct foreground chat, BullMQ background execution using [dedicated managed Valkey storage](../ADRS/0020-managed-valkey-queue-storage.md), a [Cloud Run API service and separate worker pool](../ADRS/0017-cloud-run-worker-pool.md) with manual worker scaling, and E2B execution workspaces. The [channel-turn ADR](../ADRS/0009-channel-turns-and-background-subagents.md) explains main-agent ownership of replies, background continuations, and pending completion recovery. These designs refine those decisions. The [requirements](../requirements.md) own product authority, supported connection categories, best-effort monitoring, and information quality.

Phone/SMS signup opens the persistent website dashboard. New and returning users manage financial connections and messaging channels through the same Add account flow, with previews and Add more. Financial connections and channel linking can be completed in either order; financial connections remain optional, while chat requires a verified linked channel. Channel linking supports buttons and QR codes. Chat is the default assistant surface, and each iMessage or WhatsApp chat manages its own one-off jobs, while saved schedules and proactive insights are available only through eligible linked iMessage; personal memory and financial evidence are shared across the account. The [channel scope ADR](../ADRS/0008-channel-scoped-work-and-shared-memory.md) owns that trade-off.

All answers and reports are concise, precise text suited to chat. Available-source research, substantial calculations, and background execution can support that output; image replies are low priority, while extensive deep-research reports and polished website report artifacts are deferred.

Human support is available within working hours and replies in the originating channel. **Bird Conversations** supplies the Apple-channel staff interface; the backend pauses automated delivery during human ownership and requires explicit staff handback. Requested work continues and saves results while proactive starts are suppressed. The [ownership ADR](../ADRS/0022-human-support-conversation-ownership.md) owns that trade-off; staffing, hours, response targets, and WhatsApp integration remain open in [TODO](../TODO.md).

The same backend codebase has distinct Cloud Run API/chat and worker entrypoints and deployments, which may reuse one container image. The API service uses instance-based billing so CPU remains available after HTTP acknowledgement. The worker pool has no HTTP ingress and starts with one or two running instances, adjusted manually as needed; its instance count is separate from application worker job concurrency. One active API/backend coordinator handles all users and channels concurrently, with in-process ordering and one foreground main-agent turn per channel. Deployments stop old application processes and start new ones, accepting downtime. How Cloud Run replacement and possible overlap preserve one active coordinator remains open; an instance limit alone does not establish exclusive ownership. This constraint does not limit background worker replicas.

The project owns its deployments, PostgreSQL, Valkey, private GCS storage, identities, secrets, configuration, pipeline, and resources. `mystacks-be` supplies deployment-flow conventions only, including GitHub Actions, Workload Identity Federation, Artifact Registry immutable images, migrations, health checks, separate entrypoints and identities, and Secret Manager. No shared sibling-project infrastructure or runtime dependency is selected.

One [TimescaleDB-enabled Tiger Cloud PostgreSQL service](../ADRS/0013-shared-postgresql-storage.md) holds application and Mastra records in separately owned ordinary tables; future portfolio-history tables begin as hypertables when that infrastructure is built, while Phase 1 adds no indexer. [Privy with Twilio Verify](../ADRS/0014-stable-account-and-independent-channel-links.md) supplies phone signup/login and maps provider identity to a stable internal account. Native BullMQ `QueueEvents` normally notifies the coordinator after workers save results and complete their jobs; startup and periodic pending-completion checks recover missed wakeups. Exact completion records and deduplication, native attempt accounting, SDK cancellation and identity integration, Tiger Cloud and Cloud Run service configuration and coordinator handoff, Valkey networking/authentication and provisioning, and model provider remain open. Implementation and milestone planning follow agreement on the relevant product behavior and technical contracts.

## 3. Cross-area contracts to preserve

### 3.1 Identity and authority

The backend establishes account and channel identity and authorizes each protected operation. Personal memory and financial access use account scope; conversation histories, user-requested jobs, tasks, and their results additionally enforce their originating channel. Task tools receive the current channel from trusted context, not model-selected destinations. Every execution must remain read-only for financial operations and unable to access another user's private data or credentials.

The [credential decision](../ADRS/0002-backend-owned-financial-credentials.md) keeps raw provider secrets outside sandbox environments, files, and prompts. **Credential brokering** supplies supported provider authentication through native egress-proxy injection outside the VM; application signing or proxy-incompatible authentication uses a user-bound backend read bridge. The backend chooses the user, destination, read scope, and object authority. Authorized current-user financial-data exposure is an accepted trade-off; the selected external secret/proxy layer may process credentials. The [capability decision](../ADRS/0006-composable-agent-capabilities.md) owns **programmatic tool calling** through scripts and broad provider SDK/API access; exact run-bound bridge authorization and native proxy integration compatibility remain open.

### 3.2 Financial evidence and memory

Current holdings, prices, and permissions come from authorized backend evidence. Personal memory is shared across channels and can guide explanations, but cannot override those facts or act as a copy of channel transcripts and task logs. Native partial profile updates preserve different fields; the last successful save wins for the same field. Mastra's native Observational Memory manages channel context through token-based compaction, with exact budgets still open. Common calculation definitions keep website, chat, and scheduled work consistent. Evidence retains missing coverage; conversational answers describe their actual scope without routine missing-data warnings. An unknown value is not zero.

The [current-evidence decision](../ADRS/0019-current-portfolio-evidence.md) requires the latest relevant provider evidence at analysis time, with brief appropriate reuse and exact age limits still open. Current account-state freshness and market-price freshness are separate: a new price cannot make old holdings current. Delayed sources can support bounded historical claims, and requested answers explain material limitations concisely; proactive work avoids current-exposure conclusions that lack timely evidence. Provider polling and permitted-use constraints must be resolved without silently changing accepted task frequencies or substituting stale account state.

### 3.3 Work and delivery

Conversations, user-defined tasks, digests, and independent initiative use common protected tools and delivery controls. User messages and background completions enter the same ordered channel handler in the active backend process. Native BullMQ completion events normally notify that coordinator after results are saved in PostgreSQL. Saved completions retain pending/handled state; the coordinator checks pending records at startup and periodically, then uses the same handler with current authorization, cancellation, and delivery checks. Empty checks make no model calls, and completed research is reused. Different channels can run concurrently while each channel has one foreground turn. Direct foreground chat accepts interrupted replies without automatic continuation recovery in Phase 1. A completion turn receives a compact summary and result references, reasons further as needed, and owns the reply. Actual job status belongs to the backend, while the main agent judges whether the user's request is answered. Exact record schema, sweep interval, handled boundary, crash behavior, and deduplication remain open; no exactly-once main-agent turn or reply is guaranteed.

Background job records, compact results, and retained-file references persist in PostgreSQL; retained analysis files persist in private GCS, independently of worker processes. PostgreSQL and Valkey retain state across application restarts. Native BullMQ shutdown, reconnection, and stalled-job recovery keep waiting work queued and restart eligible interrupted requested work from the beginning within at most two total attempts, including temporary-failure retries and interrupted/stalled recovery. Reuse completed results without rerunning successful work. Cancelled work and work whose authority has been revoked do not restart; failed or interrupted proactive investigations wait for the next scheduled check. The [scheduling decision](../ADRS/0004-durable-scheduling-and-queued-execution.md) owns this policy and its open native attempt-accounting integration; `attempts=2` alone is not established as sufficient. The selected design needs neither a deployment-specific state machine nor a startup script recreating all pending jobs, an empty queue, or in-agent checkpoints.

Delivery uses provider-supported idempotency, deduplication, or delivery-status checks where available. If a timeout leaves submission ambiguous, record uncertainty and do not blindly resend automatically. Occasional missing automatic reports are accepted, and the saved result remains available on request. Delivery failures never rerun completed analysis; definitive send-failure retry details remain open.

User-requested jobs, histories, and results stay in their originating channel. Saved schedules are supported in iMessage only. Website and chat share the account's **proactive insights** on/off setting, enabled by default for eligible linked iMessage subject to channel permissions. Disabling it or disconnecting iMessage stops investigations and unsent proactive delivery without selecting another destination. WhatsApp cannot receive proactive insights or create/manage iMessage schedules. At most one proactive investigation per account runs at a time. The [Apple messaging ADR](../ADRS/0021-apple-messages-with-bird.md) selects Bird as primary MSP and keeps Photon as a backup integration plan. Schedule eligibility, task intent, execution attempts, and delivery outcomes remain distinct; a subagent result grants no additional permission.

### 3.4 Changes to access and retained data

Website source disconnection stops future reads and changes portfolio coverage. Tasks continue only if remaining authorized data fulfills their request; otherwise pause and explain why once. Channel disconnection pauses that channel's tasks. Restoring a source or channel leaves affected tasks paused until explicit resume from their originating channel. Edits apply to future runs, while current permissions and pause/cancel state still constrain active work. The backend records and promptly acknowledges cancellation requests, cancels waiting work, and requests running workers to stop through native SDK controls where available. Unsent delivery, including late completions, is suppressed after the request; execution is confirmed stopped only when known. In-flight provider requests may finish and incur cost, and submitted messages may not be recallable. Status remains queryable without a mandatory second routine notification. Forgetting updates only the saved personal profile and leaves histories and compact summaries intact; retained context may still influence replies or be relearned. Account deletion is deferred; its future scope and retention policy remain separate from accepted memory controls.

The [analysis storage ADR](../ADRS/0023-analysis-data-retention-and-object-storage.md) retains useful provider inputs, reusable intermediate calculations, and results for follow-ups, with automatic pruning deferred. PostgreSQL holds records, small results, and ownership/evidence/file metadata; GCS holds retained datasets and workspace files. Save useful files before destroying the run's E2B workspace and restore only authorized files in later runs. Provider retention rights and source freshness remain part of the evidence contract; retained files do not establish a Phase 1 indexer or exact reasoning replay.

### 3.5 Execution limits and measured capacity

The [sandbox decision](../ADRS/0003-sandboxed-code-execution.md) owns one E2B workspace per independent run that needs shell or code, reused across that run's calls. Agent reasoning stays in the shared Mastra backend. Whole-job retries start fresh workspaces; a main-agent continuation reads persisted child results rather than inheriting the child's live processes. Shell, file, Python, and JavaScript tools operate under data, credential, network, and resource boundaries. Default-deny egress allows required backend-approved provider calls; general web research uses separate backend tools.

The [worker-pool decision](../ADRS/0017-cloud-run-worker-pool.md) owns configurable execution limits and measurement-first capacity planning. Native SDK controls should bound run length and resource use where appropriate. The backend records per-run duration, model usage, and outcome; operators use those records with queue-delay and resource-use observations to adjust worker instance count and job concurrency manually. Exact limits remain provisional until representative jobs provide evidence. A per-user spending budget system is deferred until actual usage justifies it.

## 4. Design completion criteria

- Each in-scope user journey has a success path, meaningful partial or failure outcomes, and the controls a user needs.
- Each protected action has an owner and a trusted user binding; each durable record has one authority.
- Shared financial evidence supports the portfolio, conversation, and proactive paths without incompatible provider-specific calculations in each consumer.
- Open choices that materially affect behavior, authority, cost, or recovery are explicit rather than hidden in example code or a vendor default.
- Representative verification covers user isolation, partial financial data, actual scheduled eligibility, delivery controls, durable memory, and sandbox execution through their real application boundaries.

These criteria guide the joint architecture review and later targeted implementation checks. Capturing a tentative approach does not finalize it or authorize implementation.
