# MyStacks backend context

## 1. Purpose and current state

`ms-agentic-be` is the canonical repository for the MyStacks personal investing agent backend. The repository contains agreed product requirements, selected architecture components, and a **tentative overall architecture** for joint review, with no runtime implementation or implementation plan.

The design uses **Mastra as the framework for the shared custom runtime**, direct foreground chat execution, durable scheduling and queued background execution, and **E2B execution workspaces for shell, files, Python, and JavaScript**. **Private Google Cloud Storage (GCS)** retains useful analysis files; PostgreSQL holds their metadata and references. **One TimescaleDB-enabled Tiger Cloud PostgreSQL service** stores application and Mastra records in separately owned ordinary tables. A **GCP Cloud Run Service** hosts the API/coordinator with CPU available after HTTP acknowledgement; a separate **Cloud Run worker pool** hosts background consumers, initially with one or two instances and manual scaling. **BullMQ uses dedicated GCP Memorystore for Valkey queue storage.** MyStacks reuses Mastra's agent, skill, tool, context, and memory facilities while owning financial logic and authorization. Orchestration and runtime execution remain separate logical responsibilities. Exact integrations and resource configuration, including Tiger Cloud plan/region/size/backups and single-coordinator handoff during Cloud Run replacement, remain open. Documenting this direction does not authorize implementation or provisioning.

This is an independent project with its own deployments, database, queue store, identities, secrets, configuration, pipeline, and resources. `mystacks-be` supplies deployment conventions only: GitHub Actions, Workload Identity Federation, Artifact Registry immutable images, migrations, health checks, separate entrypoints and identities, and Secret Manager. No shared `mystacks-be` or `hs-core` resource or runtime dependency is selected.

The [scheduling decision](docs/ADRS/0004-durable-scheduling-and-queued-execution.md) keeps DBOS as a future alternative only when concrete benefits justify adoption. The [framework decision](docs/ADRS/0005-mastra-runtime-framework.md) records **low-priority, additive LangSmith tracing**, distinct from LangSmith Deployment, which is not selected.

## 3. Discussion boundaries

Read the requirements and architecture before extending the design. Keep **accepted decisions**, **provisional technology choices**, **open questions**, and **verified implementation** distinct. The architecture glossary defines “existing agentic runtime” as the shared-machine approach represented by `mystacks-be` and `hs-llm-service`; those references do not establish that the required product is implemented.

Product requirements remain authoritative. Phase 1 provides financial information and analysis with read-only financial access; financial execution and specific investment recommendations remain outside its scope. Architecture decisions must preserve the stated monitoring limits and partial-data behavior.

Wallet onboarding supports EVM and Solana wallets through off-chain wallet-control proof before the backend saves a verified connection or imports holdings. EVM wallets sign a readable SIWE message; the exact Solana proof mechanism and supported wallets and networks remain open. The [onboarding design](docs/design/onboarding.md) owns challenge and verification behavior. Routine monitoring uses the established connection without repeated signatures; challenge expiry does not end tracking.

Device timezone is captured once during website onboarding. Users explicitly change their default in the web app or chat; an explicit task timezone overrides only that task. Existing tasks keep their assigned zone unless edited, and confirmations show time and timezone. Re-detection on later website visits is deferred; exact recurrence and daylight-saving mechanics remain open. The architecture separates shared backend financial evidence from personal memory and saved tasks from execution attempts. E2B network access defaults to deny, with backend-approved provider egress when required; required outputs persist before disposable workspaces terminate. Pause is not deletion.

The core Phase 1 user-story discussion is complete. Architecture review resolves individual decisions while the overall design remains tentative. The financial provider baseline and current-evidence requirement are accepted; exact coverage, vendor-use compatibility, and calculation methods remain open. Memory schema and budgets, database and identity integration, framework integration, sandbox configuration, messaging-provider constraints, Tiger Cloud and Cloud Run resource configuration and coordinator handoff, and remaining execution details still need review. Low-priority and deferred capabilities retain their stated scope. User stories and technical design remain separate. Update documentation in requested batches. Accepted trade-offs, including small choices, belong in an explicit ADR or a decision section of an existing ADR. Milestone sequencing and delivery timing follow architecture agreement.

Phone/SMS verification through **Privy with Twilio Verify** opens the website dashboard, where channel linking and optional financial connections can be completed in either order. Assistant chat requires a verified linked channel. Name, goals, and preferences are optional. The [account identity ADR](docs/ADRS/0014-stable-account-and-independent-channel-links.md) owns stable internal identity, unique provider identity, and idempotent account creation on the first authenticated API request. iMessage and WhatsApp linking supports buttons and QR codes, with prepared messages and copy fallbacks; WhatsApp-based login is deferred. Financial setup follows each selected provider's supported authorization flow. The [onboarding](docs/design/onboarding.md) design owns identity, linking, provider setup, and recovery mechanics.

Chat is the default assistant surface. The persistent website dashboard gives new and returning users the same Add account flow, portfolio preview, Add more, and Continue to chat. The website owns adding and removing financial sources and linking or disconnecting messaging channels. The **proactive insights** setting enables or disables eligible linked iMessage delivery and is enabled by default subject to channel permissions. Website and chat share this account setting; WhatsApp is not an eligible destination. Chat replies and requested work retain their originating channel. Chat links users to website connection controls and answers portfolio questions on request. Supported provider renewal is automatic; reconnect requires user action only when the provider requires it.

**Bird is the primary MSP for the iMessage channel, implemented as Apple Messages for Business through our own business account.** Our backend retains Mastra, memory, and scheduling; Bird supplies messaging APIs and the staff conversation interface. Photon remains a backup integration plan, without automatic failover or assumed sender/thread continuity. Apple account approval, exact notification permission and controls, and native integration remain validation work. **WhatsApp supports user-initiated chat and one-off requested analysis; its scheduling, proactive insights, and template messaging are deferred.** The [Apple messaging ADR](docs/ADRS/0021-apple-messages-with-bird.md) owns this channel split.

All Phase 1 answers and reports are text-first, concise, precise, and readable in chat. Lead with the finding, key numbers, and necessary explanation or evidence, then support deeper detail through follow-ups. Substantial research, calculation, and background execution can support concise output. Image replies are low priority; extensive deep-research reports and polished website report artifacts are deferred.

Human support is available within working hours, with replies in the originating channel. **Bird Conversations** is the Apple-channel staff interface; the backend enforces one conversation owner and pauses automated replies during human takeover. Requested analyses and iMessage schedules continue and save results, while automatic delivery waits and proactive investigations do not start. Staff explicitly return control; the main agent then handles pending results according to usefulness, evidence timestamps, and delivery authority. A new user message does not silently resume automation. The [ownership ADR](docs/ADRS/0022-human-support-conversation-ownership.md) owns this policy; staffing, hours, response targets, and WhatsApp staff integration remain open in [TODO](docs/TODO.md).

The [runtime design](docs/design/runtime.md) owns turns, model/tool rounds, and background completion examples. **One active API/backend coordinator serves all users**, with concurrent execution across channels and one foreground main-agent turn per channel. User messages and background completions enter the same channel handler; initial ordering stays in-process. Normal chat runs directly in the Cloud Run API service with CPU available after transport acknowledgement, accepting that interruption may leave an acknowledged message without a reply. Deployments stop old application processes and start new ones, accepting downtime. How Cloud Run replacement and possible overlap preserve one active coordinator remains open; an instance limit alone does not establish exclusive ownership. The main agent handles quick work or delegates to background subagents and releases the channel. Up to five main-agent-spawned subagent runs may be outstanding per chat, counting queued and running work, with no nested spawning. Scheduler-started occurrences are outside that delegation quota.

Background results are internal findings or data. Workers save compact results and retained-file references in PostgreSQL and useful files in GCS before completing their BullMQ jobs. **Native BullMQ `QueueEvents` notifications normally wake the coordinator.** Saved completions retain pending/handled state; the coordinator checks pending completions at startup and periodically, then uses the same ordered channel handler with current authorization, cancellation, and delivery checks. Empty checks make no model calls, and recovery reuses completed research. User-requested work returns to its originating channel; proactive completion uses the saved investigation for eligible linked iMessage delivery. A new main-agent turn receives a compact summary and result references, can investigate further, and owns the reply. Exact completion schema, sweep interval, handled boundary, crash behavior, and deduplication mechanics remain open, without an exactly-once turn or reply guarantee. Original-request correlation supports continuation without a separate overall-request lifecycle or workflow checkpoint system. Research runs have authorized reading and analysis tools, without settings, personal-memory, connection, saved-task, or direct-message mutations.

Delivery uses provider-supported idempotency, deduplication, or status checks where available. If a timeout leaves submission uncertain, record that uncertainty and do not blindly resend automatically; the saved result remains available on request. Occasional missing automatic reports are accepted, and delivery failure never reruns completed analysis. Definitive send-failure retry details remain open in the [task design](docs/design/tasks.md).

The [scheduling ADR](docs/ADRS/0004-durable-scheduling-and-queued-execution.md) records **one shared background queue across accounts**, with priorities ordered as main-agent-delegated subagents, user-created scheduled occurrences, then proactive investigations. Workers process jobs concurrently; priority affects waiting work without interrupting active jobs or reserving capacity. Initial shared-capacity delays are accepted. Split queues with allocated worker capacity only when observed contention justifies it. Normal chat remains outside this queue. BullMQ uses a dedicated [Memorystore for Valkey instance](docs/ADRS/0020-managed-valkey-queue-storage.md): one `custom-pico` node with 1.25 GB, cluster mode disabled, zero replicas, AOF flushed every second, `maxmemory-policy=noeviction`, private VPC connectivity, and TLS. Maintenance/node-recovery downtime and possible loss of recent unflushed writes are accepted; pinned integration and provisioning details still require validation.

**Recovery is at the whole-job boundary.** Independently hosted PostgreSQL and Valkey retain state across application restarts. Native BullMQ shutdown, reconnection, and stalled-job recovery preserve waiting work and restart eligible interrupted requested work from the beginning within at most two total attempts, including temporary-failure retries and interrupted/stalled recovery. Completed results are reused; cancelled or no-longer-authorized work does not restart. Proactive failure or interruption waits for the next scheduled check. This uses native queue behavior without a deployment-specific state machine, empty-queue requirement, or startup recreation of every pending job. Exact attempt accounting and non-interruption one-off failure handling remain open; `attempts=2` alone is not established as sufficient. In-agent checkpoint resumption is outside Phase 1.

The [worker-pool ADR](docs/ADRS/0017-cloud-run-worker-pool.md) owns **measurement-first capacity planning**: configurable execution limits, per-run duration, model usage, and outcome, with manual worker-count and concurrency tuning from observed queue delay and resource usage. Exact limits stay provisional until representative jobs provide evidence; a separate per-user spending-budget system is deferred until actual usage justifies it. Basic measurements do not depend on low-priority LangSmith tracing.

Personal memory and financial connections are shared across the account. Conversation history, current context, compaction, user-requested background jobs, scheduled tasks, and their results stay within their originating channel. Chat can list or manage only that channel's work. Useful personal facts may carry across conversations; shared memory must not become a copy of channel transcripts or task records. The [runtime design](docs/design/runtime.md) owns tentative Mastra mapping and enforcement.

Personal memory uses Mastra's native structured working memory: a few stable categories with flexible free-text content for facts, goals, preferences, and additional context. Native partial merges preserve changes to different fields; the last successful save wins for the same field, including when an older turn saves after a newer correction or deletion. PostgreSQL handles atomic storage merges without custom application-level coordination between channel conversations. A fact inside a text field still requires editing that text. Exact schema and size/selection budgets remain open. The [channel and memory ADR](docs/ADRS/0008-channel-scoped-work-and-shared-memory.md) owns profile representation; the [profile update ADR](docs/ADRS/0012-last-save-wins-profile-updates.md) owns concurrent-save semantics.

Clear new user statements update older personal facts automatically, subject to last-successful-save semantics. Unclear conflicts require clarification when they materially affect the answer; assistant interpretations remain distinguishable from user-confirmed facts. Current financial evidence stays authoritative. Forgetting uses the same memory-update tool to remove saved profile content; forgetting everything clears that profile. Histories and compact summaries remain unchanged, and retained context may still influence replies or be relearned. Avoiding restoration merely from old history is a best-effort model instruction. The [forgetting ADR](docs/ADRS/0011-profile-only-forgetting.md) owns that accepted limit.

Each main-agent turn uses the shared personal profile, recent current-channel messages, compact older channel context, and relevant request or job inputs. Mastra's native Observational Memory triggers compaction from token usage and may prepare observations in the background; it is runtime context maintenance, not a scheduled finance job. Raw messages remain stored. Fixed recent-message counts, cross-channel transcript retrieval, and vector recall are not selected. Exact token budgets and models remain open under the [compaction ADR](docs/ADRS/0010-native-channel-context-compaction.md).

User-created iMessage schedules initially have a minimum one-hour interval and a limit of five enabled tasks per chat; paused tasks do not count. Eligible occurrences are admitted independently of the main-agent delegation quota and any earlier unfinished occurrence of the same task. Scheduled runs may overlap; their expected short duration is an assumption, not a timeout. Known temporary scheduled-execution failures get one automatic retry, then the main agent reports failure if needed while recurrence stays enabled. Exact transient classification, delay, and transport retry behavior remain open.

Scheduled tasks deliver only to their originating channel. Edits affect future runs; pause holds future work and unsent automatic results, and resume uses the next scheduled occurrence without a backlog. The backend records and promptly acknowledges a cancellation request, cancels waiting work, and asks running workers to stop through native SDK controls where available. It suppresses unsent delivery, including late completions, but confirms execution stopped only when known. In-flight provider requests may finish and incur cost; already submitted messages may not be recallable. Status remains queryable without a mandatory second routine notification. Channel disconnection pauses its tasks without rerouting. Financial-source disconnection allows a task to continue only if remaining authorized data fulfills its request; otherwise pause it and explain why once. Restoring a channel or source leaves affected tasks paused until the user resumes them from their originating channel. Disabling proactive insights or disconnecting iMessage stops proactive investigations and unsent proactive delivery without selecting another channel. WhatsApp cannot create or manage an iMessage schedule. The [task design](docs/design/tasks.md) owns these lifecycle and delivery contracts.

The [task design](docs/design/tasks.md) owns proactive investigation eligibility, scheduling, failures, and notification history. Proactive checks target roughly five randomized starts per eligible account between 9 AM and 9 PM in the saved timezone. Each eligible check runs a bounded agent within defined investigation scopes. The window limits starts only; later delivery is allowed. Eligibility is checked before investigation and again before sending. One investigation per account may run at a time; overlapping or missed occurrences are skipped. Each qualifying finding is delivered only to linked, currently eligible iMessage while proactive insights are enabled. Human ownership prevents investigation starts and automated delivery. Investigation failures are recorded internally and wait for the next normal check.

Proactive insight selection prioritizes high precision and accepts lower recall to avoid spam. The user's portfolio, goals, and remembered interests guide relevance; strong evidence and attention criteria must justify a meaningfully new, useful message. Account-level notification history, separate from personal memory, supports novelty judgments across changes to the proactive insights setting. Stay quiet when nothing qualifies and suppress uncertain, minor, repetitive, or low-value findings. Explicitly scheduled updates follow their requested behavior independently. Exact investigation scopes, numeric thresholds, budgets, and evidence mechanisms remain design work. Provider-specific Apple controls remain open in [TODO](docs/TODO.md); minimum compliance requirements must not dictate the general product experience.

Portfolio display defaults to USD while preserving native quantities. The current portfolio aggregates provider-supplied account and wallet data; common calculation definitions serve website, chat, and scheduled work, while E2B supports flexible analysis. Provider-supplied history may support historical analysis. A MyStacks indexer and historical P&L or reconstruction requiring MyStacks infrastructure are deferred at low priority. Balance changes and investment returns remain distinct, with cash-flow separation when evidence supports it. Exact formulas and metrics follow demonstrated provider coverage and product needs.

The [provider baseline](docs/ADRS/0018-managed-financial-data-providers.md) selects **SnapTrade** for Binance, Coinbase, Interactive Brokers (IBKR), moomoo, and Robinhood, **Zerion** for EVM and Solana wallet data, and the direct **Hyperliquid API** at low priority. The target audience has mixed, global accounts; actual regions, account types, and available data remain provider-driven. DeBank is an optional future complement for demonstrated EVM gaps. Bybit, Upbit, and prediction-market connectors are deferred; this does not restrict general finance questions or research. SnapTrade's delayed IBKR feed and regional moomoo support remain unresolved target-coverage gaps, alongside provider polling, permitted proactive use, and retained-evidence terms.

Current portfolio analysis and account-specific proactive conclusions require **fresh or near-fresh relevant evidence**. Tools request the latest relevant provider data at analysis time, allowing brief appropriate reuse. Source-data time remains distinct from retrieval time, and fresh prices applied to old holdings cannot establish current exposure. Delayed evidence may support bounded historical or reporting claims. If timely evidence is unavailable, proactive work avoids dependent current-exposure conclusions; requested answers remain useful with concise material limitations. Exact maximum ages, reuse windows, and freshness service levels remain open under the [current-evidence decision](docs/ADRS/0019-current-portfolio-evidence.md). Approximately five daily proactive checks remain periodic detection, not continuous monitoring.

Hyperliquid setup reuses an eligible verified EVM wallet or verifies control of a new one, then binds the actual user account address for public read calls. Backend authorization still requires the active verified connection. The trusted backend uses on-demand REST through **Webshare**; proxy credentials stay outside model and E2B access. Proxy configuration and request routing/limiting remain open, and Hyperliquid limits still apply per exit IP. Account modes and overlapping provider evidence must not cause double counting. The [portfolio design](docs/design/portfolio.md) owns these read mechanics and open integration details.

The [user-story catalogue](docs/user-stories/README.md) owns priorities. Hyperliquid, file analysis, image replies, alternate display currencies, phone-number changes, recovery, and live steering are low priority. Account deletion, cross-channel work, automatic timezone re-detection, deep-research reports, and website report artifacts are deferred; export remains proposed. Memory inspection, correction, and forgetting retain their accepted account-wide scope.

The [credential ADR](docs/ADRS/0002-backend-owned-financial-credentials.md) owns **application-wide keys in GCP Secret Manager and KMS-encrypted per-user credentials in PostgreSQL**. **Credential brokering** supplies provider authentication outside the VM through a native egress proxy for supported authentication, or a user-bound backend read bridge for application signing or proxy-incompatible authentication. Raw provider secrets stay outside sandbox environments, files, and prompts; the selected external secret/proxy layer may process them. The backend binds the user, destination, read scope, and object authority. A run receives authorized current-user financial data, accepting that generated code can read and disclose that data, while another user's private data and credentials remain inaccessible. The [capability ADR](docs/ADRS/0006-composable-agent-capabilities.md) owns **programmatic tool calling**: scripts compose SDK/API reads, loops, pagination, and concurrency without a bespoke tool or model round for every step. [TODO](docs/TODO.md) tracks exact credential fields, lifecycle, IAM, native integration compatibility, and run-bound bridge authorization.

The [analysis retention ADR](docs/ADRS/0023-analysis-data-retention-and-object-storage.md) selects **conservative retention of useful analysis data**, with automatic pruning deferred. Retain provider inputs actually used, reusable intermediate calculations, and final results under permitted provider terms. PostgreSQL holds ordinary records, small structured results, ownership and evidence metadata, and file references; private **GCS** holds retained datasets and workspace files. Save useful files before destroying E2B, then restore selected authorized files into a fresh sandbox when needed. Account/channel/run, data type, saved and retrieval times, source as-of time, provider/connection, and size support later identification and cleanup. Saved data supports follow-ups without establishing current freshness, exact process replay, or a Phase 1 indexer.

The architecture owns the remaining decisions about package versions and integration, models, Tiger Cloud and Cloud Run resource configuration and coordinator handoff, Valkey networking/authentication and provisioning details, record schemas and retention, memory selection and budgets, job lifecycle integration, sandbox configuration, tools, and provider data handling. Vendor documentation is evidence to evaluate, not a guarantee of deployed behavior or approval to send customer data.
