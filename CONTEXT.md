# MyStacks backend context

## 1. Purpose and current state

`ms-agentic-be` is the canonical repository for the MyStacks personal investing agent backend. The repository contains agreed product requirements, selected architecture components, and a **tentative overall architecture** for joint review, with no runtime implementation or implementation plan.

The design uses **Mastra as the framework for the shared custom runtime**, direct foreground chat execution, durable scheduling and queued background execution, and **E2B for isolated generated-code execution**. **One PostgreSQL database** stores application and Mastra records in separately owned tables. **GCP Cloud Run worker pools** host background consumers separately from the API/chat deployment, initially with one or two instances and manual scaling. MyStacks reuses Mastra's agent, skill, tool, context, and memory facilities while owning financial logic and authorization. Orchestration and runtime execution remain separate logical responsibilities. **BullMQ is the initial background queue baseline; its Redis-backed integration remains provisional.** API/chat and database hosting, worker-pool configuration, and detailed operating policies remain open. Documenting this direction does not authorize implementation or provisioning.

The [scheduling decision](docs/ADRS/0004-durable-scheduling-and-queued-execution.md) keeps DBOS as a future alternative only when concrete benefits justify adoption. The [framework decision](docs/ADRS/0005-mastra-runtime-framework.md) records **low-priority, additive LangSmith tracing**, distinct from LangSmith Deployment, which is not selected.

## 3. Discussion boundaries

Read the requirements and architecture before extending the design. Keep **accepted decisions**, **provisional technology choices**, **open questions**, and **verified implementation** distinct. The architecture glossary defines “existing agentic runtime” as the shared-machine approach represented by `mystacks-be` and `hs-llm-service`; those references do not establish that the required product is implemented.

Product requirements remain authoritative. Phase 1 provides financial information and analysis with read-only financial access; financial execution and specific investment recommendations remain outside its scope. Architecture decisions must preserve the stated monitoring limits and partial-data behavior.

Wallet onboarding supports EVM and Solana wallets through off-chain wallet-control proof before the backend saves a verified connection or imports holdings. EVM wallets sign a readable SIWE message; the exact Solana proof mechanism and supported wallets and networks remain open. The [onboarding design](docs/design/onboarding.md) owns challenge and verification behavior. Routine monitoring uses the established connection without repeated signatures; challenge expiry does not end tracking.

Device timezone is captured once during website onboarding. Users explicitly change their default in the web app or chat; an explicit task timezone overrides only that task. Existing tasks keep their assigned zone unless edited, and confirmations show time and timezone. Re-detection on later website visits is deferred; exact recurrence and daylight-saving mechanics remain open. The architecture separates shared backend financial evidence from personal memory and saved tasks from execution attempts. Financial-analysis sandboxes default to outbound internet off; required outputs persist before disposable sandboxes terminate. Pause is not deletion.

The core Phase 1 user-story discussion is complete. Architecture review resolves individual decisions while the overall design remains tentative. The financial provider baseline and current-evidence requirement are accepted; exact coverage, vendor-use compatibility, and calculation methods remain open. Memory schema and budgets, database integration, identity, framework integration, sandbox configuration, messaging-provider constraints, hosting, and remaining execution policies still need review. Low-priority and deferred capabilities retain their stated scope. User stories and technical design remain separate. Update documentation in requested batches. Accepted trade-offs, including small choices, belong in an explicit ADR or a decision section of an existing ADR. Milestone sequencing and delivery timing follow architecture agreement.

Phone/SMS verification opens the website dashboard, where channel linking and optional financial connections can be completed in either order. Assistant chat requires a verified linked channel. Name, goals, and preferences are optional. A primary verified login phone number belongs to a stable MyStacks account. iMessage and WhatsApp linking supports buttons and QR codes, with prepared messages and copy fallbacks; WhatsApp-based login is deferred. Financial setup follows each selected provider's supported authorization flow. The [onboarding](docs/design/onboarding.md) design owns identity, linking, provider setup, and recovery mechanics.

Chat is the default assistant surface. The persistent website dashboard gives new and returning users the same Add account flow, portfolio preview, Add more, and Continue to chat. The website owns adding and removing financial sources and linking or disconnecting messaging channels. Dashboard and chat share the **proactive insight delivery channels** setting, which selects one, both, or none of the linked channels. Every newly linked channel is selected by default. That setting routes only proactive insights; chat replies and requested work retain their originating channel. Chat links users to website connection controls and answers portfolio questions on request. The website asks users to reconnect only when provider access requires their action; supported renewal is automatic, while temporary outages remain unavailable states.

All Phase 1 answers and reports are text-first, concise, precise, and readable in chat. Lead with the finding, key numbers, and necessary explanation or evidence, then support deeper detail through follow-ups. Substantial research, calculation, and background execution can support concise output. Image replies are low priority; extensive deep-research reports and polished website report artifacts are deferred.

Human support is available within working hours, with replies in the user's originating channel. [US-CHAT-07](docs/user-stories/assistant.md) owns the accepted experience; staffing, hours, timezone, response targets, and the proposed internal Slack tool remain open in [TODO](docs/TODO.md).

The [runtime design](docs/design/runtime.md) owns turns, model/tool rounds, and background completion examples. **One active ordinary API/backend process coordinates chat for all users**, with concurrent execution across channels and one foreground main-agent turn per channel. User messages and background completions enter the same channel handler; initial ordering can stay in-process. Normal chat runs directly in the backend, accepting that interruption may leave an acknowledged message without a reply. Coordinator deployments use a simple stop-and-start sequence with brief chat/traffic interruption; distributed coordination and additional traffic-switching machinery wait for observed demand and user impact. API hosting and execution support after acknowledgement remain open. The main agent handles quick work or delegates to background subagents and releases the channel. Up to five main-agent-spawned subagent runs may be outstanding per chat, counting queued and running work, with no nested spawning. Scheduler-started occurrences are outside that delegation quota.

Background results are internal findings or data. Workers save results in PostgreSQL before completing their BullMQ jobs. **Native BullMQ `QueueEvents` notifications wake the coordinator**, which resolves trusted stored bindings. User-requested work returns to its originating channel; proactive completion uses one saved investigation for the selected eligible destinations under the task delivery policy. An available destination channel starts a new main-agent turn with a compact summary and result references; the agent can retrieve details, combine results, call tools or E2B, delegate another step, or reply. The main agent owns conversational output and judges whether the user's request is answered. PostgreSQL remains authoritative for job state and results. Recovery of saved, unhandled results after missed events or coordinator restart is required; its mechanism, event retention, and duplicate-delivery handling remain open without an exactly-once reply guarantee. Original-request correlation supports continuation without a separate overall-request lifecycle or workflow checkpoint system. Research runs have authorized reading and analysis tools, without settings, personal-memory, connection, saved-task, or direct-message mutations.

The [scheduling ADR](docs/ADRS/0004-durable-scheduling-and-queued-execution.md) records **one shared background queue across accounts**, with priorities ordered as main-agent-delegated subagents, user-created scheduled occurrences, then proactive investigations. Workers process jobs concurrently; priority affects waiting work without interrupting active jobs or reserving capacity. Initial shared-capacity delays are accepted. Split queues with allocated worker capacity only when observed contention justifies it. Normal chat remains outside this queue. BullMQ is the initial baseline, with its Redis-backed integration still provisional.

**Recovery is at the whole-job boundary.** Requested background jobs and scheduled occurrences have at most two execution attempts each. Worker interruption restarts unfinished work from the beginning only while it remains active and authorized and has an attempt left; it shares the allowance used by the scheduled known-temporary-failure retry. Completed results are reused, and delivery failure does not rerun analysis. Cancelled or no-longer-authorized work does not restart. Proactive failure or interruption waits for the next scheduled check. In-agent reasoning, model-call, and tool-step checkpoint resumption is outside Phase 1. Exact BullMQ accounting and non-interruption one-off failure handling remain open within these boundaries.

The [worker-pool ADR](docs/ADRS/0017-cloud-run-worker-pool.md) owns **measurement-first capacity planning**: configurable execution limits, per-run duration, model usage, and outcome, with manual worker-count and concurrency tuning from observed queue delay and resource usage. Exact limits stay provisional until representative jobs provide evidence; a separate per-user spending-budget system is deferred until actual usage justifies it. Basic measurements do not depend on low-priority LangSmith tracing.

Personal memory and financial connections are shared across the account. Conversation history, current context, compaction, user-requested background jobs, scheduled tasks, and their results stay within their originating channel. Chat can list or manage only that channel's work. Useful personal facts may carry across conversations; shared memory must not become a copy of channel transcripts or task records. The [runtime design](docs/design/runtime.md) owns tentative Mastra mapping and enforcement.

Personal memory uses Mastra's native structured working memory: a few stable categories with flexible free-text content for facts, goals, preferences, and additional context. Native partial merges preserve changes to different fields; the last successful save wins for the same field, including when an older turn saves after a newer correction or deletion. PostgreSQL handles atomic storage merges without custom application-level coordination between channel conversations. A fact inside a text field still requires editing that text. Exact schema and size/selection budgets remain open. The [channel and memory ADR](docs/ADRS/0008-channel-scoped-work-and-shared-memory.md) owns profile representation; the [profile update ADR](docs/ADRS/0012-last-save-wins-profile-updates.md) owns concurrent-save semantics.

Clear new user statements update older personal facts automatically, subject to last-successful-save semantics. Unclear conflicts require clarification when they materially affect the answer; assistant interpretations remain distinguishable from user-confirmed facts. Current financial evidence stays authoritative. Forgetting uses the same memory-update tool to remove saved profile content; forgetting everything clears that profile. Histories and compact summaries remain unchanged, and retained context may still influence replies or be relearned. Avoiding restoration merely from old history is a best-effort model instruction. The [forgetting ADR](docs/ADRS/0011-profile-only-forgetting.md) owns that accepted limit.

Each main-agent turn uses the shared personal profile, recent current-channel messages, compact older channel context, and relevant request or job inputs. Mastra's native Observational Memory triggers compaction from token usage and may prepare observations in the background; it is runtime context maintenance, not a scheduled finance job. Raw messages remain stored. Fixed recent-message counts, cross-channel transcript retrieval, and vector recall are not selected. Exact token budgets and models remain open under the [compaction ADR](docs/ADRS/0010-native-channel-context-compaction.md).

User-created schedules initially have a minimum one-hour interval and a limit of five enabled tasks per chat; paused tasks do not count. Eligible occurrences are admitted independently of the main-agent delegation quota and any earlier unfinished occurrence of the same task. Scheduled runs may overlap; their expected short duration is an assumption, not a timeout. Known temporary scheduled-execution failures get one automatic retry, then the main agent reports failure if needed while recurrence stays enabled. Exact transient classification, delay, and transport retry behavior remain open.

Scheduled tasks deliver only to their originating channel. Edits affect future runs; pause holds future work and unsent automatic results, resume uses the next scheduled occurrence without a backlog, and cancellation requests that active work stop. Channel disconnection pauses its tasks without rerouting. Financial-source disconnection allows a task to continue only if remaining authorized data fulfills its request; otherwise pause it and explain why once. Restoring a channel or source leaves affected tasks paused until the user resumes them from their originating channel. Removing a channel from proactive insight delivery or disconnecting it does not select another channel automatically. Selecting no channels stops proactive investigations and unsent proactive delivery. The [task design](docs/design/tasks.md) owns these lifecycle and delivery contracts.

The [task design](docs/design/tasks.md) owns proactive investigation eligibility, scheduling, failures, and notification history. Proactive checks target roughly five randomized starts per eligible account between 9 AM and 9 PM in the saved timezone. Each eligible check runs a bounded agent within defined investigation scopes. The window limits starts only; later delivery is allowed. Eligibility is checked before investigation and again before sending. One investigation per account may run at a time; overlapping or missed occurrences are skipped. Each qualifying finding is delivered to all selected, currently eligible verified destinations, with a separate outcome for each channel. Investigation failures are recorded internally and wait for the next normal check.

Proactive insight selection prioritizes high precision and accepts lower recall to avoid spam. The user's portfolio, goals, and remembered interests guide relevance; strong evidence and attention criteria must justify a meaningfully new, useful message. Account-level notification history, separate from personal memory, supports novelty judgments as selected proactive insight delivery channels change. Stay quiet when nothing qualifies and suppress uncertain, minor, repetitive, or low-value findings. Explicitly scheduled updates follow their requested behavior independently. Exact investigation scopes, numeric thresholds, budgets, and evidence mechanisms remain design work. Provider-specific Apple controls remain open in [TODO](docs/TODO.md); minimum compliance requirements must not dictate the general product experience.

Portfolio display defaults to USD while preserving native quantities. The current portfolio aggregates provider-supplied account and wallet data; common calculation definitions serve website, chat, and scheduled work, while E2B supports flexible analysis. Provider-supplied history may support historical analysis. A MyStacks indexer and historical P&L or reconstruction requiring MyStacks infrastructure are deferred at low priority. Balance changes and investment returns remain distinct, with cash-flow separation when evidence supports it. Exact formulas and metrics follow demonstrated provider coverage and product needs.

The [provider baseline](docs/ADRS/0018-managed-financial-data-providers.md) selects **SnapTrade** for Binance, Coinbase, Interactive Brokers (IBKR), moomoo, and Robinhood, **Zerion** for EVM and Solana wallet data, and the direct **Hyperliquid API** at low priority. The target audience has mixed, global accounts; actual regions, account types, and available data remain provider-driven. DeBank is an optional future complement for demonstrated EVM gaps. Bybit, Upbit, and prediction-market connectors are deferred; this does not restrict general finance questions or research. SnapTrade's delayed IBKR feed and regional moomoo support remain unresolved target-coverage gaps, alongside provider polling, permitted proactive use, and retained-evidence terms.

Current portfolio analysis and account-specific proactive conclusions require **fresh or near-fresh relevant evidence**. Tools request the latest relevant provider data at analysis time, allowing brief appropriate reuse. Source-data time remains distinct from retrieval time, and fresh prices applied to old holdings cannot establish current exposure. Delayed evidence may support bounded historical or reporting claims. If timely evidence is unavailable, proactive work avoids dependent current-exposure conclusions; requested answers remain useful with concise material limitations. Exact maximum ages, reuse windows, and freshness service levels remain open under the [current-evidence decision](docs/ADRS/0019-current-portfolio-evidence.md). Approximately five daily proactive checks remain periodic detection, not continuous monitoring.

Hyperliquid setup reuses an eligible verified EVM wallet or verifies control of a new one, then binds the actual user account address for public read calls. Backend authorization still requires the active verified connection. The trusted backend uses on-demand REST through **Webshare**; proxy credentials stay outside model and E2B access. Proxy configuration and request routing/limiting remain open, and Hyperliquid limits still apply per exit IP. Account modes and overlapping provider evidence must not cause double counting. The [portfolio design](docs/design/portfolio.md) owns these read mechanics and open integration details.

The [user-story catalogue](docs/user-stories/README.md) owns priorities. Hyperliquid, file analysis, image replies, alternate display currencies, phone-number changes, recovery, and live steering are low priority. Account deletion, cross-channel work, automatic timezone re-detection, deep-research reports, and website report artifacts are deferred; export remains proposed. Memory inspection, correction, and forgetting retain their accepted account-wide scope.

**Application-wide keys use GCP Secret Manager; per-user provider credentials are encrypted in PostgreSQL using GCP KMS.** Exact provider fields, persistence schemas, IAM, key granularity and rotation, and direct versus envelope encryption remain open. Direct exchange OAuth, aggregator authorization, and API-key connections may yield different credentials and identifiers; required permissions, expiry, and supported renewal follow each provider's contract. Trusted API and background-worker adapters may resolve and decrypt credentials after user and connection authorization. Models and E2B receive data, never secrets. This accepts that a compromised backend process can expose credentials within its service permissions; a separate financial service is deferred until a concrete need. The [credential ADR](docs/ADRS/0002-backend-owned-financial-credentials.md) owns this decision and trade-off, and [TODO](docs/TODO.md) tracks implementation choices and provider validation.

The architecture owns the remaining decisions about package versions and integration, models, API/chat and database hosting, worker-pool configuration, record schemas and retention, memory selection and budgets, job lifecycle, sandbox configuration, tools, and provider data handling. Vendor documentation is evidence to evaluate, not a guarantee of deployed behavior or approval to send customer data.
